**確認は完了した（2026-08-15、`D-023`）。** `Q-011` は `Resolved → D-023`。複勝・ワイドの過去発走前オッズだけ取得経路が見つからず `Q-018` に切り出した。実行時に `race.netkeiba.com` が20年前のレースに空テンプレートしか返さないことが判明したため、`db.netkeiba.com/race/{race_id}/` を探索先に追加している（下記 `PAGES`）。このディレクトリは捨ててよい状態だが、生HTML（`raw/`、gitignore済み）と `check.py` は次に似た確認が要るとき（`Q-018` の調査等）に再利用できるため、当面残す。

## なぜ必要か

**この時点で実データを1行も見ていない。** それなのに `D-001`〜`D-018` の18件の設計判断が積み上がっており、その一部は特定のデータが取れることを前提にしている。前提が崩れたまま仕様書を書き進めると、大半が無駄になる。

先に半日かけて確認する。

## 実行環境

**このリポジトリの開発に使っているリモート環境からは `netkeiba.com` に到達できない**（egress ポリシー）。ローカルの Claude Code か、ネットワーク制約のない環境で実行すること。

依存は標準ライブラリのみ。`Q-008`（実装スタック）が未確定のため、外部パッケージを要求しない作りにしてある。

```bash
python3 tools/q011_feasibility/check.py --race-id <ID> --race-id <ID> ...
```

## 判定基準

スクリプトの出力は **「手掛かりの有無」であって「パースの成否」ではない。** ページ構造を一度も見ずに書いているため、セレクタを断定していない。

`OK` が出たら保存済みHTMLを開いて、**その項目が使える形で存在するか**を目視で確認する。`NG` が出たら、キーワードが外れているだけかもしれないので同様にHTMLを見る。

## 取れなかった場合に見直すもの

| 取れない項目 | 影響 | 見直す対象 |
|---|---|---|
| **実測ラップ** | **設計の柱が崩れる** | `D-007`（2段階構成）。Stage 1 の代替（メンバー構成のみから直接勝率を出す1段構成）か、`D-005` を見直してJRDBを前倒し |
| コーナー通過順 | 期待値上位2領域が消える | `F-101` `F-501`。`domain-knowledge.md` 2節の優先順位を組み替える |
| 払戻（全券種） | バックテストが成立しない | `D-008` の主評価券種。単複のみで回すか、別ソースを足す |
| レース番号・発走時刻 | 同日前後判定ができない | `D-010`。`F-501` `F-502` を諦めるか、判定キーを変える |
| 頭数の内訳 | 母数が定義できない | `D-012`。`F-801` の定義を変える |
| 出走状態 | 返還処理が壊れる | `D-011`。`P-4` の収支計算 |

**実測ラップが取れないケースが最も重い。** ここが崩れたら、仕様書を書く前に `D-007` の再検討から入ること。
