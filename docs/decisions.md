# 決定事項ログ（ADR）

確定した設計判断とその根拠。仕様書からは `D-xxx` で参照する。

書式：

- **決定** … 何を決めたか（断定形で書く）
- **根拠** … なぜそう決めたか
- **影響** … この決定が縛る範囲
- **状態** … `Accepted` / `Superseded by D-xxx`

## D-001 対象範囲はJRA平地G1に限定する

**状態**: Accepted

**決定**: 予測対象はJRA平地G1（年24競走前後）とする。JpnI（地方交流）、J・GI（障害）、海外G1はMVPのスコープ外。

**根拠**: 対象が明確で年間の検証サイクルを回しやすい。ただしG1は情報量・投票数ともに最大で**市場が最も効率的**なレース群であり、収支面では条件戦より難度が高いことを承知のうえでの選択。

**影響**: 予測対象は年24レース。後述 `D-003` のデータ量制約の直接の原因となる。

## D-002 目的は「両建て」とする

**状態**: Accepted

**決定**: オッズを予測に使わない**ファンダメンタルモデル**を主軸に構築し、オッズは最終段の期待値計算でのみ使用する。

**根拠**: オッズを特徴量に入れると精度は上がるが、市場を超える余地が消え回収率の改善に繋がらない。オッズを比較対象として残すことで、的中率（LogLoss / Brier）と回収率の**両方**を評価できる。

**影響**:
- 特徴量パイプラインは「予測対象レースのオッズ」を参照してはならない
- **過去レースのオッズ**は騎手・厩舎の交絡除去に使用してよい（`F-701` / `F-703`、`Q-006`）
- 越えるべき基準線は `normalize(1 / 単勝オッズ)` で定義される市場確率（`architecture.md` 参照）

## D-003 全レースで学習しG1に特化させる

**状態**: Accepted

**決定**: JRA全レース（20年で約90万出走行）で学習し、以下の3手段でG1へ特化させる。

1. クラス（新馬〜G1）を特徴量として保持する
2. 重賞近傍サンプルに `sample_weight` を厚く配分する
3. 最終的な確率校正（calibration）のみG1データで行う

**根拠**: G1のみでは20年遡っても約480レース / 約7,700出走行しかなく、機械学習の学習データとして成立しない。全レース学習なら100倍以上のデータが使える。

**影響**: データ取得はG1だけでなく全レースが対象になる（取得コストが跳ね上がる。`D-005` の段階取得方針の根拠）。

## D-005 データは段階取得とし、ソースは差し替え可能にする

**状態**: Accepted

**決定**:

1. **Phase 1〜3**: 出馬表・成績・ラップ・払戻を無料ソースから20年分取得する
2. **Phase 4以降**: 調教・直前情報が必要になった時点でJRDBを追加購入し合流させる
3. JRA-VAN Data Labは**採用しない**

**根拠**:
- JV-LinkがWindows COM依存であり、開発環境がLinux/Macのみのため実質的に利用不可
- 初期データ収集に時間をかけられる前提のため、無料ソースで着手できる
- 調教データ（坂路タイム・併せ馬・調教評価）は無料範囲では取得困難であり、ドメイン知識を厚く使う `F-4xx` 系の特徴量を実装する段階でJRDBが必要になる

**影響**: 中間スキーマとローダー抽象化（`D-009`）が前提条件になる。無料ソースを使う場合は `Q-001` の解決が着手の必要条件。

## D-006 出力は全出走馬の勝率分布とする

**状態**: Accepted

**決定**: 単一の「本命馬」ではなく、出走全頭の勝率分布を出力する。連系・3連系の確率はPlackett-Luceモデルで勝率から展開する。

**根拠**: 期待値計算には確率が必須であり、確率さえあれば全券種の期待値が一度に計算できる。単一の推奨馬では回収率の評価ができない。

**影響**: モデルの目的関数はレース内の相対順位を直接扱う形になる（`D-007`）。

## D-007 モデルは2段階構成とする

**状態**: Accepted

**決定**:

```
Stage 1  レース質予測モデル（レース単位）
         出走馬構成 → 想定ペース・ラップ構成
Stage 2  適性照合モデル（馬単位）
         馬の適性 × Stage1の出力 → スコア → レース内softmax → 勝率
```

**根拠**: プロの予想プロセスは「レース質の想定 → 求められる適性の特定 → 各馬の照合」の順で進む。馬ごとに独立してスコアを出す一般的なモデル構造ではこの相互作用を表現できない。

またリーク回避の観点で必然でもある。対象レースの実測ラップは発走後にしか判明しないため、メンバー構成から**予測する**工程を挟む以外に手段がない。

**影響**: `domain-knowledge.md` の `F-1xx` 系がStage 1の入出力を規定する。

## D-008 検証はwalk-forward、主評価は複勝・ワイド

**状態**: Accepted

**決定**:

- 時系列walk-forward検証のみを用いる（ランダムCVは禁止）
- 回収率は必ずブートストラップ信頼区間つきで報告する
- **主評価券種は複勝・ワイド**とし、3連単は当面対象外

**根拠**: 検証に使えるG1は約240レース。単勝は1点あたりの標準偏差がσ≈4程度あり、標準誤差は `4/√240 ≈ 26%` になる。つまり**回収率74%〜126%の範囲では有意差を主張できない**。複勝・ワイドは分散が小さく、同一レース数でも遥かに早く有意性が出る。控除率も複勝20%・ワイド22.5%と低い部類にある。

3連単は控除率27.5%かつ超高分散で、検出力が絶望的に低い。

**影響**: バックテストの評価指標セットとレポート様式を規定する。

## D-010 同日レースの前後判定は `(date, course, race_number)` で行う

**状態**: Accepted

**決定**: `races` に `race_number` と `post_time` を持たせる。`F-501` / `F-502` が使う「対象レースより前に発走した同日レース」の判定キーは `(date, course, race_number)` とし、`race_number <` の厳密不等号で絞る。別競馬場のレースは含めない。

**根拠**: 元のスキーマ案は `date` までしか持たず、**前後判定が成立しなかった**。日付粒度で同日レースを引くと対象レース自身と後続レースが混入し、検出困難なリークになる。

判定キーに `post_time` ではなく `race_number` を選ぶのは、同一開催内ではR番号が発走順と一致し、かつ発走時刻より取得の確実性が高いため。`post_time` は補助的に保持する。

別競馬場を含めないのは、馬場バイアスが競馬場ごとの現象であり他場の結果が情報にならないことに加え、複数場開催では `race_number` の大小が発走の前後と一致しないため。

**影響**: `F-501` / `F-502` の実装仕様を規定する。`P-1` のリーク検査（`tests/test_leakage.py`）はこの判定を検証対象に含める。

## D-011 出走状態を `runners.status` で保持する

**状態**: Accepted

**決定**: `runners` に `status` を持たせ、出走・取消・除外・競走中止・失格・降着を区別する。該当行を削除しない。

**根拠**: 元のスキーマ案は状態を表現できず、`finish_pos` を NULL にする以外の手段がなかった。しかし**取消・除外は返還あり、競走中止・失格は返還なし**であり、一律に NULL にすると両者を区別できない。区別できないと、買えなかった馬券を買ったことにして回収率が歪み、`D-008` の検証が成立しなくなる。

行を削除しない理由は、`n_entries` との整合（`D-012`）と、出馬表段階の情報を使う特徴量の再現性のため。

**影響**: `P-4` の払戻計算とバックテストの前提になる。

## D-012 頭数は `n_entries` と `n_starters` を分けて持つ

**状態**: Accepted

**決定**: `races` に出馬表頭数（`n_entries`）と実出走頭数（`n_starters`）の両方を持たせる。`F-901`（レース内相対化）と `F-801`（枠順バイアス）の母数は `n_starters` とする。

## D-013 仕様書の分割基準を定め、番号は識別子として扱う

**状態**: Accepted

**決定**:

1. 独立した仕様書に分けるのは、次のいずれかに当たるとき。
   - 別の人が別のタイミングで実装しうる
   - 変更理由が違う（一方の変更が他方を巻き込まない）
   - 一緒にすると片方が肥大化して保守されなくなる
2. `docs/spec/NNN-*.md` の `NNN` は**取得順に振る連番であり、順序も依存関係も表さない**。Phase は `docs/spec/README.md` の表の列で示す。

**根拠**: 当初の想定リスト11本は構想段階で一度に書いたもので、上記の基準に照らすと3つの取りこぼしがあった。

- データ品質検査（`012`）は `001` の一部にする想定だったが、`001` が**スキーマの形**、`012` が**入ってきたデータの中身の妥当性**であり、変更理由が違う
- 馬場差推定（`013`）は `003` に含める想定だったが、混合効果モデル単体で仕様書1本分の重さがあり、他の特徴量と同じ節に置くと確実に薄くなる。`F-302` と `F-103` の両方が依存する
- 学習パイプライン（`014`）は置き場所自体がなく、`005` / `006` / `007` / `010` が共通で依存するのに各所へ重複して書かれるか誰も書かないかになる状態だった

番号を識別子と割り切るのは、Phase順に振る当初の規定が破綻したため。追加した `012`（`P-0`）と `013`（`P-1`）は既存の `011`（`P-5`）より前段であり、Phase順を維持するには既存番号の付け替えが必要になる。しかし `.claude/rules/docs-writing.md` のID規約は「一度振ったIDは再利用しない」であり、付け替えは相互参照を壊す。

**影響**: `docs/spec/README.md` の想定リストは17本。仕様書間の順序は Phase 列と各仕様書のヘッダ表で読む。

## D-014 一次データソースは netkeiba とする（条件付き）

**状態**: Accepted

**決定**: `P-1`〜`P-3` の一次データソースを netkeiba とする。以下を遵守条件とし、条件が満たせなくなった時点で本決定を見直す。

1. **個人利用に限る。** 取得したデータおよびその派生物を再配布・公開しない
2. **レート制限とローカルキャッシュを実装に組み込む。** 再取得を避け、サーバー負荷を抑える（`002-loader.md` / `019-incremental-update.md` の必須要件）
3. **利用規約と `robots.txt` を定期的に再確認する。** どちらも改定・追加されうるため、決定時点の状態に依存し続けない

**根拠**: 判断時点で確認した材料は次のとおり。

- `robots.txt` が存在せず、`robots.txt` 上の指示に反しない
- 利用規約に自動収集を明示的に禁止する条項が見当たらない。アクセス制限をかけうる旨の条項はあるが、過剰アクセスを対象とするものと解釈した
- JRA全レース・20年遡及・ラップ・コーナー通過順・払戻を単一の無料ソースで揃えられる候補が他にない。JRA-VAN は `D-005` で環境制約により除外済み

ただし `robots.txt` の不在は「許可」ではなく「指示がない」であり、規約の一般条項の解釈余地も残る。上記3条件は、この不確実性に対する緩和策として置いている。

**影響**: `P-0` のローダー実装に着手できる。`002-loader.md` の対象ソースが確定する。ただし `Q-011`（必要なデータ項目が実際に取得できるか）は未解決のまま残るため、**着手のブロッカーは `Q-001` から `Q-011` に移る**。

## D-015 期間の上限は設けず、成功を2段階で定義する

**状態**: Accepted

**決定**: 開発期間・工数の上限は設けない。個人利用であり、反復して改良することを前提とする。代わりに到達目標を2段階で定義する。

| 段階 | 条件 | 意味 |
|---|---|---|
| **A：モデルとして成功** | 開発用検証のG1で LogLoss が市場確率を下回る | オッズに乗っていない情報を掴んでいる |
| **B：馬券として成功** | 封印セット（`D-016`）で LogLoss が市場確率を下回り、かつ複勝・ワイドの回収率のブートストラップ信頼区間の下限が100%を上回る | 実際に収支が改善する |

**Aのみの達成も成果として扱う。** 「モデルとしては市場を超えたが、控除率を埋めるには至らなかった」は失敗ではなく、`D-001` で承知していた難度（G1は市場が最も効率的）の帰結である。

**根拠**: 期間を切らないのであれば、「いつやめるか」より「何を達成したら成功と呼ぶか」を定義するほうが機能する。定義がないと、達成しているのに気づかないか、永久に不足感が残るかのどちらかになる。

段階を分けるのは、`D-002` の両建て方針が2つの異なる目標（確率精度と収支）を持つため。片方の達成をもう片方の未達で打ち消すと、何が進んだのか分からなくなる。

**影響**: `010-backtest.md` のレポートは、AとBを分けて報告する。**期間の上限を設けないことは、反復回数が増えることを意味し、`D-016` の封印を必須にする。**

## D-016 直近3年のG1を封印し、開いた回数を記録する

**状態**: Superseded by `D-017`（封印セットの定義を固定年からローリングに変更）

**決定**:

1. **直近3年のG1（約72レース）を封印セットとし、開発中は一切参照しない。**
2. **封印は「G1での評価」にのみ適用する。学習データ（`D-003` の全レース約90万行）は封印しない。**
3. 封印セットを開いた回数を記録し、**報告時に必ず添える**。開くこと自体は禁止しない。
4. 封印セットの主指標は **LogLoss / Brier** とする。回収率は信頼区間つきの参考値として併記する。

**根拠**: `D-008` の walk-forward は、モデルを改善するたびに同じG1を評価に使う。`D-015` で期間の上限を設けず反復を前提としたため、**検証セットへの適合が累積することが確実**になった。封印しなければ、開発終了時に汎化性能を示す数字が1つも残らない。

学習データを封印しない設計は、開発が止まらないようにするため。全レース約90万行でのランキング性能・特徴量の効き・リーク検査は封印の影響を受けず、開発中のフィードバックループはそのまま回せる。封印が効くのは「G1での最終的な成績を名乗るとき」だけである。

「1回しか開けてはいけない」という禁止にしないのは、個人プロジェクトで守れない規律は機能しないため。回数を計上して報告に添えれば、**3回目に見た数字は1回目より信頼できないという事実が数字と一緒に運ばれる**。禁止より計上のほうが守られる。

主指標を回収率にしないのは、72レースでは回収率の標準誤差が大きすぎて何も言えないため（`D-008` の計算による）。確率指標はレース単位の分散が小さく、72レースでも市場確率との比較に十分な検出力がある。

**影響**: `014-training-pipeline.md`（封印セットを学習・検証の対象から除外する仕組み）と `010-backtest.md`（開封回数の記録と報告様式）を規定する。封印期間3年は `P-3` 着手前であれば見直してよい。開発用検証は約168レースになる。

## D-017 封印セットは「まだ開発に使っていない直近N年」とする（ローリング封印）

**状態**: Accepted（`D-016` を置き換える）

**決定**:

1. 封印セットを **「まだ一度も開発に使っていない直近N年のG1」** と定義する。固定の年ではない。
2. Nの初期値は3年（約72レース）。
3. 開発が長期化して新しい年のG1が蓄積したら、封印セットを更新する。**開封済みの年は開発用に解放してよい。**
4. `D-016` の他の規定はそのまま維持する。
   - 封印は「G1での評価」にのみ適用し、学習データ（`D-003` の全レース）は封印しない
   - 開封回数を記録し、報告時に必ず添える（禁止ではなく計上）
   - 封印セットの主指標は LogLoss / Brier。回収率は信頼区間つきの参考値

**根拠**: `D-016` の固定封印には、**開発中ずっと古い分布に対してチューニングし続ける**という欠陥があった。競馬はドリフトする。`Q-005` に記録したとおり、20年前と現在では「直行 vs 叩き」のトレンドが逆転している。直近を固定封印したまま長期開発すると、最後に開けたときには分布が変わっており、評価そのものが成立しない恐れがある。

`D-015` で期間の上限を設けないと決めたため、開発中に新しいG1が実際に蓄積する（年24競走前後）。**時間の経過が新しい封印データを供給する。** ローリングにすれば、開発が長引くほど封印セットは新鮮になり、古い封印年は開発用に解放される。`D-015` の「急がない」という方針が、この設計では不利ではなく有利に働く。

封印を時系列の中間に置く案は採らない。封印期間より後のデータで学習すると、同じ馬・種牡馬・騎手の将来の成績が逆流し、別種のリークになる。**封印は必ず時系列の末尾に置く。**

**影響**: `D-016` を置き換える。`014-training-pipeline.md`（封印セットの動的な決定と除外）と `010-backtest.md`（開封回数の記録）を規定する。

## D-020 発走前オッズを全券種分、専用テーブルで保持する

**状態**: Accepted

**決定**: `runners.odds_win` だけでは足りないため、発走前オッズを保持する `odds` テーブルを追加する。

```
odds     race_id, bet_type, combination, odds_low, odds_high, as_of
```

- `combination` は `payouts` と同じ表記規則で組を表す（単勝・複勝は1頭、ワイドは2頭）
- **`odds_low` / `odds_high` の2列を持つ。** 複勝とワイドは的中組数によって配当が変わるため、発売中のオッズは幅で提示される。単一値に潰すと期待値計算が成立しない
- `as_of` は取得時点。`Q-003` の予測タイミングによって使う断面が変わる

**根拠**: `D-008` は主評価券種を複勝・ワイドと定めたが、スキーマには単勝オッズしか存在せず、`payouts` は**的中組の払戻しか持たない**。つまり発走前に複勝・ワイドの期待値を計算する材料がどこにもなく、`P-4` の「EV > 1 のみ購入」が構造的に成立しない状態だった。

しかもこの欠陥はバックテストを止めない。単勝オッズで代用するなどして数字は出てしまうため、気づかないまま結果を信じることになる。

**影響**: `001-schema.md` と `002-loader.md` の対象が増える。**取得可否は未確認**であり、`Q-011` の確認対象に加える。取得できない場合は `D-008` の主評価券種を見直す必要がある。

## D-021 レース単位の変数には `F-901` を適用しない

**状態**: Accepted

**決定**: `F-901`（レース内相対化）を適用するのは**馬ごとに値が異なる特徴量に限る**。`F-102`（想定ペース）のようにレース内で全馬共通の値を取る変数は、相対化せず生値のまま Stage 2 に渡す。

`F-104`（`F-102` × `F-103` の交互作用）も相対化しない。相対化するなら `F-103` の側だけに適用し、交互作用は相対化後に取る。

**根拠**: `architecture.md` 4節は「Stage 2の入力は原則すべて相対値であるべき」と書いていたが、これを機械適用すると **`D-007` の2段階構成が実行時に無効化される**。

`F-102` はレース内定数なので、z-score は 0/0 になる。さらに `F-104 = F-102 × F-103` を相対化すると、

```
z(F-104) = sign(F-102) · z(F-103)
```

に代数的に潰れ、**想定ペースの大きさが完全に消える**。`F-102` が 2.7 でも 40.0 でも、相対化後の値は同一になる。Stage 1 が何を予測しても Stage 2 に届かない。

この欠陥はモデルの学習を止めない。正常に学習でき、精度がやや出ないだけなので、テストでは捕まらない。

**影響**: `architecture.md` 4節と `domain-knowledge.md` の `F-901` を修正した。`003-features.md` / `007-stage2-ranker.md` の実装仕様を規定する。

## D-022 `F-501` は通過順位ベースの脚質バイアスとして定義し直す

**状態**: Accepted

**決定**: `F-501` を「当日内外バイアス」から **「当日の脚質バイアス」** に定義変更する。同日・同競馬場・同馬場で先に行われたレースについて、勝ち馬および上位馬の**4角通過順位を頭数で正規化した値**の平均を使う。

内外（ラチからの横位置）バイアスは、直接測る手段がないため当面あきらめる。

**根拠**: 従来の定義は「勝ち馬の4角通過ラチ位置の平均」だったが、**この量は公開データに存在しない**。取得できるのはコーナー通過順位（縦の並び）であって、横位置ではない。実装不能な特徴量を優先度1に置いていた。

通過順位ベースなら実在するデータで構成でき、「先行有利か差し有利か」は測れる。内外バイアスとは別の情報だが、当日の馬場傾向を捉えるという目的には部分的に応える。

**影響**: `domain-knowledge.md` の `F-501` を書き換えた。`domain-knowledge.md` 2節の優先度表は「当日馬場バイアス」を1位に置いているが、**測れる範囲が当初想定より狭い**ため、実データで効果を確認するまで優先度は暫定とする。
