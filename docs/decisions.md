# 決定事項ログ（ADR）

確定した設計判断とその根拠。仕様書からは `D-xxx` で参照する。

書式：

- **決定** … 何を決めたか（断定形で書く）
- **根拠** … なぜそう決めたか
- **影響** … この決定が縛る範囲
- **状態** … `Accepted` / `Superseded by D-xxx`

## D-001 対象範囲はJRA平地G1に限定する

**状態**: Accepted

**決定**: 予測対象はJRA平地G1（年24競走前後）とする。JpnI（地方交流）、J・GI（障害）、海外G1はMVPのスコープ外。

**根拠**: 対象が明確で年間の検証サイクルを回しやすい。ただしG1は情報量・投票数ともに最大で**市場が最も効率的**なレース群であり、収支面では条件戦より難度が高いことを承知のうえでの選択。

**影響**: 予測対象は年24レース。後述 `D-003` のデータ量制約の直接の原因となる。

## D-002 目的は「両建て」とする

**状態**: Accepted（**根拠は `D-124` で取り直した**。決定内容そのものは維持）

**決定**: オッズを予測に使わない**ファンダメンタルモデル**を主軸に構築し、オッズは最終段の期待値計算でのみ使用する。

**根拠**: オッズを特徴量に入れると精度は上がるが、市場を超える余地が消え回収率の改善に繋がらない。オッズを比較対象として残すことで、的中率（LogLoss / Brier）と回収率の**両方**を評価できる。

**影響**:
- 特徴量パイプラインは「予測対象レースのオッズ」を参照してはならない
- **過去レースのオッズ**は騎手・厩舎の交絡除去に使用してよい（`F-701` / `F-703`、`Q-006`）
- 越えるべき基準線は `normalize(1 / 単勝オッズ)` で定義される市場確率（`architecture.md` 参照）

## D-003 全レースで学習しG1に特化させる

**状態**: Accepted

**決定**: JRA全レース（20年で約90万出走行）で学習し、以下の3手段でG1へ特化させる。

1. クラス（新馬〜G1）を特徴量として保持する
2. 重賞近傍サンプルに `sample_weight` を厚く配分する
3. 最終的な確率校正（calibration）のみG1データで行う

**根拠**: G1のみでは20年遡っても約480レース / 約7,700出走行しかなく、機械学習の学習データとして成立しない。全レース学習なら100倍以上のデータが使える。

**影響**: データ取得はG1だけでなく全レースが対象になる（取得コストが跳ね上がる。`D-005` の段階取得方針の根拠）。

## D-005 データは段階取得とし、ソースは差し替え可能にする

**状態**: Accepted

**決定**:

1. **Phase 1〜3**: 出馬表・成績・ラップ・払戻を無料ソースから20年分取得する
2. **Phase 4以降**: 調教・直前情報が必要になった時点でJRDBを追加購入し合流させる
3. JRA-VAN Data Labは**採用しない**

**根拠**:
- JV-LinkがWindows COM依存であり、開発環境がLinux/Macのみのため実質的に利用不可
- 初期データ収集に時間をかけられる前提のため、無料ソースで着手できる
- 調教データ（坂路タイム・併せ馬・調教評価）は無料範囲では取得困難であり、ドメイン知識を厚く使う `F-4xx` 系の特徴量を実装する段階でJRDBが必要になる

**影響**: 中間スキーマとローダー抽象化（`D-009`）が前提条件になる。無料ソースを使う場合は `Q-001` の解決が着手の必要条件。

## D-006 出力は全出走馬の勝率分布とする

**状態**: Accepted

**決定**: 単一の「本命馬」ではなく、出走全頭の勝率分布を出力する。連系・3連系の確率はPlackett-Luceモデルで勝率から展開する。

**根拠**: 期待値計算には確率が必須であり、確率さえあれば全券種の期待値が一度に計算できる。単一の推奨馬では回収率の評価ができない。

**影響**: モデルの目的関数はレース内の相対順位を直接扱う形になる（`D-007`）。

## D-007 モデルは2段階構成とする

**状態**: Accepted

**決定**:

```
Stage 1  レース質予測モデル（レース単位）
         出走馬構成 → 想定ペース・ラップ構成
Stage 2  適性照合モデル（馬単位）
         馬の適性 × Stage1の出力 → スコア → レース内softmax → 勝率
```

**根拠**: プロの予想プロセスは「レース質の想定 → 求められる適性の特定 → 各馬の照合」の順で進む。馬ごとに独立してスコアを出す一般的なモデル構造ではこの相互作用を表現できない。

またリーク回避の観点で必然でもある。対象レースの実測ラップは発走後にしか判明しないため、メンバー構成から**予測する**工程を挟む以外に手段がない。

**影響**: `domain-knowledge.md` の `F-1xx` 系がStage 1の入出力を規定する。

## D-008 検証はwalk-forward、主評価は複勝・ワイド

**状態**: Accepted

**決定**:

- 時系列walk-forward検証のみを用いる（ランダムCVは禁止）
- 回収率は必ずブートストラップ信頼区間つきで報告する
- **主評価券種は複勝・ワイド**とし、3連単は当面対象外

**根拠**: 検証に使えるG1は約240レース。単勝は1点あたりの標準偏差がσ≈4程度あり、標準誤差は `4/√240 ≈ 26%` になる。つまり**回収率74%〜126%の範囲では有意差を主張できない**。複勝・ワイドは分散が小さく、同一レース数でも遥かに早く有意性が出る。控除率も複勝20%・ワイド22.5%と低い部類にある。

3連単は控除率27.5%かつ超高分散で、検出力が絶望的に低い。

**影響**: バックテストの評価指標セットとレポート様式を規定する。

## D-010 同日レースの前後判定は `(date, course, race_number)` で行う

**状態**: Accepted

**決定**: `races` に `race_number` と `post_time` を持たせる。`F-501` / `F-502` が使う「対象レースより前に発走した同日レース」の判定キーは `(date, course, race_number)` とし、`race_number <` の厳密不等号で絞る。別競馬場のレースは含めない。

**根拠**: 元のスキーマ案は `date` までしか持たず、**前後判定が成立しなかった**。日付粒度で同日レースを引くと対象レース自身と後続レースが混入し、検出困難なリークになる。

判定キーに `post_time` ではなく `race_number` を選ぶのは、同一開催内ではR番号が発走順と一致し、かつ発走時刻より取得の確実性が高いため。`post_time` は補助的に保持する。

別競馬場を含めないのは、馬場バイアスが競馬場ごとの現象であり他場の結果が情報にならないことに加え、複数場開催では `race_number` の大小が発走の前後と一致しないため。

**影響**: `F-501` / `F-502` の実装仕様を規定する。`P-1` のリーク検査（`tests/test_leakage.py`）はこの判定を検証対象に含める。

## D-011 出走状態を `runners.status` で保持する

**状態**: Accepted

**決定**: `runners` に `status` を持たせ、出走・取消・除外・競走中止・失格・降着を区別する。該当行を削除しない。

**根拠**: 元のスキーマ案は状態を表現できず、`finish_pos` を NULL にする以外の手段がなかった。しかし**取消・除外は返還あり、競走中止・失格は返還なし**であり、一律に NULL にすると両者を区別できない。区別できないと、買えなかった馬券を買ったことにして回収率が歪み、`D-008` の検証が成立しなくなる。

行を削除しない理由は、`n_entries` との整合（`D-012`）と、出馬表段階の情報を使う特徴量の再現性のため。

**影響**: `P-4` の払戻計算とバックテストの前提になる。

## D-013 仕様書の分割基準を定め、番号は識別子として扱う

**状態**: Accepted

**決定**:

1. 独立した仕様書に分けるのは、次のいずれかに当たるとき。
   - 別の人が別のタイミングで実装しうる
   - 変更理由が違う（一方の変更が他方を巻き込まない）
   - 一緒にすると片方が肥大化して保守されなくなる
2. `docs/spec/NNN-*.md` の `NNN` は**取得順に振る連番であり、順序も依存関係も表さない**。Phase は `docs/spec/README.md` の表の列で示す。

**根拠**: 当初の想定リスト11本は構想段階で一度に書いたもので、上記の基準に照らすと3つの取りこぼしがあった。

- データ品質検査（`012`）は `001` の一部にする想定だったが、`001` が**スキーマの形**、`012` が**入ってきたデータの中身の妥当性**であり、変更理由が違う
- 馬場差推定（`013`）は `003` に含める想定だったが、混合効果モデル単体で仕様書1本分の重さがあり、他の特徴量と同じ節に置くと確実に薄くなる。`F-302` と `F-103` の両方が依存する
- 学習パイプライン（`014`）は置き場所自体がなく、`005` / `006` / `007` / `010` が共通で依存するのに各所へ重複して書かれるか誰も書かないかになる状態だった

番号を識別子と割り切るのは、Phase順に振る当初の規定が破綻したため。追加した `012`（`P-0`）と `013`（`P-1`）は既存の `011`（`P-5`）より前段であり、Phase順を維持するには既存番号の付け替えが必要になる。しかし `.claude/rules/docs-writing.md` のID規約は「一度振ったIDは再利用しない」であり、付け替えは相互参照を壊す。

**影響**: `docs/spec/README.md` の想定リストは17本。仕様書間の順序は Phase 列と各仕様書のヘッダ表で読む。

## D-014 一次データソースは netkeiba とする（条件付き）

**状態**: Accepted

**決定**: `P-1`〜`P-3` の一次データソースを netkeiba とする。以下を遵守条件とし、条件が満たせなくなった時点で本決定を見直す。

1. **個人利用に限る。** 取得したデータおよびその派生物を再配布・公開しない
2. **レート制限とローカルキャッシュを実装に組み込む。** 再取得を避け、サーバー負荷を抑える（`002-loader.md` / `019-incremental-update.md` の必須要件）
3. **利用規約と `robots.txt` を定期的に再確認する。** どちらも改定・追加されうるため、決定時点の状態に依存し続けない

**根拠**: 判断時点で確認した材料は次のとおり。

- `robots.txt` が存在せず、`robots.txt` 上の指示に反しない
- 利用規約に自動収集を明示的に禁止する条項が見当たらない。アクセス制限をかけうる旨の条項はあるが、過剰アクセスを対象とするものと解釈した
- JRA全レース・20年遡及・ラップ・コーナー通過順・払戻を単一の無料ソースで揃えられる候補が他にない。JRA-VAN は `D-005` で環境制約により除外済み

ただし `robots.txt` の不在は「許可」ではなく「指示がない」であり、規約の一般条項の解釈余地も残る。上記3条件は、この不確実性に対する緩和策として置いている。

**影響**: `P-0` のローダー実装に着手できる。`002-loader.md` の対象ソースが確定する。ただし `Q-011`（必要なデータ項目が実際に取得できるか）は未解決のまま残るため、**着手のブロッカーは `Q-001` から `Q-011` に移る**。

## D-015 期間の上限は設けず、成功を2段階で定義する

**状態**: Accepted（**B判定の判定方法は `D-030` で改訂**。2段階の構造そのものは維持）

**決定**: 開発期間・工数の上限は設けない。個人利用であり、反復して改良することを前提とする。代わりに到達目標を2段階で定義する。

| 段階 | 条件 | 意味 |
|---|---|---|
| **A：モデルとして成功** | 開発用検証のG1で LogLoss が市場確率を下回る | オッズに乗っていない情報を掴んでいる |
| **B：馬券として成功** | 封印セット（`D-016`）で LogLoss が市場確率を下回り、かつ複勝・ワイドの回収率のブートストラップ信頼区間の下限が100%を上回る | 実際に収支が改善する |

**Aのみの達成も成果として扱う。** 「モデルとしては市場を超えたが、控除率を埋めるには至らなかった」は失敗ではなく、`D-001` で承知していた難度（G1は市場が最も効率的）の帰結である。

**根拠**: 期間を切らないのであれば、「いつやめるか」より「何を達成したら成功と呼ぶか」を定義するほうが機能する。定義がないと、達成しているのに気づかないか、永久に不足感が残るかのどちらかになる。

段階を分けるのは、`D-002` の両建て方針が2つの異なる目標（確率精度と収支）を持つため。片方の達成をもう片方の未達で打ち消すと、何が進んだのか分からなくなる。

**影響**: `010-backtest.md` のレポートは、AとBを分けて報告する。**期間の上限を設けないことは、反復回数が増えることを意味し、`D-016` の封印を必須にする。**

## D-016 直近3年のG1を封印し、開いた回数を記録する

**状態**: Superseded by `D-017`（封印セットの定義を固定年からローリングに変更）

**決定**:

1. **直近3年のG1（約72レース）を封印セットとし、開発中は一切参照しない。**
2. **封印は「G1での評価」にのみ適用する。学習データ（`D-003` の全レース約90万行）は封印しない。**
3. 封印セットを開いた回数を記録し、**報告時に必ず添える**。開くこと自体は禁止しない。
4. 封印セットの主指標は **LogLoss / Brier** とする。回収率は信頼区間つきの参考値として併記する。

**根拠**: `D-008` の walk-forward は、モデルを改善するたびに同じG1を評価に使う。`D-015` で期間の上限を設けず反復を前提としたため、**検証セットへの適合が累積することが確実**になった。封印しなければ、開発終了時に汎化性能を示す数字が1つも残らない。

学習データを封印しない設計は、開発が止まらないようにするため。全レース約90万行でのランキング性能・特徴量の効き・リーク検査は封印の影響を受けず、開発中のフィードバックループはそのまま回せる。封印が効くのは「G1での最終的な成績を名乗るとき」だけである。

「1回しか開けてはいけない」という禁止にしないのは、個人プロジェクトで守れない規律は機能しないため。回数を計上して報告に添えれば、**3回目に見た数字は1回目より信頼できないという事実が数字と一緒に運ばれる**。禁止より計上のほうが守られる。

主指標を回収率にしないのは、72レースでは回収率の標準誤差が大きすぎて何も言えないため（`D-008` の計算による）。確率指標はレース単位の分散が小さく、72レースでも市場確率との比較に十分な検出力がある。

**影響**: `014-training-pipeline.md`（封印セットを学習・検証の対象から除外する仕組み）と `010-backtest.md`（開封回数の記録と報告様式）を規定する。封印期間3年は `P-3` 着手前であれば見直してよい。開発用検証は約168レースになる。

## D-017 封印セットは「まだ開発に使っていない直近N年」とする（ローリング封印）

**状態**: Accepted（`D-016` を置き換える）

**決定**:

1. 封印セットを **「まだ一度も開発に使っていない直近N年のG1」** と定義する。固定の年ではない。
2. Nの初期値は3年（約72レース）。
3. 開発が長期化して新しい年のG1が蓄積したら、封印セットを更新する。**開封済みの年は開発用に解放してよい。**
4. `D-016` の他の規定はそのまま維持する。
   - 封印は「G1での評価」にのみ適用し、学習データ（`D-003` の全レース）は封印しない
   - 開封回数を記録し、報告時に必ず添える（禁止ではなく計上）
   - 封印セットの主指標は LogLoss / Brier。回収率は信頼区間つきの参考値

**根拠**: `D-016` の固定封印には、**開発中ずっと古い分布に対してチューニングし続ける**という欠陥があった。競馬はドリフトする。`Q-005` に記録したとおり、20年前と現在では「直行 vs 叩き」のトレンドが逆転している。直近を固定封印したまま長期開発すると、最後に開けたときには分布が変わっており、評価そのものが成立しない恐れがある。

`D-015` で期間の上限を設けないと決めたため、開発中に新しいG1が実際に蓄積する（年24競走前後）。**時間の経過が新しい封印データを供給する。** ローリングにすれば、開発が長引くほど封印セットは新鮮になり、古い封印年は開発用に解放される。`D-015` の「急がない」という方針が、この設計では不利ではなく有利に働く。

封印を時系列の中間に置く案は採らない。封印期間より後のデータで学習すると、同じ馬・種牡馬・騎手の将来の成績が逆流し、別種のリークになる。**封印は必ず時系列の末尾に置く。**

**影響**: `D-016` を置き換える。`014-training-pipeline.md`（封印セットの動的な決定と除外）と `010-backtest.md`（開封回数の記録）を規定する。

## D-021 レース単位の変数には `F-901` を適用しない

**状態**: Accepted

**決定**: `F-901`（レース内相対化）を適用するのは**馬ごとに値が異なる特徴量に限る**。`F-102`（想定ペース）のようにレース内で全馬共通の値を取る変数は、相対化せず生値のまま Stage 2 に渡す。

`F-104`（`F-102` × `F-103` の交互作用）も相対化しない。相対化するなら `F-103` の側だけに適用し、交互作用は相対化後に取る。

**根拠**: `architecture.md` 4節は「Stage 2の入力は原則すべて相対値であるべき」と書いていたが、これを機械適用すると **`D-007` の2段階構成が実行時に無効化される**。

`F-102` はレース内定数なので、z-score は 0/0 になる。さらに `F-104 = F-102 × F-103` を相対化すると、

```
z(F-104) = sign(F-102) · z(F-103)
```

に代数的に潰れ、**想定ペースの大きさが完全に消える**。`F-102` が 2.7 でも 40.0 でも、相対化後の値は同一になる。Stage 1 が何を予測しても Stage 2 に届かない。

この欠陥はモデルの学習を止めない。正常に学習でき、精度がやや出ないだけなので、テストでは捕まらない。

**影響**: `architecture.md` 4節と `domain-knowledge.md` の `F-901` を修正した。`003-features.md` / `007-stage2-ranker.md` の実装仕様を規定する。

## D-027 再現性は「同一入力→同一出力」に留め、バックテストに実行時間の要件を課さない

**状態**: Accepted

**決定**:

1. 再現性の要件は **「同じコード・同じデータ・同じ乱数シードで2回実行したとき、出力が完全一致すること」** とする。
2. **過去の任意時点で出せたはずの予測を後から再構成すること（as-of 予測再現）は要件にしない。** 代わりに、出した予測を実行時点で全頭分保存する（`R-008`）。
3. **バックテストの実行時間には上限を設けない。** ただし**推論には課す**（発走15分前、`D-024`）。

**根拠**: as-of 予測再現を要件にすると `017-feature-store.md`（特徴量の実体化）が `P-1` の必須成果物になり、`P-0`〜`P-1` の作業量が増える。個人プロジェクトで最初に積む負債としては重い。予測を出した時点で保存すれば、後から実績と突合する目的は満たせる。

**リーク防止の原則7（集計統計量の推定期間も as-of で切る）はこの決定の対象外であり、要件として維持する**（`R-019`）。原則7の検査は「未来のデータを足して再計算しても過去分の値が1ビットも変わらない」という形式であり、特徴量の実体化を必要としない。**再現性の水準を下げたことを、原則7の緩和と読まないこと。**

実行時間に上限を設けないのは、`D-015` で期間の上限を設けない方針を取っているため。推論だけを例外にするのは、当日予測（`D-024`）が実行時間の制約そのものを含むため。

**影響**: `017-feature-store.md` は必須ではなくなる（想定リストには残すが優先度は下がる）。`014-training-pipeline.md` が乱数シードとモデル保存を規定する。`Q-008` のスタック選定から「性能」という判断基準が1つ減る。

## D-030 B判定の回収率は、互いに素なローリング封印評価を累積して判定する

**状態**: Accepted（`D-015` のB判定の判定方法を改訂する）

**決定**:

1. **B判定の回収率条件は、複数回の封印評価を累積した標本で判定する。** 1回の封印評価（約72レース）では判定しない。
2. **累積対象は互いに素な封印セットに限る。** `D-017` のローリング封印により、開封済みの年は開発用に解放され、次の封印セットは別の年になる。**同じ年を2回カウントしない。**
3. 報告には**累積標本数**と**累積に要した封印評価の回数**を添える（`D-017` の開封回数の記録と同じ扱い）。
4. **B判定の前半（LogLossが市場確率を下回る）は各回の封印評価で判定する。** 累積を要しない。
5. 累積した回収率は、`D-018` に従い年代別成績を併記する。

**根拠**: `D-015` と `D-016`／`D-017` が矛盾していた。`D-015` は封印セットで「複勝・ワイドの回収率のブートストラップ信頼区間の下限が100%を上回る」ことをB判定の条件としたが、`D-016`／`D-017` は同じ封印セットについて「主指標は LogLoss / Brier。回収率は信頼区間つきの参考値」と定め、その根拠として「72レースでは回収率の標準誤差が大きすぎて何も言えない」と書いていた。**要求と、それが測れないという記述が同居していた。**

`D-008` の計算に従えば、検証用240レースから封印72レースに減ると標準誤差は `√(240/72) ≈ 1.8` 倍に広がる。この状態でCI下限を100%より上に持ち上げるのは、要求される効果量が現実的でない可能性が高い。

**累積を選ぶのは、`D-017` のローリング設計が標本を供給する仕組みを既に持っているため。** `D-017` は「時間の経過が新しい封印データを供給する」ことを利点として記録している。互いに素な封印セットを累積すれば、**テストセットの潔白さを保ったまま標本を増やせる**。

他の選択肢を採らない理由。封印期間Nを延ばすと開発用検証が減り、A判定側の検出力が落ちる。回収率条件を「点推定>100%」に緩めると `D-008` の「74%〜126%では有意差を主張できない」と正面から衝突する。回収率を開発用検証で見ると、`D-016` が防ごうとした検証セットへの適合がそのまま入る。

**影響**: **B判定は最短でも数年かかる。** `D-015` は期間の上限を設けていないため方針には反しないが、`D-004` の成果物が出た時点でB判定が未達なのは正常な状態である。A判定は従来どおり開発用検証で判定できる。`010-backtest.md` は累積標本数と評価回数を報告様式に含める。`R-024` の判定方法を書き換えた。**何セット累積すれば足りるかは未定**（`Q-022`）。

## D-036 ストレージは DuckDB とし、可変長データは LIST 型で持つ

**状態**: Accepted（`Q-008` のうちストレージのみを確定する）

**決定**:

1. ストレージは **DuckDB** とする。`001-schema.md` のDDLはDuckDB方言で書く。
2. 長さが可変のデータは **LIST 型**で持つ。対象は `runners.corners`（コーナー通過順）と `payouts` / `odds` の `combination`（組み合わせ）。
3. `combination` の正規形を定める。**順序券種（馬単・三連単）は着順順、非順序券種（馬連・ワイド・三連複・複勝）は馬番の昇順。**

**根拠**: `Q-008` の暫定案がDuckDBであり、変更する理由が出ていない。

LIST 型を選ぶのは、**コーナー通過順の要素数がレースによって変わる**ため。`D-023` の取得データで、東京3R（1600m）は `2-2` の2要素、日本ダービー（2400m）は `12-13-6-6` の4要素であることを確認した。固定列にすると「コーナーが存在しない」と「取得できていない」がどちらも NULL になり区別できず、`R-015` が禁じている状態になる。

`combination` の正規形を定めるのは、`D-020` が「`payouts` と同じ表記規則」とだけ書いて**規則自体を定義していなかった**ため。正規形がないと同じ組が別表記で入り、期待値計算の突合が失敗する。

**影響**: `Q-008` のうちストレージが確定する。**言語・データ処理ライブラリ・モデル・混合効果モデルの実装は未確定のまま残る**（`Q-008`）。`001-schema.md` のDDLがDuckDB方言に固定される。他エンジンへ移す場合はLIST型の置き換えが必要になる。

## D-040 品質検査は `fail` / `warn` の2段階とし、`P-0` の完了条件を「`fail` が0件」とする

**状態**: Accepted

**決定**:

| 重大度 | 意味 | 扱い |
|---|---|---|
| `fail` | **データが壊れていることが確定している。** 論理的に成り立たない状態 | `P-0` の完了条件。1件でもあれば未完了 |
| `warn` | 壊れている可能性がある。**判定に基準値が要るもの** | 件数と年代別分布をレポートに出す。閾値は設けない |

`P-0` の完了条件は **「2〜3年分を取り込んで `fail` が0件」** とする。`warn` は完了条件に含めない。

検査の実行履歴をDBに残す（実行単位と個々の違反）。

**根拠**: `Q-020`（必須項目を欠く行が大量に出た場合どうするか）が未解決であり、**率で判定する検査には基準値がない**。基準がないまま `fail` にすると検査を実装できず、かといって検査自体を作らないと分布が分からず `Q-020` を永久に潰せない。

2段階に分けると、**基準の要らない検査だけで完了判定ができる**。頭数の不一致や着順の矛盾は、閾値なしに「壊れている」と言える。

履歴を残すのは、`Q-020` が「先に基準を決めるのではなく、分布を見てから決めるほうが妥当」と記録しているため。実行のたびに件数が蓄積すれば、それがそのまま判断材料になる。`D-018` の年代別報告と同じ考え方で、年代別に分解して見る。

**影響**: `012-data-quality.md` が検査ごとに重大度を割り当てる。`architecture.md` 7節の `P-0` 完了条件（2〜3年分が再現可能に引ける）を、判定可能な形に具体化する。**`warn` に閾値を設けないため、`warn` が何件あっても `P-0` は完了しうる。** 分布を見て `Q-020` を潰した時点で、一部の `warn` が `fail` に昇格する可能性がある。

## D-044 完走しなかった馬の `corners` は `NULL` とし、意味は `corner_nos` との組で判定する

**状態**: Accepted

**決定**: `runners.corners` の `NULL` は「この馬のコーナー通過順が存在しない」を表す。原因の切り分けは列単独では行わず、`races.corner_nos` と `status` との組で判定する。

| `races.corner_nos` | `runners.status` | `runners.corners` | 読み方 |
|---|---|---|---|
| `[]` | 任意 | `[]` | レースにコーナーが無い |
| 非空 | `出走` / `降着` | 要素数が `corner_nos` と一致 | 正常 |
| 非空 | `競走中止` / `失格` | `NULL` | **正常。** ソースが記録していない |
| 非空 | `出走取消` / `競走除外` | `NULL` | 正常。ゲートを出ていない |
| 非空 | `出走` / `降着` | `NULL` | **異常。** 取得できていない |

最終行だけが取得漏れである。品質検査はこの行のみを検出する。

**根拠**: `R-015` は「無い」と「取れていない」の区別を要求するが、`corners` は単独ではこれを表現できない。空配列はレース単位の事実（コーナーが無い）を表すため、馬単位の事実（この馬には通過順が無い）に流用すると意味が二重になる。

**実データで確認済み。** 日本ダービー2023 の競走中止馬（馬番17）は、レース単位のコーナー通過順位テーブルには4つのコーナーすべてに現れるが、**馬ごとの `通過` 列は空**である。ユニコーンS2019 の競走除外2頭も同様に空。ソースは完走しなかった馬の通過順を馬単位では記録しない。

**影響**: `002-loader.md` の要素数不一致の扱いが「行を棄却」から「`corners = NULL` として取り込み `rejected_rows` に理由を残す」に変わる。`012-data-quality.md` の `corners_uniform` は完走馬に範囲を限定する。`001-schema.md` / `002-loader.md` / `012-data-quality.md` の受け入れケース（日本ダービー2023 が全18行・全検査通過）が3仕様書とも整合する。

## D-045 `fetch_log` は URL ごとに最新の取得結果で上書きする

**状態**: Accepted

**決定**: `fetch_log` は URL ごとに1行とし、再取得時は同じ行を上書きする（upsert）。取得の試行履歴は保持しない。

```sql
INSERT INTO fetch_log (url, source, page_kind, source_key, http_status, outcome, detail, fetched_at)
VALUES (?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT (url) DO UPDATE SET
    http_status = excluded.http_status,
    outcome     = excluded.outcome,
    detail      = excluded.detail,
    fetched_at  = excluded.fetched_at;
```

**根拠**: `url` を主キーに置きながら upsert を規定していなかったため、2回目の取り込みが主キー違反で落ちる。`D-024` は当日の増分取得を複数回行うことを前提としており、再実行は例外ではなく通常の運用である。

上書きにするのは `R-021`（同じ入力から同じ出力）のため。試行履歴を残す形（`(url, fetched_at)` を主キーにする等）にすると、**同じキャッシュから2回取り込んだだけで行数が変わり、`fetched_at` を除いた完全一致が成立しなくなる**。

暗黙のスキップを採らないのは、`outcome` が初回の結果に固定されるため。`http_error` で失敗した URL が後に成功しても失敗のまま残り、`fetch_incomplete`（`012-data-quality.md`）を実態より悪く見せる。

**影響**: `002-loader.md` に upsert 規則が入る。`tasks.md` の冪等性検証タスク（`R-021`）が判定可能になる。

**根拠**: 二重実行は `domain-knowledge.md` 5節が与えた定式化をそのまま実装する形であり、**実装の中身を問わない**。推定器を個別に検査する形は、推定器を1つ足すたびに検査を足す必要があり、足し忘れが検査の穴になる。原則7は「日付フィルタの検査では捕まらない」種類の失敗であり、検査そのものが漏れやすい形では意味がない。

Stage 1 を対象に含めるのは、**`F-102` が Stage 2 の入力だから**である。Stage 1 を全期間で学習すると、過去行の `F-102` が未来のレースに依存する。これは `F-902` の `μ_global` を全期間で推定するのと同じ失敗であり、`domain-knowledge.md` 5節の原則7が名指しする3つに含まれていないのは列挙漏れとみなす。`architecture.md` 6.1 の walk-forward は評価の分割を定めるが、**Stage 1 をどこで学習するかは定めていなかった**。

コストは上がる。fold の数だけ Stage 1 の学習が必要になり、`Q-025` が警告する実行時間の問題に加算される。それでも含めるのは、**含めなければ Stage 1 経由のリークが検査されないまま残る**ため。

**影響**: `003-features.md` に `as_of` 入口を要求する。`006-stage1-pace.md` と `014-training-pipeline.md` が fold ごとの再学習を規定する。`domain-knowledge.md` 5節 原則7 に Stage 1 を追記する。

**追記（2026-08-18、`004` のリーク検査骨組み実装時に判明）**: `μ_global` のような共有統計量を「`build_features` 呼び出し単位の単一定数」として実装すると、この検査に**確実に落ちる**。`as_of` だけで境界を引いた値を全対象行に一律適用すると、別の `as_of` で呼び出したときに以前と同じ対象行の値まで変わってしまう（2つの呼び出しの間に新しいレースが1件でも増えれば、その分だけ全体平均が動くため）。正しい実装は、**対象行ごとに、その行自身のレース日付より前のデータだけで母集団を切り直す**形にする必要がある。二重実行での突き合わせが機能したのはこの誤りを実際に検出できたためであり、`003-features.md` の `F-902` 節に同じ注記を追加した。

## D-055 特徴量の同一性はビット完全一致で判定し、集計順序を決定的にする

**状態**: Accepted

**決定**: `D-054` の突き合わせは**ビット完全一致**で判定する。許容誤差を設けない。

これを成立させるため、`003-features.md` は**集計の順序を決定的にする**。具体的には、集計対象の行を集約前に一意なキー（`(race_id, horse_id)` など）で整列させ、並列実行や辞書の反復順に依存した加算順を作らない。

**根拠**: `R-019` が「1ビットも変わらない」と定めており、判定を緩めるなら要件側を書き換えることになる。許容誤差を置くと、**誤差より小さいリークが通ってしまう**。少サンプルの集計に1レース分の未来が混ざる程度の差は、相対誤差 `1e-12` より小さくなりうる。

浮動小数の加算は結合則を満たさないため、同じ集合でも加算順が変われば結果が変わる。順序を決定的にしないとビット一致は偶然に頼ることになり、**リークが無くてもテストが落ちる**。この場合の落ち方は再現性が低く、原因の切り分けに時間がかかるうえ、「たまに落ちるテスト」として無視される方向に働く。順序の決定性はリーク検査の前提条件である。

**影響**: `003-features.md` の共通規約に「集計順序の決定性」を追加する。`R-021`（同一入力から同一出力）とも整合する。

## D-059 過去走集計は全履歴と直近N走の両方を列として持つ

**状態**: Accepted

**決定**: 過去走を集計するすべての特徴量について、**全履歴の集計**と**直近N走の集計**を別の列として出す。`N` は特徴量ごとの設定値とし、既定値の決定は `P-3` のハイパーパラメータ探索に委ねる（`D-051` の `k` と同じ扱い）。

どちらを使うかをここで決めない。両方を渡し、モデルに選ばせる。

**根拠**: 通算値と直近値は**別の量を測っている**。通算は能力の水準を、直近は充実・衰退の局面を表す。7歳馬の3歳時の成績を同じ重みで入れると現在の状態が見えず、逆に直近だけにすると少走馬の標本がさらに減って `F-902` の縮約が強く効き、情報が全体平均に潰れる。

**実データで裏付けがある。** 3年分で1頭あたりの出走回数は中央値5走（`D-051`）。直近5走に限ると中央値の馬は全履歴と一致し、多走馬だけが差分を持つ。**多走馬こそ通算と直近が乖離する層**であり、そこを見分けられる形にする価値がある。

片方に決め打ちしないのは、どちらが効くかが**特徴量ごとに違う**と見込まれるため。`F-802`（コース適性）は通算が効きそうだが、`F-601`（反動リスク）は直近しか意味を持たない。一律の窓を選ぶと、どちらかの特徴量が必ず損をする。

**影響**: `003-features.md` の共通規約に入る。集計系の列数が約2倍になる。`Q-028`（合成 fixture の規模）は、直近N走の集計が意味を持つ程度の出走履歴を持つ必要がある。

## D-061 `F-103` のペース指数は自馬の寄与を除いて計算する

**状態**: Accepted（`Q-016` を解決）

**決定**: `F-103`（ペース適性）の回帰に使うペース指数 `p_i` を、**その馬自身を除いた他馬だけで再計算した値**とする。

```
p_i^(-self) = そのレースのペース指数を、対象馬を除く出走馬の
              F-101（逃げ意欲）分布から算出した値
β = d_i を p_i^(-self) に回帰した傾き（F-902 で縮約）
```

**根拠**: `Q-016` が指摘したとおり、逃げ馬・先行馬は**自分でそのペースを作っている**。オーバーペースで飛ばして失速した馬は「ハイペースに弱い」と記録されるが、そのハイペースは本人が作ったものであり、適性ではなく自壊を測っている。

自馬を除く形にすると、`p_i` は**その馬にとって外生的な条件**になる。逃げ馬であっても「他に逃げ馬が2頭いた」ことは自分の能力と独立に決まるため、そこへの反応は適性として読める。

脚質で場合分けする案（`Q-016` の候補4）を採らないのは、**逃げ・先行馬の `F-103` が欠損になる**ため。`F-104`（`F-102` × `F-103`）は Stage 2 の中核であり、G1の逃げ馬でこれが効かなくなる損失が大きい。操作変数（候補3）を採らないのは、妥当な操作変数の選定自体が研究課題になり `P-1` の範囲を超えるため。

**この決定は `F-101` に依存する。** `p_i^(-self)` は他馬の `F-101` から算出するため、`F-101` が欠損するレース（1角の無いコース）では `F-103` も計算できない。該当レースでは `F-103` を `NaN` とする（`D-058`）。

**影響**: `Q-016` を `Resolved → D-061` とする。`003-features.md` の `F-103` にレース単位の再計算が入り、実装が重くなる。`F-101` の欠損が `F-103` → `F-104` へ伝播する経路が生まれるため、`003` に明記する。

## D-065 `F-103` のペース指数 `p_i` は「他馬F-101の平均を反転した値」とする

**状態**: Accepted

**決定**: `F-103`（ペース適性）が回帰に使う `p_i`（過去走 `i` におけるペース指数）を、次式で定義する。

```
p_i = 1 − mean(F-101 of 他の出走馬)   # 自馬を除く（D-061）
```

`F-101`（逃げ意欲）は「1角の通過順位/頭数」の下位分位点なので、**小さいほど先行意欲が強い**。他馬の `F-101` 平均が小さい＝先行意欲の強い馬が多い＝先頭を争う馬が多い＝ハイペースになりやすい、という向きになる。`1 −` で符号を反転させ、`p_i` が大きいほどハイペースという直感的な向きに揃える（`domain-knowledge.md` の「`β > 0`: ハイペース得意」という符号規約と整合させるため）。

**この過去走の `p_i` が計算できないケース**: 他の出走馬全員の `F-101` が欠損している過去走（`domain-knowledge.md` 3節・海外馬混在レースなど、全馬が新規参入で過去走を持たない場合）。この場合、その過去走を `d_i ~ p_i` の回帰対象から除外する（1件でも他馬に値があれば、その馬たちの平均で計算する）。

**根拠**: `D-061` は「他馬の `F-101` 分布から算出した値」とのみ定めており、平均・中央値・閾値以下の頭数など複数の集約方法が実在する。平均を選んだのは、他の集約（例えば閾値以下の頭数）が「ハイペース」をどの閾値で判定するかという追加のパラメータを持ち込み、`P-1` の範囲を超える調整対象になるため。分布の要約として最も単純な一次統計量である平均を採用し、必要であれば `P-3` で見直す。

**影響**: `003-features.md` の `F-103` に算出式を明記する。`src/umagic/features/f103.py` はこの式で実装する。

## D-086 Stage 2 の学習データの `F-102` はクロスフィッティングで作る

**状態**: Accepted

**決定**: Stage 2（`007-stage2-ranker.md`）の学習データに与える `F-102`（Stage 1 の出力）を、**inner fold の out-of-fold 予測**として作る。

```
fold の学習期間を時系列で K 分割する
  各ブロック k について:
    ブロック k を除いた学習期間で Stage 1 を学習する
    ブロック k の F-102 をそのモデルで予測する
fold の検証期間の F-102 は、学習期間全体で学習した Stage 1 から予測する
```

この失敗は**モデルが正常に学習でき、検証成績がやや悪くなるだけ**なので、リーク検査（`004-leakage-test.md`）でも通常のテストでも捕まらない。`architecture.md` が `F-901` の適用範囲について警告しているのと同じ種類の、静かに効く設計ミスである。

時系列 hold-out（学習期間の前半で Stage 1、後半で Stage 2）を採らないのは、**Stage 2 の学習データが半分に減る**ため。`D-003` が全レース学習を選んだのはデータ量の確保が理由であり、それを半減させると前提が崩れる。

**影響**: `014-training-pipeline.md` がクロスフィッティングの分割を提供する。Stage 1 の学習回数が fold あたり `K + 1` 回になる。`K` の既定値は `014-training-pipeline.md` が定める。`D-054`（集計統計量の推定期間も as-of で切る）が Stage 1 を対象に含めているのと整合し、**inner ブロックの分割も時系列順で行う**（ランダム分割にしない）。

## D-087 Stage 1 の目的変数は「1ハロンあたりに揃えた前後半バランス」の単変量とする

**状態**: Accepted（`Q-007` を解決する）

**決定**: Stage 1（`006-stage1-pace.md`）の目的変数を、次式の単変量とする。

```
N = そのレースの laps の本数
上がり3F平均 = (lap[N-2] + lap[N-1] + lap[N]) / 3
前半平均     = (Σ lap[1..N-3]) / (N - 3)

F-102 = 上がり3F平均 − 前半平均        # 単位: 秒/ハロン
```

**符号は「大きいほどハイペース」とする。** 前半が速く（小さく）上がりが遅い（大きい）ほど値が大きくなる。

**生値のまま出す。** 距離帯やコースでの標準化を行わない。

**根拠**: `Q-007` は「基準タイムからの偏差にするのが素直だが、基準タイムの算出自体が `F-301`（馬場差推定）に依存する循環がある」と論点を挙げていた。`F-301` は `Q-025` で、同じ「基準タイム」を使う `F-502` は `Q-031` でそれぞれブロックされており、**基準タイムに依存する目的変数を選ぶと Stage 1 が `P-3` で着手できなくなる。**

前後半の**差分**にすると、馬場・コースが両方の項に同じ向きに効くため大部分が相殺され、基準タイムを介さずに済む。循環が切れる。

1ハロンあたりに揃えるのは、**端数距離のレースが予測対象に実在する**ため。有馬記念は2500mでラップの先頭が端数になり、「先頭3本」が600m未満になる。両辺を「1ハロンあたりの秒数」にすればラップ本数が何本でも定義が一意に決まる。末尾3本（上がり3F）はどの距離でも600mなので基準側が安定する。

符号を「大きいほどハイペース」にするのは、`F-104 = F-102 × F-103_z` の解釈を保つため。`domain-knowledge.md` は `F-103` の `β > 0` を「ハイペース得意」と定めており、この向きに揃えると「ハイペース想定 × ハイペース得意 → `F-104` が大きい（有利）」が成り立つ。**逆向き（前半 − 上がり）でも木モデルは学習できるが、交互作用項の符号の意味が反転して読めなくなる。**

生値のまま出すのは、距離とコースが Stage 1 の入力特徴量であり、モデルが条件付けて学習できるため。標準化すると母集団を as-of で切り直す必要が生じ（`R-019`）、`F-902` と同じ対象行ごとの再計算が入って実装が重くなる。

多変量（前半3F・上がり3F・バランスの同時予測）を採らないのは、`F-104` が要求するのがスカラーであり、絶対タイム側は馬場・コース依存が残って結局使いどころが無いため。**必要になれば出力を足せる**（`006-stage1-pace.md` のインターフェースは追加を妨げない）。

**影響**: `Q-007` を `Resolved → D-087` とする。`006-stage1-pace.md` の目的変数と `F-102` の定義を規定する。**`Q-025` / `Q-031` の解決を待たずに `P-3` に着手できる。**

### 追記（2026-08-19）: 端数距離を実測し、前半の除数を修正した

`Q-035` として残していた「端数距離のラップ本数と1本目の長さ」を、キャッシュ済みHTML **12,678レースページ**（21種類の距離）で確認した。

| 確認事項 | 結果 |
|---|---|
| ラップの本数 | **`ceil(距離/200)`**。21種類の距離すべてで一致 |
| 端数の位置 | **先頭**。1本目が短い |
| 末尾3本 | **常に600m**（本決定の前提は成立する） |

端数が先頭にあることは算術的にも確定した。1本目を200mと仮定すると27〜30 m/s（時速100km前後）になり成立しない。

| 距離 | 本数 | 1本目 | 端数 | 1本目の速度 |
|---|---|---|---|---|
| 1150m | 6 | 9.6秒 | 150m | 15.6 m/s |
| 1700m | 9 | 7.0秒 | 100m | 14.3 m/s |
| 2500m（有馬記念） | 13 | 7.4秒 | 100m | 13.5 m/s |

**前提は成立したが、当初の式には端数距離で系統的な偏りがあった。** 前半平均を `Σ lap[1..N-3] / (N-3)` としていたが、これは短い1本目を200m区間と同じ重みで数えてしまう。2500mなら前半は `100 + 9×200 = 1900m` を10区間で割ることになり、**前半平均が約5%（およそ0.6秒）低く出て、`F-102` が実際より約0.6秒ハイペース側に振れる。** 距離は Stage 1 の入力なのでモデルは条件付けられるが、`F-102` は Stage 2 で**レースをまたいで**比較される（`F-104 = F-102 × F-103_z`）ため、2400mと2500mの間に見かけ上の差が残る。

**除数を実距離ベースに直す。** 本決定の主旨（1ハロンあたりに揃える）はそのままで、その主旨を端数距離でも満たす形にする。

```
N        = laps の本数（= ceil(距離/200)）
上がり3F = lap[N-2] + lap[N-1] + lap[N]           # 常に600m
前半合計 = Σ lap[1..N-3]
前半距離 = 距離 − 600

F-102 = 上がり3F/3 − 前半合計/(前半距離/200)      # 両辺とも「200mあたりの秒数」
```

距離が200mの倍数のときは `前半距離/200 = N-3` となり、当初の式と一致する。

## D-092 カテゴリ変数は低頻度を「その他」に丸めてから LightGBM のネイティブカテゴリに渡す

**丸めの対応表は fold の学習期間から作る。** 検証期間・推論時に現れる未知のカテゴリも「その他」に落とす。

**丸めの対応表を fold の学習期間から作るのは `R-019` / 原則7 による。** 全期間の出現回数で閾値を判定すると、検証期間の情報が学習側に漏れる。

**影響**: `007-stage2-ranker.md` のカテゴリ処理を規定する。`D-082` の `meta.json` に丸めの対応表（またはその生成条件）を記録する必要がある。**丸め後のカテゴリ集合が fold ごとに変わるため、`feature_names` は同じでもカテゴリの意味が fold 間で異なる。** モデルを fold をまたいで流用しない。

## D-097 確率校正は温度スケーリング `softmax(score / T)` とする

**状態**: Accepted

**決定**: `015-calibration.md` の校正手法を温度スケーリングとする。Stage 2 のスコアを温度 `T` で割ってからレース内 softmax を取る。

```
p_i = exp(score_i / T) / Σ_{j ∈ race} exp(score_j / T)
```

`T` は LogLoss を最小化する1次元最適化で求める。`T > 0` を制約とし、探索範囲は `[0.1, 10.0]` に限る。

**根拠**: 推定するパラメータが1つだけなので、**G1が年24競走しかない標本量でも安定して推定できる**。fold あたりの校正データは10年分でも約192レース（3年分なら72レース）にとどまる。

温度スケーリングは単調変換なので**レース内の順位が変わらない**。`007-stage2-ranker.md` が `lambdarank` で学習した順位性能を壊さずに確率の尺度だけを直せる。

softmax の形を保つため、**`R-002`（レース内の合計が `1.0 ± 1e-6`）が自動的に満たされる**。isotonic regression や Platt scaling は確率を個別に変換するため合計が `1.0` を外れ、再正規化が必要になる。再正規化は校正の効果を部分的に打ち消す。

isotonic regression はノンパラメトリックで表現力が高いが、**36〜192レースでは階段関数が粗くなりすぎる**。

`Q-036`（`lambdarank` のスコアを素の softmax にかけたときの尺度が未検証）が指摘する飽和・均一化は、まさに温度が直す対象である。`D-095` が Stage 2 で温度を退けたのは責務分離のためであり、本決定がそれを引き取る。

**探索範囲を `[0.1, 10.0]` に限るのは、最適化が発散したときに気づけるようにするため。** 境界に張り付いた場合は校正が成立していない兆候として扱う。

**影響**: `015-calibration.md` の手法を規定する。`T` は単一の浮動小数点数なので `D-082` の `meta.json` にそのまま記録できる。**頭数が4〜18と幅があるなかで単一の `T` が妥当かは未検証（`Q-037`）。**

## D-100 orchestration層（`predict_fold`）はクロスフィット用サブモデルに inner 検証を使わず、校正は `run_walk_forward()` の外で適用する

## D-102 `F-103` の `β`（OLS の傾き）に分散の下限ガードを追加する

**状態**: Accepted

**決定**: `src/umagic/features/f103.py` の `_ols_slope()` に `MIN_VAR_X = 1e-6` の下限ガードを追加する。`p_i` の分散 `var_x` がこの値未満なら `beta = cov_xy / var_x` を計算せず `None` を返す（既存の `var_x == 0` チェックを拡張したもの）。

**根拠**: `Q-038`（同一入力・同一コードで `run_p3_completion_check()` を2回実行した結果が一致しない、`R-021` 違反の疑い）の原因調査で判明した。

`p_i`（`F-103` の説明変数、他馬の `F-101` 平均の反転）は `_PACE_PAIRS_SQL` の `AVG()` 集計（DuckDB、既定8スレッドの並列実行）を経由しており、実行のたびに最終桁レベルの浮動小数点誤差（`~1e-14` 程度、通常は無害）が乗る。この誤差自体は問題にならないはずだったが、`beta = cov_xy / var_x` は `var_x` で割る**悪条件の計算**であり、対象馬の過去走間で `p_i` のばらつきが極小（同じようなペースのレースばかり走っている馬）だと、この誤差が `beta` に大きく増幅される。

増幅された誤差は個々の馬の `beta` だけの問題では終わらない。`beta` は日付ごとに集約され、**全馬共通の `mu_global`（累積平均）** の一部になる（`D-054` 追記事項）。少数の不安定な `beta` が `mu_global` を通じて、shrink 後の `f103` を持つ**大多数の行**に薄く広がって伝播する。実測では、実行ごとの `f103` の差の最大値が `1.21e-7`（浮動小数点として明らかに異常な大きさ）、影響を受けた行が全体の約60%（144,561行中87,343行）に達していた。

**`var_x` の分布を実データ（310,504件）で確認したうえで閾値を決めた。** 中央値は `0.066`、`var_x < 1e-6` は全体の約0.13%（405件）のみで、大多数の `beta` 推定には影響しない。この閾値適用後、同じ2回実行の差分は `f103` の最大差 `1.21e-7` → `3.15e-11`（約3800分の1）に縮小し、他の列（`f501` 等、`~1e-16`）と同程度のオーダーに収まった。

**この修正だけでは完全なビット完全一致にはならない。** 残る `~1e-11` 程度の差は、DuckDB の並列集計に起因する通常の浮動小数点丸め誤差であり、完全に除去するには DB 接続をシングルスレッド化する必要がある（`SET threads=1`）。これは全クエリを対象にすると特徴量組み立て全体（fold あたり約350秒）を大きく遅くする可能性があり、**費用対効果が見合わないため見送る。** `R-021`（同一入力から同一出力）は「LightGBM の学習自体（`deterministic=True`/`num_threads=1`）」と「通常の浮動小数点丸め誤差（`~1e-11`〜`~1e-16`）を除く入力特徴量」の範囲で満たすものとして扱う。この程度の摂動が LightGBM のヒストグラムベースの分割点探索の結果を変えることは実務上想定しない。

## D-104 `F-301` は交互反復で推定し、縮約強度は分散成分から決める

**状態**: Accepted（`Q-025` を解決する）

**決定**: `F-301`（馬場差推定）の混合効果モデルを、**レース効果と馬効果を交互に更新する自前の反復推定**で実装する。各更新の縮約強度は、その反復時点の分散成分から `k = σ²_誤差 / σ²_効果` として決める。`statsmodels` の `MixedLM` も `PyMC` も使わない。

**根拠**: `Q-025` は3方式を候補に挙げていたが、規模を実データで確定させた結果2つが脱落した。対象は10年分で464,765出走行・レース33,236水準・馬53,712水準の**交差ランダム効果**である。

`MixedLM` は交差ランダム効果を大規模に扱う設計になっておらず、この水準数では実質的に動かない。`PyMC` は原則7（`D-054`）により fold ごとの再推定が要り、さらに `D-086` のクロスフィッティングを掛けると最低35回のMCMCを回すことになる。`D-027` はバックテストの実行時間に上限を設けないが、`P-3` の walk-forward が既に約101分かかっている現状で、その上に載せられる計算量ではない。

交互反復を選べる決め手は `D-051` にある。`D-051` は「差が出るのは不確実性の定量化であって、点推定を特徴量として渡す用途では効かない」として階層ベイズを外している。`F-301` の出力も `F-302` という特徴量の点推定であり、同じ論理が当てはまる。

縮約強度を分散成分から決めるのは、混合効果モデルにおける最適な収縮量がまさにその比だからである。`D-051` が `F-902` の `k` を設定値としたのは、あちらが単純な平均への縮約で分散成分を分離できないため。`F-301` は誤差と効果の分散を反復の中で分離できるので、推定できるものを設定値にする理由がない。**ハイパーパラメータを2つ増やさずに済む**ことは、`D-103` が探索の優先度を下げた方針とも整合する。

**影響**: `Q-025` は Resolved。`013-track-variant.md` が書ける。`P-1` の完了時点から `NaN` のままだった `F-302` が埋まる見込みになる。反復の収束条件と上限回数は `013` に書く。

## D-105 `F-301` の目的変数は `(surface, distance)` ごとに標準化し、距離・クラスの固定効果を残す

**状態**: Accepted

**決定**: `F-301` の目的変数を、`time_sec` を `(surface, distance)` ごとのレース内偏差の標準偏差で割った値とする。距離・馬場・クラスの固定効果は式に残す（`domain-knowledge.md` の `F-301` の式どおり）。標準偏差の推定期間も as-of で切る（`D-054` 原則7）。

**根拠**: 標準化しないと、条件によって馬効果の尺度が最大2.7倍ずれる。実データ（2015-2024）でレース内偏差の標準偏差を条件別に測ると、芝1200mが0.809秒に対しダート2400mが2.216秒だった。レース効果がレース内の平均を吸収するため残るのは偏差であり、その偏差の尺度が条件ごとに違えば、**長距離ダートを使った馬の効果だけが大きく出る**。`F-302` は条件をまたいで馬の能力を比較するための特徴量なので、この歪みは目的に反する。

速度（m/s）への変換では平均の差は消えるが分散の差は残り、今度は短距離馬の効果が大きく出る向きに偏る。馬場差を「秒」で読める利点は生の秒のままにしないと得られないが、`D-107` により `F-302` として使うのは馬効果であってレース効果ではないため、その利点は本件では効かない。

固定効果を残すのは、縮約の収縮先を「全体平均」ではなく「その条件の標準的な水準」にするため。レース効果は原理的にはレース単位の共変量を吸収するが、縮約が入ると完全には吸収しない。固定効果が無いと、出走頭数の少ないレースの効果が0へ強く引っ張られ、その分が馬効果に漏れる。

**影響**: `013-track-variant.md` の目的変数の定義がこれに従う。馬効果の単位は「秒」ではなく標準偏差になる。`F-302` を人が読むときはこの単位に注意すること。

## D-108 `F-301` の交互反復は、実データ規模で収束フラグが立たないまま `DEFAULT_MAX_ITER=100` を既定にする

**状態**: Accepted

**決定**: `fit_track_variant()` の `converged` フラグは、実データ規模（1フォールドの学習期間、143,656〜419,328行）では `max_iter=100`（既定）はもとより `max_iter=5000` でも `True` にならない。それでも `DEFAULT_MAX_ITER=100` を既定値として採用する。**収束の判定基準は相対誤差**（現在の効果の最大絶対値でスケールした変化量が `tol` を下回るか）にする。

**根拠**: `013-track-variant.md` のテスト観点15は「実データ1ブロックで `converged=True` かつ `n_iter<max_iter`」を求めているが、実測ではこれを満たせない。原因を反復回数を振って確認したところ、`delta`（1反復あたりの変化量）は最初の50反復で `79.3 → 6.1e-4` まで急減したあと、以降は極めて遅い線形収束（1反復あたり約0.04%）に移る。ブロック座標降下（交差ランダム効果 → 固定効果 → 交差ランダム効果 …）は、ブロック間の結合が強い（1レースあたりの平均出走頭数が少なく、多くのレースが2〜3頭しか馬効果の手がかりを持たない）と収束率が1に近づき、理論上は正しくても実務的な反復回数では「厳密収束」に届かない性質がある。

**実害が無いことを実測で確認した。** `max_iter=100` と `max_iter=5000`（19.8秒）の `horse_effects` を比較すると、差の最大値は `2.5e-4`、平均は `7.9e-5`。効果の標準偏差は `0.99` であり、相対誤差は0.03%程度に収まる。`D-102` が `F-103` の `~1e-11` の丸め誤差を「実務上問題にならない摂動」として扱ったのと同種の判断として、**この残差は特徴量として使う分には無視できる**。

**相対誤差基準に変更した理由**: 当初は絶対誤差 `delta < tol`（`tol=1e-6`）だった。実データでは効果の尺度が標準化後でも数十単位に達する（後述の外れ値の影響）ため、絶対 `tol=1e-6` は要求として非現実的に厳しい。効果の最大絶対値でスケールした相対誤差に変えることで、小規模な合成テスト（尺度〜1、`tests/test_track_variant.py` の18件）では従来どおり厳密に収束を検出し、実データ（尺度〜10〜30）では判定の意味が保たれる。ただしこの変更後も実データでは前述のとおり収束フラグは立たない（残る `delta` が相対 `tol` を割るまでに数千反復を要するため）。

**外れ値による効果の尺度膨張を実測で確認した。** 2015-2017年の学習データで最大の馬効果は `+34.38`（`horse_id=29935`）。原因を追うと、この馬は該当期間に1走しかしておらず、その1走が芝1600mを`149.5秒`で走破していた（通常は95〜100秒程度）。標本が1件しかない馬が極端な値を1つ引くと、縮約（`k_horse`）はそれを大きく弾けない。これは実装の不具合ではなく、分散に基づく縮約が外れ値に頑健ではないという、混合効果モデル一般の性質である。**ロバスト化（外れ値の影響を抑える）は今回のスコープに含めない。** LightGBM は木ベースであり、極端な特徴量値1つが訓練を不安定化させる可能性は線形モデルより低いため、実害は `Q-041`/`Q-042` 同様に `R-023` の実測を見てから判断する。

**性能への影響は小さい。** `max_iter=100` での実行時間は、3年分（143,656行）で1.2秒、9年分（419,328行）で3.6秒。fold あたり5回（`D-106`）× 7 fold でも、`P-3` の総所要時間（約101分）に対して数分の追加に収まる見込み。

**影響**: `013-track-variant.md` のテスト観点15は、実データでの厳密な `converged=True` を求める記述のままにはできない。仕様書側に「実データでは相対収束の意味で十分小さい変化に達するが、`converged` フラグ自体は `True` にならないことがある」という注記を追加する必要がある（本 `D-108` を参照するに留め、根拠の複製はしない）。`DEFAULT_MAX_ITER` を増やしてフラグを `True` にする追加のチューニングは行わない（費用対効果が見合わない、`D-102` と同じ判断）。

## D-116 `F-103` の `β` は少標本で発散する。原因は `MIN_VAR_X` の桁と縮約式の設計にあり、既定は据え置いて候補を `Q-044` に登録する

**状態**: Accepted

**決定**: `Q-044`（`F-103` の縮約が `F-302` と同型の未ロバスト化問題を抱えているか）を実データで診断し、**同型であることを確認した**。機構も特定できたが、`src/umagic/features/f103.py` の既定（`MIN_VAR_X=1e-6`・`DEFAULT_K=5.0`・`mu_global`の単純累積平均）は**このセッションでは変更しない**。対処候補を `Q-044` に登録し、`D-101` の規律（G1 OOF で選び、`R-023` の判定指標そのもので確認する）を経てから採否を決める。

`D-102` が `MIN_VAR_X` を導入したのは**数値的**不安定性（DuckDB の並列 `AVG()` が生む `~1e-14` の浮動小数点誤差の増幅）を防ぐためで、その目的には `1e-6` で足りている。しかし**統計的**な不安定性はそれより3〜4桁早く始まる。閾値を上げたときの効果は非常に安い:

|---|---|---|---|---|

**(3) 縮約（`F-902`、`k=5`）はこの外れ値に対して無力である。** `shrink()` は `θ = (n·β + k·μ)/(n+k)`。`n=2`・`k=5` では `β` の 2/7（29%）がそのまま残るため、生の std 50.069 は縮約後も 14.859（**3.37倍しか縮まない**）で、範囲は `[-1501.71, +1653.34]` のまま。**縮約は「安定した尺度のまわりの標本誤差」を想定した式であり、値そのものが無制限な場合には効かない**——`D-114` が `F-302` について到達したのと同じ結論。

**最も重要な発見: `drop`（`F-103`/`F-104` を丸ごと落とす）も base と区別がつかない**（−0.0046 / −0.0366 / +0.0044）。`D-116` は `F-103` の `β` が少標本で発散し統計的に壊れていることを実証したが、**その壊れた特徴量を除去しても測定可能な変化が起きない。** `D-115` が示した「`f103_z`/`f104` は label とほぼ無相関」と整合する——`F-103` は有害なのではなく**不活性**である。LightGBM は `cat_smooth`/`cat_l2`（`D-113`）を含む現在の設定下で、この列を実質的に無視できている。

**影響**: `f103.py` は無変更（`D-117` のベクトル化のみ適用済み）。`Q-044` を「実装は壊れているが実害・改善余地ともに測定限界以下」として決着させ、優先度を下げる。`D-116` が指摘した `Q-042` との共通課題（精度重み付き縮約への設計変更）は、`F-103` 単体では投資を正当化できないことが分かった——**`F-301`/`F-302` 側（`Q-042`）で効果が実証されて初めて `F-103` にも展開する順序にする。** `R-023` の本丸（`D-103`: モデルが市場に上乗せ情報を持たない）は依然として未着手のまま残る。

## D-119 現在の特徴量には市場に対する上乗せ情報が実質的に存在しない。`R-023` は現データでは達成できない

**状態**: Accepted

**決定**: `D-103` が残した本丸（モデルが市場に上乗せ情報を持たない）の原因を、「データ問題（特徴量に情報が無い）」と「モデリング問題（情報はあるが取り出せていない）」に切り分けた。**データ問題であると確定した。** `R-023`（G1でLogLossが市場確率を下回る）は、**現在の特徴量セットのままでは、モデルの改良によっては達成できない。**

**この構成は `D-002`（対象レースのオッズを特徴量にしない）に違反しており、出荷できない。上限を測る診断としてのみ用いた。得られた数値を `R-023` の達成として報告してはならない。**

**検算**: `rounds=0` が3 fold とも市場と完全一致（差 `+0.0000`）した。オフセットの足し戻しと `softmax(log p) = p`（実測の再現誤差 `1.7e-16`）が正しいことを確認している。

**結果1: 市場を渡しても超えられない**（市場からの差、負が市場超え）:

| rounds | fold 0 G1 / all | fold 1 G1 / all | fold 2 G1 / all |

| 0 | +0.0000 / +0.0000 | +0.0000 / +0.0000 | +0.0000 / +0.0000 |

**`all` で得られる上乗せは最大 `0.0002`〜`0.0010`、5ラウンドで消える。G1 では一度も市場を下回らない。** 以降は単調に劣化する。`R-023` が埋めるべきG1のギャップは `0.4173`（モデル 2.3085・市場 1.8912）であり、**測定された上限はその 0.1% 以下**である。

**結果2: 目的関数の不一致は犯人ではない**。`lambdarank` は NDCG（順位）を最適化するため、「順位は改善しているのに LogLoss だけ悪化している」なら条件付きlogit / Plackett-Luce top-1 に替えれば信号を取り出せる可能性が残っていた。同じ軌跡で順位指標を測ったところ、**top-1的中率・NDCG@3 も LogLoss と同じ形で劣化した**。

| 2 | 0.3224 → 0.3240（r=5） → 0.3128 | 0.5292 → 0.5297（r=10） → 0.5188 |

**この結果は今セッションの経過をすべて説明する。** `F-302`（`D-110`）が悪化させ、`F-103`（`D-118`）が不活性で、`Q-039` の正則化（`D-113`、−0.0270）だけが効いた——いずれも**市場が既に織り込んでいる同じ公開情報を再処理していた**からである。特徴量の作り方を変えても、縮約を頑健にしても、目的関数を替えても、この壁は動かない。

**残る可能性（本診断が否定していないもの）**:

1. **走破時計に基づく能力指標**。本診断は `f302` 列を落とした**現行の本番構成**を測っている（`D-110` により既定で無効なため）。`D-103` の診断5が「能力の絶対値に相当する特徴量が1本も無い」と指摘した穴は依然として埋まっていない。`F-301`/`F-302` は**推定方法の実装が破綻した**（`D-108`/`D-114`）のであって、**速度指数という概念自体は公正に試されていない**

3. 本診断は LightGBM の表現力の範囲での測定である。ただし順位指標も改善しない以上、モデル族の問題である可能性は低い

**影響**:

- **`P-4` のブロックは維持される**（`D-103` の判断を、より強い根拠で追認した）
- `R-023` の達成可能性そのものを見直す必要がある。`D-015` は `R-023` の A判定を `P-3` の完了条件としているが、**現データでは満たせないことが実測で示された**。要件を維持するなら新データ源の追加が前提になる

## D-120 粗い速度指数は「よく効くが市場に織り込み済み」。`D-103` 診断5の穴は閉じた

**状態**: Accepted

**決定**: `D-119` が唯一否定していなかった筋——走破時計に基づく能力指標——を、**わざと粗いが頑健な速度指数**で先に検証した（`D-119` の次の一手 `1'`）。**市場への上乗せ情報は無い。** `F-301` の全面再設計には進まない。`D-103` の診断5（能力の絶対値に相当する特徴量が1本も無い）が残した穴は、これで閉じたものとする。

**なぜ粗い版で先に測ったか**: `F-301`/`F-302` は混合効果モデルの推定が2度破綻している（`D-108` の外れ値耐性、`D-114` の relativize 後も残る有害性）。全面再設計は数日規模の投資になるため、**縮約も混合効果も使わない中央値ベースの粗い版**で上限を先に測る方が費用対効果が高い。中央値ベースなら `D-108` の外れ値問題が構造的に起きない。

**構築方法**（`data/diag20_crude_speed_figure.py`。すべて as-of、`D-054` 原則7を満たす）:

```
base(surface, distance, class_key, month)  その月より前の time_sec の平均・標準偏差
resid = time_sec − base
tv(date, course, surface)                  その日その場その馬場の resid の中央値
spd = −(resid − tv) / base_sd              正が速い
```

`class_key` は `COALESCE(grade, race_class, 'その他')`。`race_class` は `G1`〜`G3`・`L` を `'オープン'` に丸めるため（`D-111`）`grade` を優先する。基準は**月単位**にした——年単位だと2015年が丸ごと落ち、さらに**2019年のJRAクラス名称変更**（`1勝クラス` 等の新設で前年に同名の履歴が無い）でカバー率が70.5%に落ちるため。月単位＋`(surface, distance)` のみのフォールバックで、カバー率は2015年88.8%・他は約100%になった。

馬ごとの特徴量は過去走（`race_date < target_date`）の集約5列（`fspd_best`/`fspd_mean`/`fspd_last`/`fspd_recent3`/`fspd_n`）。大差負けが平均を壊すため `±5` でクリップしてから集約する。

**結果1: 速度指数は本物の予測力を持つ**（fold 0 全行、`label` との Spearman）:

| （参考）`last3f_recent_z` | −0.1287 | — |
| （参考）`f103_z`（不活性、`D-118`） | −0.0042 | — |

**`fspd_recent3` は本プロジェクトで2番目に強い特徴量である**（`last3f_recent_z` の1.8倍、`f103_z` の55倍）。集約は壊れておらず、測定は公正だった。

**結果2: しかし市場への上乗せは無い**（`data/diag21_speed_ceiling.py`。市場を `init_score` に置き差分だけを学習。`rounds=0` が3 fold とも `+0.0000` で検算済み）:

**検出力のある `all` 母集団（約1万レース）では、`spd_only` は3 fold とも市場を実質的に上回らない**（最良 −0.0001）。G1側の −0.0017 / −0.0109 は 68〜119レースの母集団で信頼区間が ±0.05〜0.10 あり、`*超` の判定が付いた箇所は G1 に一つも無い。fold 1 に至っては改善が全く出ていない。

## D-122 `D-015` の成功定義を改訂する。A判定を「情報捕捉率」に置き換え、`R-023`/`R-024` は未達確定として維持する

**状態**: Accepted（`D-015` の A判定を改訂する。2段階の構造と B判定の枠組みは維持）

**決定**:

1. **`R-023`（A判定）・`R-024`（B判定）は削除せず、「現在取得しているデータでは達成不可能」という判定結果を注記して維持する。** IDを再利用しない規約と整合させ、なぜ諦めたかの根拠（`D-119`/`D-120`/`D-121`）を要件の横に残す。
2. **新しいA判定として `R-029`（情報捕捉率）を設ける。** G1で `0.75` 以上を合格とする。
3. **`P-4` の着手条件を `R-030` として明文化する。** 「市場への上乗せが正で有意」であること。`D-103` が示唆していた読み替えを要件に昇格させる。

**情報捕捉率の定義**:

```
情報捕捉率 = (LL_uniform − LL_model) / (LL_uniform − LL_market)

LL_X = レース単位の平均負対数尤度 = (1/R) Σ_r [ −Σ_i y_ri · log p_X(r,i) ]
  y_ri           1着なら 1/(1着同着頭数)、それ以外 0（`D-074`）
  p_uniform(r,i) 1 / n_starters(r)
  p_market(r,i)  normalize(1 / odds_win)（出走取消・競走除外を除く、`D-073`）
  p_model(r,i)   校正後のモデル確率（G1は `D-097`/`D-098` の温度スケーリング適用後）
```

`1.0` が市場と同等、`> 1.0` が `R-023` の達成に相当する。

**なぜこの形か**: 生の LogLoss 差（例「市場の +0.2 以内」）は頭数分布が変わると同じ閾値の意味が変わる。相対劣後率（「市場の X% 以内」）は一様分布という下限を見ないため進捗が過小評価される。**情報捕捉率は尺度が無く、G1（一様 2.8018）と `all`（一様 2.6037）を直接比較できる。**

**現状値**（`data/p3_walk_forward_raw_v9.parquet` = `D-113` 確定後の現行既定）:

| 母集団 | 一様 | モデル | 市場 | 情報捕捉率 |
|---|---|---|---|---|
| G1（135レース） | 2.8018 | 2.3040 | 1.8912 | **0.5468** |
| all（23,224レース） | 2.6037 | 2.1853 | 1.9365 | 0.6271 |

**閾値を `0.75` にした理由**: 現状 `0.5468` に対し `+0.20`。`D-119` により上限は `1.0`（特徴量 ⊆ 市場の情報のため市場は超えられない）であり、`0.85` は上限に近すぎて再び達成不可能な要件を立てる危険がある。`0.65` は `all` が既に `0.6271` に達しており目標として弱い。`0.75`（市場の情報の3/4を再現する）は、`F-304`（`D-123`）の投入で届く可能性がある水準として選んだ。

**`D-015` の「Aのみの達成も成果」は維持する。** 本改訂により、A判定は「市場を超える」ではなく「モデルとして市場に匹敵する水準に達する」という意味に変わる。**`D-015` が想定していた「オッズに乗っていない情報を掴んでいる」という含意は失われる**——`D-119` がそれを不可能と実証したため。この含意の喪失を隠さずに記録する。

**影響**: `R-023`/`R-024` に判定結果を注記し、`R-029`/`R-030` を新設した。`D-015` の A判定行は `R-029` に置き換わる（`D-015` 自体は Superseded にしない。2段階の構造とB判定は生きている）。`010-backtest.md` のレポートは情報捕捉率を出力に含める必要がある。

## D-123 中央値ベースの速度指数を `F-304` として本番に採用する

**決定**: `D-120` で構築・検証した中央値ベースの速度指数を `F-304` として `domain-knowledge.md` に登録し、Stage 2 の特徴量に組み込む。`F-301`/`F-302`（混合効果モデルによるルート）は既定無効のまま（`D-110`）据え置き、**別立ての特徴量**として扱う。

## D-124 プロジェクトの目的を「新データへの土台」に定め、`D-002` の根拠を取り直す

**状態**: Accepted（`D-002` の根拠を差し替える。`D-002` の決定内容は維持）

**決定**:

1. **本プロジェクトの当面の目的を「市場が持っていない情報を将来投入するための土台を整えること」に置く。** 市場確率に近づくこと（`R-029`）はその手段であり、到達点ではない。
2. **`R-029` は新A判定として維持するが、プロジェクトの完成条件にしない。** 達成しても「土台が整った」以上の意味を持たない。
3. **`D-002`（対象レースのオッズを特徴量にしない）を維持し、根拠を差し替える。**
4. **`Q-002`（JRDBの契約形態・価格・遡及範囲）を本命の調査対象に格上げする。**

**なぜ目的の再定義が要るか**: `D-119`〜`D-121` により、`R-029` の上限は「市場と同等」であることが確定した。**情報捕捉率 0.75 のモデルは、オッズ板を見れば無料で・即座に・より正確に得られるものの劣化再現でしかない。** 馬券にも意思決定支援にも、オッズを直接読む以上の使い道がない。したがって `R-029` の達成自体を成果として掲げることはできない。

意味を持つのは、**市場が織り込んでいない情報を入手できたときに、それを載せる場所として素性の良い基礎モデルが要る**という一点である。`domain-knowledge.md` の `F-4xx`（調教）は `D-005` が既に「Phase 4以降でJRDBを追加購入」と計画しており、`Q-002` がその未決事項として残っている。**`D-120` の一般則が言う「市場が誤って重み付けしているもの」の候補として、定性情報（追い切りの本数・併せ馬の格・厩舎コメント）の織り込みの粗さは検証に値する。** ただし調教タイムそのものは市場も見ており、当たる保証はない。

**`D-002` の新しい根拠**: 元の根拠は「オッズを入れると精度は上がるが、**市場を超える余地が消える**ため」だった。`D-119` はその余地が最初から存在しないことを実証しており、**この根拠は失効している。** 維持する理由を次に置き換える。

> **将来新しい情報を投入したときに、その情報が市場に対して上乗せを持つかを測れる状態を保つため。** オッズを特徴量に入れると、モデル出力と市場が交絡し、`R-030`（`w_model > 0`）の測定が原理的に成立しなくなる。`D-119`/`D-120`/`D-121` の診断はすべて「市場とモデルが独立に構成されている」ことに依存しており、この性質を壊すと**同じ診断を二度と実行できない。**

**`R-029` を即座に達成できてしまう問題を明示する。** `R-029`（情報捕捉率 0.75）は、単勝オッズを特徴量に入れれば `1.0` に到達する。それを禁じているのは `D-002` だけである。**したがって `R-029` は「`D-002` の制約下での」達成度を測る指標であり、この前提を外した数値には意味がない。** 報告時にこの条件を省略しない。

**影響**: `Q-002` の優先度を上げ、`docs/tasks.md` に調査タスクを追加した。`R-029`/`R-030` の判定方法は変更しない。`F-304` の実装（`D-123`）は土台整備として予定どおり進める。`D-015` の「Aのみの達成も成果」は、本決定により「土台としての成果」と読み替える。
