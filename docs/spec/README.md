## 位置づけ

| ドキュメント | 書くこと | 書かないこと |
|---|---|---|
| `decisions.md` | なぜそうするか | 実装の詳細 |
| `domain-knowledge.md` | 何を根拠にするか | 実装の詳細 |
| **`spec/`** | **何をどう作るか** | **判断の根拠**（`D-xxx` を参照するに留める） |

仕様書に根拠を書き込まないこと。根拠は `decisions.md` に `D-xxx` として置き、仕様書からは参照する。
こうしておくと、仕様が変わっても根拠が失われず、根拠が変わったときに影響範囲を追える。

## ファイル命名

```
docs/spec/NNN-<名前>.md
```

`NNN` は3桁の連番。**取得順に振るだけで、順序や依存関係は表さない**（`D-013`）。Phase は表の列で示す。

想定される仕様書（現時点の見込み。確定ではない）。下表はPhase順に並べてあり、番号順ではない。

**この一覧は「全部書く約束」ではない。着手するPhaseの分だけ書く。** 前提が崩れたときに大半が無駄になる。`P-0`（データ基盤）・`P-1`（特徴量パイプライン + リーク検査）・`P-2`（ベースライン）は完了済みで、現在は `P-3`（Stage 1 + Stage 2 + walk-forward）の仕様を固めている。

## テンプレート

```markdown
# NNN <タイトル>

| | |
|---|---|
| Phase | P-x |
| 関連決定 | D-xxx, D-xxx |
| 関連特徴量 | F-xxx, F-xxx |
| 状態 | Draft / Fixed / Implemented |

## 目的

このモジュールが何を担うか。1〜3文。

## 入出力

入力と出力の型・形式を明記する。

## 仕様

実装すべき内容。曖昧さが残らない粒度で書く。

## 制約

守るべき条件（リーク防止、性能要件など）。

## テスト観点

何を検証すれば「できた」と言えるか。

## 未決事項

この仕様書の範囲で未確定のもの。`Q-xxx` として `open-questions.md` にも登録する。
```
