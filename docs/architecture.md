## 1. 前提条件の確認

設計判断の背景にある、動かせない制約。

### 1.1 データ量

JRA平地G1は年24競走前後。1レース平均16頭として、**20年遡っても約480レース / 約7,700出走行**しかない。
JRA全体なら年間約3,450競走・約4.5万出走、20年で約90万行。差は100倍以上。

→ `D-003`（全レース学習 → G1特化）の根拠。

### 1.2 控除率という固定コスト

| 券種 | 払戻率 |
|---|---|
| 単勝・複勝 | 80.0% |
| 枠連・馬連・ワイド | 77.5% |
| 馬単・3連複 | 75.0% |
| 3連単 | 72.5% |

何もしなければ回収率は払戻率に収束する。回収率100%を目指すなら「当てる」のではなく**市場より正確である**必要がある。

### 1.3 G1は最も市場が効率的なレース群

情報量・投票数ともに最大で、オッズが最も「正しい」場。収支面では未勝利・条件戦のほうが歪みは大きい。
`D-001` はこれを承知のうえでの選択。

## 2. 越えるべき基準線

`D-002` の両建て方針により、目標が明確に定義できる。**市場確率に勝つこと。**

```python
市場確率 = normalize(1 / 単勝オッズ)   # 控除率20%を除いた確率
```

これが最強のベースラインである。
ファンダメンタルモデル（オッズ非使用）のLogLossがこれを下回れば、オッズに乗っていない情報を掴んでいることになり、その乖離がそのまま期待値になる。

**逆にここを超えられなければ、券種を工夫しても回収率は改善しない。**

`P-2` でこのベースラインを先に実装することが、以降すべての評価の前提になる。

## 3. 中間スキーマ（ソース非依存）

`D-009` に基づく。データ取得元が変わってもこの形は変えない。

```
races    race_id, date, course, race_number, post_time,
         distance, surface, direction, grade,
         track_condition, weather, weather_forecast,
         n_entries, n_starters, prize

runners  race_id, horse_id, frame, number, jockey_id, trainer_id,
         weight_carried, horse_weight, weight_diff, age, sex,
         odds_win, popularity, status, finish_pos, time, last_3f, corners

horses   horse_id, name, birth, sire_id, dam_id, damsire_id

payouts  race_id, bet_type, combination, payout

odds     race_id, bet_type, combination, odds_low, odds_high, as_of

# 全テーブル共通（D-026）
         source, fetched_at
```

### 注意点

- **`payouts` を省略しないこと。** 馬連・3連複の実配当は結果表から復元できず、バックテストが成立しなくなる。
- `runners.corners` はコーナー通過順の配列。`F-101`（逃げ意欲）と `F-501`（当日の脚質バイアス）の両方が依存する。**要素数はレースによって変動する**（コーナー数が距離で変わるため）。`F-101` は1〜2角を要求するので、要素数が足りないレースは入力なしとして扱い、3角・4角で代用しない。
- ラップタイムは `races` に別テーブルとして持つ（Stage 1の目的変数になるため）。
- `race_number` / `post_time` は同日レースの前後判定に使う（`D-010`）。次項の規約に従うこと。
- `status` は出走状態（`D-011`）。`n_entries`（出馬表頭数）と `n_starters`（実出走頭数）を分けて持つ（`D-012`）。
- **`odds` を省略しないこと（`D-020`）。** `runners.odds_win` は単勝しか持たず、`payouts` は的中組の払戻しか持たない。`D-008` が主評価に選んだ複勝・ワイドの**発走前オッズ**がないと `P-4` の期待値計算が成立しない。複勝・ワイドは的中組数で配当が変わるため `odds_low` / `odds_high` の幅で保持する。単勝は全件取得可能だが、**複勝・ワイドは過去分の全頭オッズが取得できない**ことが判明している（`D-023` / `Q-018`）。
- **`weather` と `weather_forecast` を混ぜないこと（`D-029`）。** `weather` は実測（当日確定）、`weather_forecast` は予報（木曜時点で入手）。暫定予測は予報値、本命予測は実測値を使う。同じ列に入れると本命予測にリークする。**過去分の予報値は取得できない**ため、既存データの `weather_forecast` は `NULL` になる（`Q-021`）。馬場状態には対応する予報列を置いていない（事前情報の有無が未確認）。
- **`source` / `fetched_at` を全テーブルに持つ（`D-026`）。** 合流するソースが3系統（`netkeiba_jra` / `netkeiba_nar` / `jrdb`）あり、出所がないと同じ列に別ソース由来の値が混在しても区別できない。`fetched_at` はレース当日に複数回の増分取得を回す（`D-024`）ため、どの断面かを識別するのに要る。

### 同日レースの前後判定（`D-010`）

`F-501` / `F-502` は同日レースを使う唯一の例外だが、**判定を誤ると検出困難なリークになる**。以下を守る。

```sql
-- 対象レースより前に発走した同日・同競馬場のレース
WHERE date   =  target.date
  AND course =  target.course      -- 別競馬場を混ぜない
  AND race_number < target.race_number   -- <= にしない
```

- **`<=` にしない。** 対象レース自身を含めると、そのレースの結果が特徴量に入る。
- **別競馬場を混ぜない。** 馬場バイアスは競馬場ごとの現象であり、他場の結果は情報にならないうえ、発走時刻の前後が `race_number` では判定できない。
- 判定キーは `post_time` ではなく `(date, course, race_number)` を使う。同一開催内では R番号が発走順と一致し、かつ `post_time` より取得の確実性が高い。`post_time` は補助的に保持する。

### 将来の拡張（`D-005` Phase 4以降）

JRDB合流時に以下を追加する。既存テーブルは変更しない。

```
training      horse_id, date, course, times[], partner, partner_result, intensity
pre_race      race_id, horse_id, body_weight, condition_note
```

## 4. モデル構成

`D-007` の2段階アーキテクチャ。

```
Stage 1  レース質予測モデル（レース単位）
   入力: 出走馬の脚質分布(F-101), 頭数, 距離, コース, 馬場・天候(F-804)
   出力: 前半3F/5Fタイム, 後半3F, ペース指数（前後半バランス）
              ↓ 予測されたレース質 (F-102)
Stage 2  適性照合モデル（馬単位）
   入力: 馬の適性ベクトル(F-103) × Stage1出力 の交互作用(F-104)
         + F-2xx〜F-8xx の全特徴量（馬ごとに値が異なるものはF-901で相対化）
   出力: 各馬のスコア → レース内softmax → 勝率
              ↓
確率展開  Plackett-Luce → 連対率・複勝率・馬連・ワイド・3連複の確率
          ※ Harville bias の補正が要る（Q-017）
              ↓
期待値    確率 × オッズ → EV → 分数ケリーで賭け金決定
```

### 予測経路ごとの入力（`D-028`）

入力は特徴量の**確定時刻**で決まる。名指しで列挙しない。一覧は `domain-knowledge.md` 4節。

| 経路 | 使える特徴量 |
|---|---|
| 暫定予測（木曜） | 確定時刻が `木曜` 以前 |
| 本命予測（当日） | 確定時刻が `T-15` 以前 |

**`F-102` は `F-804`（当日の天候・馬場状態）を入力に含むため当日確定であり、`F-104` もこれに従う。** つまり暫定予測では Stage 1 の出力が馬場状態なしで推定され、Stage 2 の中核特徴量が劣化する。天候については予報値で部分的に埋める（`D-029`）が、**過去分の予報値が存在しないためバックテストでは埋まらない**（`Q-021`）。

### `F-901` の適用範囲（`D-021`）

**レース単位の変数を相対化してはならない。** `F-102`（想定ペース）はレース内で全馬共通の値を取るため、z-score が 0/0 になる。さらに `F-104 = F-102 × F-103` を相対化すると `z(F-104) = sign(F-102)·z(F-103)` に潰れ、**想定ペースの大きさが消えて Stage 1 が Stage 2 に届かなくなる**。この状態でもモデルは正常に学習でき、精度がやや出ないだけなのでテストでは捕まらない。

### 確率展開の偏り（`Q-017`）

Plackett-Luce（Harville 方式）は、**2着以下の確率について人気馬を系統的に過大評価する**ことが知られている。`D-008` が主評価に選んだ複勝・ワイドを直撃するため、補正しないまま期待値を計算すると人気馬を買いすぎる方向に歪む。

補正方法は `Q-017`。**モデルを作る前に市場データだけで偏りの大きさを確認できる**ので、`P-2` で潰す。

### モデル選択

- **Stage 2**: LightGBM `lambdarank`（`group` にレース単位を渡す）から始める。
  レース内相対性を目的関数側に組み込める。厳密なレース内softmaxはカスタム目的関数になるが、まずは `lambdarank` で十分。
- **発展形（`P-6` 以降）**: Set Transformer / DeepSets。出走馬の集合を入力し、馬同士の相互作用をattentionで学習する。
  `F-104` のような相互作用を手で設計しなくても拾える可能性があるが、データ量とチューニングコストが重い。

## 6. 評価設計

`D-008` に基づく。

### 6.1 検証手順

時系列walk-forward のみ。ランダムCVは禁止。

```
学習 2005-2014 → 検証 2015
学習 2005-2015 → 検証 2016
学習 2005-2016 → 検証 2017
...
```

年24レースしかないため単年の検証はサンプル数として無意味。**複数年ロールで累積して評価する。**

### 6.2 評価指標

| 指標 | 対象 | 判定 |
|---|---|---|
| LogLoss / Brier | 勝率予測 | **市場確率を下回ること**が最低条件 |
| Top-1 / Top-3 的中率 | 参考 | 市場と比較 |
| 回収率 + ブートストラップ95%CI | 複勝・ワイド主体 | CIが100%を上抜けるか |
| EV>1 のみ購入した場合の収支 | 全対象券種 | 購入点数と併せて評価 |

### 6.3 統計的検出力の限界（必ず意識する）

検証に使えるG1は約240レース。単勝の1点あたり標準偏差は σ≈4 程度。

```
回収率の標準誤差 ≈ 4 / √240 ≈ 26%
```

**回収率74%〜126%の範囲では「有意に勝てている」と言えない。**
「バックテストで回収率120%出た」が単なるノイズになる領域である。

→ 分散の小さい複勝・ワイドを主評価軸に置く（`D-008`）。

### 6.4 バックテストの罠

- ハイパーパラメータを検証期間の成績で選ぶと、それ自体がオーバーフィットになる。
  → 学習期間内でのネストした時系列分割でチューニングする
- 生存バイアス（引退馬・地方転出馬の扱い）
- 出走取消・競走中止の扱い。`runners.status`（`D-011`）で区別する。**取消・除外は返還あり、競走中止・失格は返還なし**なので、一律に `finish_pos` を NULL にすると両者を区別できず、買えなかった馬券を買ったことにして収支が歪む

## 7. 開発フェーズ

| Phase | 内容 | 完了条件 |
|---|---|---|
| **P-0** | 中間スキーマ + ローダー抽象化 + DuckDB格納 | 2〜3年分が再現可能に引ける |
| **P-1** | 特徴量パイプライン + **リーク検査テスト** | 発走時点情報のみをテストで保証 |
| **P-2** | ベースライン（1番人気ベタ買い / 市場確率） | 基準線のLogLossと回収率が出る |
| **P-3** | Stage 1 + Stage 2 + walk-forward検証 | 市場確率のLogLossを下回る |
| **P-4** | Plackett-Luce展開 + EV・分数ケリー | 回収率 + CI付きレポートが出る |
| **P-5** | CLI整備 | `umagic predict --race <id>` が動く |
| **P-6** | （将来）Set Transformer、JRDB調教データ合流 | — |

### P-1 のリーク検査について

**ここで失敗する人が最も多い。** テストコードとして書き、CIで常時検証する。
検証対象は `domain-knowledge.md` 5節「リーク防止の原則」の7項目。

特に注意：過去成績集計の日付フィルタ、同日開催レースの扱い（`F-501` `F-502` の例外規定）、そして**原則7（集計統計量の推定期間）**。原則7は日付フィルタの検査では捕まらないため、「未来のデータを足して再計算しても過去分の値が1ビットも変わらない」という形で中核テストに据える。

### P-2 を飛ばさないこと

「1番人気を買い続ける」の回収率（おおむね75〜80%）と市場確率のLogLossが、
**あらゆる改善の評価基準**になる。これがないと自分のモデルが良いのか悪いのか判定できない。
