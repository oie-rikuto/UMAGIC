# UMAGIC ドキュメント

JRA平地G1に限定した競馬予想モデルの設計ドキュメント群。

## ドキュメントの役割分担

このプロジェクトでは **「なぜそうするか」と「何を作るか」を意図的に分離** している。
設計の根拠を仕様書に混ぜると、仕様変更のたびに根拠が失われ、
逆に根拠を残したまま仕様を書くと読み手が実装すべきものを見失うため。

| ドキュメント | 役割 | 誰が読むか |
|---|---|---|
| [`requirements.md`](./requirements.md) | 満たすべき要件（`R-xxx`） | 完了判定をする人 |
| [`decisions.md`](./decisions.md) | 確定した設計判断とその根拠（ADRログ） | 設計変更を検討する人 |
| [`domain-knowledge.md`](./domain-knowledge.md) | プロの予想プロセスの形式化・特徴量カタログ | 特徴量を実装する人 |
| [`architecture.md`](./architecture.md) | システム構成・スキーマ・Phase計画・評価設計 | 全体像を掴む人 |
| [`open-questions.md`](./open-questions.md) | 未決事項と、決めるために必要な情報 | 次に判断する人 |
| [`spec/`](./spec/) | **実装仕様書（今後追加）** | 実装する人 |
| [`tasks.md`](./tasks.md) | 実作業と完了条件（`P-0`〜`P-3`） | 手を動かす人 |
| [`mcp-server.md`](./mcp-server.md) | UMAGICをLLMエージェント（Claude）に接続する手順（`Q-048`/`D-182`） | 実際に使ってみる人 |

`design.md` は作らない（`D-019`）。設計は `architecture.md`（全体）と `spec/`（モジュール単位）が担う。

## ID体系

ドキュメント間の相互参照のため、以下のIDを使う。
仕様書を書く際は、これらのIDを参照して「どの決定・どの特徴量の実装仕様か」を明示する。

| プレフィックス | 対象 | 定義場所 |
|---|---|---|
| `D-xxx` | 決定事項（Decision） | `decisions.md` |
| `F-xxx` | 特徴量（Feature） | `domain-knowledge.md` |
| `Q-xxx` | 未決事項（Open Question） | `open-questions.md` |
| `P-x` | 開発フェーズ（Phase） | `architecture.md` |
| `R-xxx` | 要件（Requirement） | `requirements.md` |

`tasks.md` のタスクにはIDを振らない（`D-019`）。

IDは**一度振ったら再利用しない**。決定が覆った場合は元のIDを `Superseded by D-xxx` として残し、新しいIDを振る。

## 仕様書を書くときの手順

1. `docs/spec/` に `NNN-<名前>.md` を追加する（[テンプレート](./spec/README.md)を使う）
2. 冒頭で関連する `D-xxx` / `F-xxx` を参照する
3. 仕様の過程で新たな設計判断が発生したら、`decisions.md` に `D-xxx` を追加してから仕様書側で参照する
   （仕様書の中に根拠を書き込まない）
4. 未決事項が出たら `open-questions.md` に `Q-xxx` を追加する

### `P-4` に進めない理由（`D-103`）

`R-023` 未達の要因を実データで診断した結果（2026-08-25）、**現在のモデルは市場確率に対する上乗せ情報を持たない**ことが分かった。市場確率とモデル確率を対数線形ブレンドして重みを探索すると、23,224レースという十分な検出力で最良重みが `w_model = 0.00` になる。この状態で期待値計算に進めば控除率20%ぶんそのまま負ける。

診断で分かったことは他に4点ある。ギャップの正体は校正ではなく識別力（最適温度で縮むのはギャップの1.6%のみ）。確率の目盛りは壊れていない（信頼性曲線の実測/予測が0.87〜1.07）。学習不足でもない（`best_iteration` は上限200に対して64〜65）。そして**能力の絶対値（走破時計ベース）に相当する特徴量が1本も無い**（→下記 `F-301`/`F-302`）。

### `F-301`/`F-302`（馬場差推定）は実装済みだが既定で無効（`D-104`〜`D-112`）

`Q-025` は解決済み（実装方法は自前の交互反復、`D-104`）。しかし実装して7fold walk-forwardで測定したところ、**`all` 母集団を7fold全て（+0.048〜+0.087の狭い幅）で一貫して悪化させた**。実装過程で `build_features()` の既存バグ（`D-109`、出走取消・競走除外が基底集合に混入し `_rank` 列が1.0を超える。`F-301`/`F-302`に限らず既存21列に影響）も発見・修正したが、修正後の汚染されていない基準でも `F-302` は悪化させた（`D-110`）。

原因究明として `Q-042`（レース効果へのメンバーレベル混入）を検証した。`race_class` が `G1`〜`G3`・`L`・無格付を `'オープン'` 1水準に丸めていることを確認し、`grade` を固定効果に追加した（`D-111`）。7fold walk-forwardで再測定すると **G1側の悪化幅は半減した**（+0.0484→+0.0229）が、**`all`側はほぼ無風**（+0.0702→+0.0697、`D-112`）。`Q-042`はG1側の副次的要因として部分的に実証されたが、`all`が一貫して悪化する主要因ではないと確定した。

`all`側は追加で分解診断も行った（`D-114`）。`F-302`の生値（relativize前）を含む構成は一貫して悪く、除いた構成は一貫して良かった——生値の無制限な尺度（縮約が弱い馬で効果量が二桁に達しうる）が主犯の一つ。しかし relativize 後（`z`のみ・`rank`のみ）でも全除去には届かず、**relativize後もF-302の中身自体がノイズとして働いている**ことが分かった。単純な後処理では埋まらず、`F-301`の推定方法自体（縮約の頑健化等）の見直しが要る、より大きな課題として残った。

`Stage2FoldRunner.include_track_variant` の既定値は `False` のまま。フルの7fold再検証は、見つかったどの候補も現状の既定を上回らなかったため実施していない。

`Q-039`（生IDのカテゴリ正則化）は解決済み。`cat_smooth=200`・`cat_l2=200`を`Stage2FoldRunner`の既定にし、7fold walk-forwardで確認した——`all`が7fold全て（−0.028〜−0.039の狭い幅）・G1（135レース集計）が−0.0270、いずれも改善した（`D-113`）。このセッションで唯一、`R-023`を実際に前進させた変更である。

### 本丸の答え: 現特徴量では `R-023` は達成できない（`D-119`）

`D-103` が残した本丸（モデルが市場に上乗せ情報を持たない）を切り分けた結果、**データ問題であることが確定した。**

市場確率を `init_score`（オフセット）として与え、モデルには**市場からの差分だけ**を学習させた（`f=0` で厳密に市場を再現する構成。`rounds=0` が3 fold とも市場と完全一致することで検算済み）。**市場を渡してもなお、`all` で得られる上乗せは最大 `0.0002`〜`0.0010` で5ラウンドで消え、G1 では一度も市場を下回らない。** `R-023` が埋めるべきG1のギャップ `0.4173` に対し、測定された上限はその **0.1% 以下**である。

順位指標（top-1的中率・NDCG@3）も同じ形で劣化したため、**目的関数の不一致（`lambdarank` は NDCG を最適化する）でも確率の尺度の問題でもない**。取り出す信号が無い。

**この結果は今セッションの経過をすべて説明する。** `F-302` が悪化させ（`D-110`）、`F-103` が不活性で（`D-118`）、`Q-039` の正則化だけが効いた（`D-113`）——いずれも市場が既に織り込んでいる同じ公開情報を再処理していたからである。**特徴量の作り込み・ハイパーパラメータ探索・縮約設計への追加投資は、下記の穴を埋めない限り `R-023` に対して無価値である。**

### 成功定義を改訂した（`D-121` 〜 `D-123`）

複勝プールも測った結果、**券種を変えても市場は超えられない**と確定した（`D-121`）。モデル本命の複勝回収率は市場本命を下回り（`all` で 0.8243 対 0.8386）、**市場に逆らうほど回収率が下がる**（0.8465 → 0.8060 → 0.7821、全バケツ有意に100%割れ）。`D-103` の診断2が複勝の実払戻でも再現した形である。

これを受けて `D-015` の成功定義を改訂した（`D-122`）。

- **`R-023`（旧A判定）・`R-024`（B判定）は削除せず、「現データでは達成不可能」という判定結果を注記して維持する**
- **新A判定 `R-029`: G1の情報捕捉率 `(一様LL − モデルLL) / (一様LL − 市場LL)` が `0.75` 以上**（現状 **0.5468**、上限 `1.0`）
- **`R-030`: `P-4` の着手条件を「市場への上乗せ `w_model > 0` が有意」と明文化**

**A判定の意味が変わったことを隠さない。** `D-015` は A判定に「オッズに乗っていない情報を掴んでいる」という含意を持たせていたが、`D-119` がそれを不可能と実証したため、新A判定は「モデルとして市場に匹敵する水準に達する」という意味になる。

`F-304`（中央値ベースの速度指数）を本番に採用することも決めた（`D-123`）。市場は超えないが `label` との相関 `+0.2345` で**本プロジェクト2番目に強い特徴量**であり、`R-029` を押し上げる主力になる。

### プロジェクトの目的を定め直した（`D-124`）

**当面の目的は「市場が持っていない情報を将来投入するための土台を整えること」に置く。** 市場確率に近づくこと（`R-029`）はその手段であり到達点ではない——**情報捕捉率 0.75 のモデルは、オッズ板を見れば無料で・即座に・より正確に得られるものの劣化再現でしかない。**

`D-002`（対象レースのオッズを特徴量にしない）は維持するが、**根拠を取り直した**。元の根拠「市場を超える余地を残す」は `D-119` が失効させたため、新しい根拠は「**将来新しい情報を投入したときに、その情報が市場に対して上乗せを持つかを測れる状態を保つため**」とする。オッズを入れるとモデルと市場が交絡し、`R-030` の測定が原理的に成立しなくなる。

**`R-029` は単勝オッズを特徴量に入れれば即座に `1.0` に到達する。** 禁じているのは `D-002` だけであり、`R-029` は「`D-002` の制約下での」達成度を測る指標である。報告時にこの前提を省略しない。

### 次に手を付けるもの

**`all` の情報捕捉率を `0.6767` から `0.75` に近づける**（`R-029`）。必要なLogLoss改善は **`2.1522 → 2.1033` の `0.0489`**。`D-119` が禁じたのは市場を**超える**ことであって、市場に**近づく**ことは否定されていない。

**刈り込みは経路にならない（`D-128`）。** 現構成でグループ別アブレーションを測り直したところ、**外した方が良いグループは1つも無かった**（14グループ × 3 fold の42セルすべてが正）。`D-103` の診断3（外した方が良いものが並ぶ）は `D-109` バグ修正前・`D-113` 正則化前・`F-304` 実装前・fold 0単独・CIなしの測定であり、現構成の判断材料として引用してはならない。

寄与の順位は3 foldで安定している——`F-601 前走`（+0.036〜+0.038）> **`F-304 速度指数`（+0.025〜+0.028）** > `F-7xx 人的ID` > `F-303 上がり3F` > `F-603 馬体重`。

**参考: これまでの単発の改善幅**は `D-113`（正則化）が `0.0341`、`F-304` が `0.0331`。**同規模が2件あれば `0.0489` に届く計算**になる。

**2つの経路は閉じた。** 刈り込みは `D-128`（外した方が良いグループは1つも無い）、ハイパーパラメータ探索は `D-129`（上限が `0.005` 前後で必要量の約10%）。条件付き速度指数（適性）も不発だった（`D-132`）。

### `R-029` の現在地と方針（`D-134`）

**`all` 捕捉率 `0.6951`、合格 `0.75`、残り `0.0549`**（LogLoss換算 `0.0367`）。**閾値 `0.75` は維持する**（`D-134`）——`v9` の `0.6271` から1セッションで `+0.068` 動いており射程内と判断した。下げると指標が事後的な定義になる（`D-030` の失敗の裏返し）。

**不利な材料も記録しておく**: 簡単な当たりは使い切った（未使用列・目的関数・速度指数）。外れた候補はいずれも「既にある情報の焼き直し」だった。上限は `1.0`（市場と同等）で `D-119` により超えられない。

### 探索の指針が2つ立った（`D-132` / `D-135`）

**木が自力で作れる情報を渡しても効かない（`D-132`）。** 条件付き速度指数（`surface` 別・距離帯別の適性）が不発だったのは、モデルが `f803_surface` と `fspd_*` の交互作用を自力で構成できたため。

**その対として、モデルが原理的に構成できない情報は効く（`D-135`）。** 該当するのは**他の行にまたがる集約**——モデルは対象馬の過去成績は見ているが、**その過去走で誰と走ったか**は別の行にあり到達できない。相手強度（`F-806`）は3 fold とも有意に改善した（−0.0061 / −0.0066 / −0.0045）。

**ただし指針には限界がある（`D-136`）。** 「モデルが構成できない情報」は**必要条件であって十分条件ではない**——`course`・斤量の自己履歴・馬体重の自己履歴はいずれも不発だった。**既存列と重複していれば効かない。** `F-806` が効いたのは、対戦相手の質が既存のどの列にも入っていなかったため。次に候補を立てるときは「構成できないか」に加えて「**既存列と重複していないか**」を確かめる。

なお `course`（競馬場）が特徴量に無いのは実装漏れではなかった。追加すると2 foldで有意に悪化する——`f803_distance`/`surface`/`direction` が実質的にコースを絞り込み、`F-802` が馬自身のコース別成績を持つため。`D-131`（`age`/`sex`/`weight_carried`）と表面上は同じ「使われていない列」だが、結論は逆だった。

### 2条件を満たす候補は当たった（`D-137` / `D-138`）

|---|---|

| **複勝** | `0.9637` → `0.5171` の**強い単調勾配**。単勝には無い歪みが複勝にだけある |

### 壁の理由が判明した——元返しによる構造的天井（`D-156`）

`D-154` の上限（`0.983`〜`0.991`）は探索不足による経験的な壁ではなく、**JRA の元返し（最低払戻100円）から導かれる構造的な天井**だった。

`ROI = 複勝率 × 払戻倍率` と分解すると、両者が逆方向に動いて積が `1.0` 未満で閉じる:

| PL複勝確率 | 複勝率 | 払戻倍率 | **元返し率** | ROI |
|---|---|---|---|---|
| 0.624 | 0.560 | 1.497 | 0.1% | 0.8387 |
| 0.922 | 0.837 | 1.096 | 4.6% | 0.9180 |
| **0.967** | **0.930** | **1.057** | **43.1%** | **0.9828** |

**最上位帯では的中の43.1%が元返し**。複勝率を上げようと極端な人気馬に向かうほど払戻倍率が `1.0` の床に張り付く。**「もっと極端な人気馬を探す」方向は原理的に無意味**だと確定した。

一般形では利益に `P_true / P_market > 1/(1−t) = 1.25` が必要で、実測は `1.2240`——**favorite-longshot bias が控除率20%のうち18ポイントを取り返すが、最後の2ポイントを元返しが塞ぐ。**

**未着手だった24スライスも全滅**（馬場状態4・芝ダ2・競馬場10・レース番号4・クラス4）。値が `0.87`〜`0.92` に密集し、点推定が `1.0` を超えたセルは1つも無い——この歪みは条件によらない**市場全体に一様な現象**である。

### `Q-018` の余地を定量化した（`D-157`）。候補としては残す

元返しは**実際の払戻**にかかる制約なので、複勝オッズ板が見えれば元返しの馬を避けられ、天井が動く可能性があった。**定量化した結果、余地は薄い。**

元返しを避ければ倍率は `1.06 → 1.10` に上がり、複勝率が変わらなければ **+1.5ポイントの黒字**。しかし余裕は `+0.015` しかなく、**黒字が見える領域では複勝オッズがほぼ動かない**（PL複勝確率 `0.923` 帯の四分位が `[1.10, 1.10]`、変動係数 `0.022`）。払戻が10円刻みで下限100円のため取りうる値が実質2つしかなく、**板を見ても選ぶ対象が存在しない。** さらに元返しになるのは群衆が最も確信している馬であり、避ければ複勝率が下がる（逆選択）。

**`Q-018` は候補として残す（ユーザー方針）。** 優先度は「高」から「中」に下げたが可能性は閉じていない。取得できた場合の判定基準（高払戻側で複勝率が `1.5` ポイント以上落ちないか）と取得経路の候補（`JRA-VAN` 未調査 / Webアーカイブ / 今から自前収集）は `D-157` と `Q-018` に記録した。

**なお `D-156` の「元返しが塞ぐ」という記述は `D-158` で訂正した。** 複勝払戻に100円未満は1件も無く、元返しは払戻を**引き上げる補助**である。塞いでいるのは控除率そのもので、元返しの役割は極端側の上限を複勝率で頭打ちにすること。`D-156` の結論（上限が構造的、探索方向が無意味、24スライス全滅）は変わらない。

### `G2`/`G3` を切り出しても超えられる歪みは無いと確定した（`D-169`）

ユーザーの質問（「G2/G3はどんな扱いか」）をきっかけに、**新規データ取得なしで**（既存の `payouts`/`runners`/`races` を絞るだけ）`D-152`〜`D-158` のプール構造分析を `G2`/`G3`（1,039レース）に限定して再測定した。**結論: `G2`/`G3` も `all`/`G1` と同じ構造で、超えられる歪みは無い。**

### オッズを特徴量にする経路も試し尽くした（`D-171`〜`D-173`）

ユーザーの提案（「オッズを特徴量にして良い。ただし単純な使い方ではダメで順位的な工夫が要る」）を受け、`D-002` を一時的に例外扱いして検証した。まず `D-163` の加法ブレンドを人気順位・オッズ帯21スライスで再測定したが**全て `w*=0.00`**（`D-171`）——特定の帯にだけ上乗せがあるという仮説も否定された。

次に、オッズ由来の順位特徴量（人気順位・相対順位・市場確率の対数、生のオッズ値は使わない）を**モデルの入力そのものに加えて再学習**した（`D-172`/`D-173`）。3 fold全てで市場のLogLossに届かなかった（`+0.0176`〜`+0.0198`）。**さらに切り分けたところ、この未達の大部分（約75%）はオッズ由来3列だけの構成でも既に生じており**、他の特徴量が原因ではなく**モデリング手法自体（Plackett-Luce目的関数・正則化・離散化）の技術的な限界**だと判明した。

**加法ブレンド・学習された変換器（`D-162`）・特徴量としての直接投入の3通りを試し、いずれも市場を超えられなかった。** オッズを使う経路はこれで一通り試し尽くしたと判断する。`D-002` は開発指標としては引き続き有効なまま維持する（本実験は独立した診断スクリプトのみで、`FEATURE_FNS`・本番パイプラインは変更していない）。

**現時点で残る前進経路は地方競馬（NAR）だけ**という状況を受け、`Q-047` 段階①（軽いサンプルでの市場効率測定）を実施した。**ただしユーザーは「中央競馬（JRA）での利益」が揺るがない最終目標であることを明示しており（`D-174`）、NAR探索はその代替ではなく並行探索と位置づけている。**

### `NAR`（大井）`Q-047` 段階①を実施した。明確な非効率は見つからなかった（`D-175`）

大井の2023年4〜6月（300レース）を、取り込みパイプラインを使わないスタンドアロンスクリプト（`data/nar_stage1_sample.py`）で軽くサンプル取得し、`D-152`/`D-169` と同じ単勝オッズ帯別ROIの手法で測定した。既存の `LocalCacheFetcher`・パーサーをそのまま再利用でき、新規実装は会場別レースID抽出のみで済み、`Q-047` の「取り込みパイプラインの新規実装は不要」という前提は成立した。

**両foldともCIが完全に正——市場に有意に劣後する。** 情報捕捉率自体はJRAの到達点（`v15` の `0.7169`）とほぼ同水準で、JRA向けにチューニングした特徴量・ハイパラがそのまま転用できたことは技術的な副産物だが、**市場には届かないという構造はJRAと同じ**だった。

**`Q-047` 段階①（プール構造、`D-175`）と段階②（予測モデル、`D-177`）の2つの独立した手法が、いずれも大井で捕捉可能な非効率を検出できなかった。** ただし大井1場・3年のみの標本で、特徴量もNAR向けに一切チューニングしていない、他場遠征馬の履歴も欠落している、という留保付き。

副産物として `shrinkage.py`（`F-103`/`F-202`/`F-303`/`F-701` 等が共通で使う `per_row_stat_before()`）の潜在バグを発見・修正した——データベース全体で最初期の日付（先頭100行超が `NULL`）で列のdtype推論を誤り `ComputeError` になりうる不具合で、JRA本番でも未発火のまま潜んでいた可能性がある（同日複数場開催のJRAでは先頭100行に実数値が混ざりやすく顕在化していなかった）。

段階③（NAR全場展開、`大`規模投資）に進む根拠は、この2段階の測定では得られなかった。

### 地方競馬の探索を段階②で打ち切った（`D-178`）

ユーザーは段階③（全場展開）を時間的コストを理由に見送ると明示した。**地方競馬（NAR）の探索はここで打ち切る。** `data/umagic_nar.duckdb` と取り込み基盤（`NetkeibaNarSource` 等）はコードとして残るため、将来再開する場合のコストは低い。

`D-174`（JRA利益が真の目標）と合わせ、**プロジェクトの前進経路は再びJRAに一本化される。** `D-124`〜`D-173` で確定した「現データ・現手法ではJRAの市場を超えられない」という状態は、地方競馬の探索を経ても変わっていない。

### `D-119`の(a)/(b)を再検証した。L2正則化つき線形残差モデルが市場に有意に勝った（`D-179`）

ユーザーの依頼で「既存の設計を見直す余地」を検討した結果、**LightGBM以外のモデルファミリーで`D-119`の残差検証をやり直すのが最有力**と判断し実施した。市場確率を固定オフセットとし現行特徴量（数値列121本）で残差を学習するL2正則化つき線形モデルが、`all`母集団で**市場に有意に勝った**（真のholdout併合 `-0.0039 [-0.0059, -0.0019]`、n=9,947レース、3fold中2foldが個別にも有意）。`D-142`の教訓どおり学習期間OOFだけでなく真のholdoutでも確認し、両者が一致した。

**`D-119`の結論を修正する: 「LightGBM（PL top-3・現行正則化）は市場への上乗せ情報を持たないが、データには小さな線形残差信号がある」。** 3fold共通で再現した係数（`f806_field_mean`・`f601`前走着順系・`F-304`速度指数系・`f809_top3_rate`等）は偶然とは考えにくい安定性を示した。

**ただし効果量は過去の実改善（`D-113` `0.03`〜`0.04`、`F-304` `0.033`）の約1桁小さく、G1では3fold とも有意差が出なかった**（標本が薄い）。

### 追試: LightGBMへの移植（b）失敗、G1限定（c）で逆に有意悪化 → 不採用（`D-180`）

ユーザーの事前合意（「(b)(c)が不成立なら(d)＝現状維持」）に従い2方向で追検証した。**両方とも不成立で、線形残差モデルは不採用と判定した。**

**(b)**: 目的関数・特徴量集合をLightGBMと完全に揃え（PL top-1・数値列のみ）、正則化・木の複雑さをグリッド探索して3fold・真のholdoutまで確認したが、**`all`母集団の対市場差は3fold全てCIが0をまたぎ有意差なし。** 目的関数・特徴量を揃えても木モデルは同じ改善を再現できなかった——`D-173`の「モデリング手法自体の限界」は木構造そのものの限界である可能性が高い。

**(c)**: G1個別foldは全て「差なし」だったが点推定は3fold全て市場より悪い側。`D-101`と同じ手法（学習期間G1をクロスフィッティングで標本を増やす、282レース）で確認したところ、**`+0.0187 [+0.0100, +0.0271]` と市場に有意に劣後**——`CLAUDE.md`が警告する既知の罠（「`all`で選ぶとG1を悪化させる候補を最良と誤判定する」）の3例目だった。

**線形残差モデルは本番採用を見送る。** `all`での有意な改善という発見自体（`D-119`の(a)/(b)切り分け）は撤回しないが、LightGBMへの移植経路が無く、G1では逆に有意悪化するため。ユーザー合意どおりここで追加投資を打ち切る（(d)）。

### 出馬表パーサーを新規実装した。「実際にまだ結果の出ていないレースを予測する」経路の第一歩（`D-181`）

ユーザーの提案（「G1/G2/G3を実際に予測できる状況か確認したい」）を受け、`Q-048`が挙げていた欠落の1つ目——出馬表（発走前の情報）を読むパーサーが無い——を解消した。`race.netkeiba.com`の`shutuba`ページは`archive`ページと全く別のHTMLテンプレートのため独立実装が必要だった。実ページ5レース（G1/G2/G3/未勝利/1勝クラス）で検証し、全て`races`テーブルの確定値と一致した。

発見: (1) オッズ・人気は静的HTMLに含まれない（`D-002`によりそもそも不要なので好都合）、(2) 馬場状態が1文字に略される（フル表記への展開表を実装）、(3) ヘッダの頭数と実際の出走予定行数が食い違うことがある（取消等、行の方が実勢を反映）。

**残る欠落**: 「今持っている全データで学習し、まだ走っていないレースを予測する」推論パス自体はまだ無い。次の一手として、JRA本番DBを書き換えずに対象レースを重ね合わせる設計（`ATTACH READ_ONLY` + `UNION ALL`ビュー、`D-176`と同じ「本番データを汚染しない」方針）を検討中。対象は2026年9月6日開催の重賞（ユーザー選択: 直近の重賞、G1/G2/G3問わず）を想定。

### 運用推論パスを実装し、実際に動作確認できた。JRA本番DB最新化に着手、MCPサーバーも実装（`D-182`）

`src/umagic/inference.py`（`ATTACH READ_ONLY` + `UNION ALL`ビュー）と`scripts/predict_race.py`を実装し、**皐月賞2026（本番DBに存在しないレース）で動作確認できた**——18頭の予測勝率が合計1.0000に正規化され、妥当な分布を示した。実装過程で2つのバグ（`inner_valid`が空になる／対象レース自身が封印される）を発見・修正した。

**JRA本番DBの最新化に着手した**（ユーザー依頼）。`2025-01-01〜2026-08-30`をバックグラウンドで取り込み中（推定8時間超、事前バックアップ済み）。完了後、皐月賞直前までのデータで再検証する。

**MCPサーバーも実装した（`Q-048`）。** 着手条件（市場に対して意味のある構成ができてから）はユーザーが明示的に一時解除した。`scripts/mcp_server.py`に5ツール（`predict_race`・`lookup_doc`・`search_docs`・`list_source_files`・`read_source`）。`predict_race`の戻り値には「市場への優位は未実証」という留保を毎回含める。**市場優位という核心の問題（`D-119`〜`D-180`）はMCPサーバー自体では解決しない。**

### `predict_race`が全履歴を毎回再計算し実用時間で終わらなかった。推論キャッシュを実装した（`D-183`）

本番DB最新化後（11年3ヶ月分）に皐月賞2026を再予測したところ**4時間経過しても終わらなかった。** macOS標準の`sample`コマンド（プロセスを終了させず調査可能）で原因を切り分けたところ、**物理メモリ8.7GB（ピーク14.1GB）に対し実行マシンの物理RAMが8GBしかなく、激しいスワップが発生していた**（相転移的にデータ量13%増で実行時間が5倍以上に伸びた）。

根本原因は`predict_fold()`が呼ぶたびに**過去の確定済みレース全履歴の特徴量を対象レース1件のために毎回ゼロから再計算**していたこと。`src/umagic/production_model.py`に推論キャッシュを実装した——`build_production_cache()`で全履歴のStage1・Stage2モデルを1回だけ学習・保存し（`scripts/build_prediction_cache.py`、本番DB更新時に再実行）、`predict_with_cache()`は**対象レース1件だけ**特徴量計算してキャッシュ済みモデルで予測する。`predict_race.py`・MCPサーバーの`predict_race`ツールともキャッシュ利用に切り替えた。

実装中、既存の`LightGBMStage1Model.load()`（未使用のまま埋まっていた）を誤って壊しかけたが、既存テストが検知して発覚・修正した。テスト追加（合成DBでのスモークテスト）、全452件通過。

### 本番DBでの実地検証: 再び数時間かかった。原因は「対象レースが既に本番DBに実在していた」重複だった（`D-184`）

本番DBでの実地検証で`predict_race`が再び7時間近くかかった。原因は**皐月賞2026が本番DB最新化（2026-04-25まで取り込み済み）によって「まだ結果の無い未来のレース」から「本番DBに実在する確定済みレース」に変わっていたこと。** `build_overlay()`が対象レースを本番DBに重ね合わせる際、両側に同じ`race_id`が重複し、`races`/`runners`のviewが非一意になって`join_asof`等の下流結合が異常な実行計画になっていた。

**この重複は運用上、今後も繰り返し起こりうる構造的リスク**（本番DBを最新化し続ける限り、過去に指定した対象レースの日付を取り込みが追い越すため）。`build_overlay()`に「対象レースが既に本番DBに存在する場合はValueErrorで明示的に拒否する」チェックを追加した。

修正後、本番DBに存在しない実在レースで検証したところ**20秒以内に完了**（合計勝率1.0000に正規化）——`D-183`のキャッシュ機構自体は設計どおり機能していたことが実証された。テスト2件追加（`tests/test_inference_realdata.py`）、全463件通過。

### MCPプロトコル経由の実地接続を検証した（`D-185`）

`claude mcp add`で登録し`✔ Connected`を確認、さらに`mcp`パッケージのクライアントSDKでサーバーをsubprocessとして直接起動し、`initialize`→`tools/list`→`tools/call`という実際のJSON-RPCプロトコルを叩いた（`data/mcp_client_test.py`）。5ツール全てが正しく列挙され、`lookup_doc`・`search_docs`・`list_source_files`が期待どおりの結果を返した（`predict_race`は本番DBが他の検証で使用中のため今回は呼んでいない）。

`claude mcp add`で登録したサーバーは**登録した瞬間には稼働中のセッションに反映されず、新しいセッション起動時にのみ読み込まれる**ことも実測で分かった。`Q-048`のMCP接続に関する未検証項目はこれで解消した。

### 皐月賞2026の真のheld-out予測を実施した。市場に届かなかった（`D-186`）

ユーザー依頼（「皐月賞ギリギリまでで学習して予測してみる」）に応え、`Stage2FoldRunner.predict_fold()`に`train_end=2026-04-18`のFoldを渡して真のheld-out検証を実施した（所要38.2分、`D-017`の封印を明示的にバイパス。`D-182`での確認を含めこれで2回目の開封——`D-186`で訂正・記録）。

モデルの本命グリーンエナジー（20.5%）は実際7着、実際の勝ち馬ロブチェン（市場1番人気）はモデルで4位（10.5%、LogLoss 2.26）——市場（LogLoss 1.62）には届かなかった。ただし`D-182`のstale版（LogLoss 2.94）からは改善しており、新しいデータで学習する価値自体は示された。単一レースのため統計的結論は出せないが、方向性は`D-119`〜`D-185`の構造と整合する。
