# UMAGIC MCPサーバーの使い方

`Q-048`（`D-181`/`D-182`）で実装した、UMAGICをLLMエージェント（Claude）に
接続するための手順。**着手条件（中央競馬か地方競馬で市場に対して意味の
ある構成ができてから）はユーザーが明示的に一時解除して実装したもの**で、
市場に対する優位という核心問題（`D-119`〜`D-190`）はこのサーバー自体
では解決していないことを踏まえて使うこと。

## サーバーが提供するもの

`scripts/mcp_server.py`（stdio transport）。

| ツール | できること |
|---|---|
| `predict_race(race_id)` | まだ発走していないJRAレースの各馬の勝率を予測する。推論キャッシュ（`D-183`）利用で20秒程度。戻り値に「市場への優位は未実証」という留保を毎回含む |
| `explain_race(race_id, top_k)` | 同じレースの**スコアの内訳**を`F-xxx`単位で返す（`D-192`、SHAP値）。「なぜその評価をしたか」を、人手で計算できない量（`F-304`速度指数・`F-809`キャリア成績率等）に分解する |
| `query_history(sql, max_rows)` | 本番DB（38,861レース・546,304出走行）に**読み取り専用**SQLを投げる（`D-192`）。過去の傾向を自由に問い合わせる |
| `lookup_doc(doc_id)` | `D-xxx`/`Q-xxx`/`R-xxx`/`F-xxx` のいずれかを指定して全文を1件取得する |
| `search_docs(query, doc=None)` | 上記4体系（`decisions.md`/`open-questions.md`/`requirements.md`/`domain-knowledge.md`）を横断検索する |
| `list_source_files(subdir)` | `src/umagic/` または `docs/` 配下のファイル一覧を返す |
| `log_prediction(race_id, picks, agent, ...)` | **発走前に**予想を記録する（`D-195`）。結果確定済みのレースは拒否する。券種は`単勝`/`複勝`/`ワイド`のみ |
| `score_agent(agent)` | 記録済みの予想を採点する（`D-195`）。回収率と95%信頼区間 |
| `list_logged_predictions(agent)` | 記録の一覧 |
| `read_source(path)` | 実装本体（`.py`）・仕様書（`docs/spec/*.md`）の中身をそのまま返す |

`predict_race` の `race_id` は netkeiba の12桁レースID（例:
`"202606030811"`）。出馬表は発走の数日前（例年水〜木曜）にしか公開され
ない。

## 接続手順

サーバー本体は素の stdio MCP サーバーなので、**Claude Desktop・Claude
Code CLI のどちらからも同じ実行コマンドで接続できる**。`uv`/`PATH` の
違いに左右されないよう、`.venv` の Python を絶対パスで直接呼ぶのが
確実（`uv run` はPATH次第で見つからないことがある。本セッションでも
`uv` コマンド自体はPATHに無く、絶対パスでの呼び出しが必要だった）。

```
python  = /Users/oierikuto/Desktop/UMAGIC/.venv/bin/python
script  = /Users/oierikuto/Desktop/UMAGIC/scripts/mcp_server.py
```

### Claude Code CLI から接続する

```bash
claude mcp add umagic -- /Users/oierikuto/Desktop/UMAGIC/.venv/bin/python \
  /Users/oierikuto/Desktop/UMAGIC/scripts/mcp_server.py
```

登録後は `claude mcp list` で確認できる。**登録した瞬間には稼働中の
セッションのツール一覧には反映されない**（`D-185`で実測確認）——
**新しいセッションを起動して初めて**`umagic`サーバーのツールが使える
ようになる。外すときは `claude mcp remove umagic`。

### Claude Desktop から接続する

設定ファイル（macOS）: `~/Library/Application Support/Claude/claude_desktop_config.json`

```json
{
  "mcpServers": {
    "umagic": {
      "command": "/Users/oierikuto/Desktop/UMAGIC/.venv/bin/python",
      "args": ["/Users/oierikuto/Desktop/UMAGIC/scripts/mcp_server.py"]
    }
  }
}
```

保存後、Claude Desktop を再起動すると認識される。

**サーバーのコードを変更したら、Claude Desktop を完全に終了して再起動
すること**（`⌘Q`。ウィンドウを閉じるだけでは足りない）。MCPサーバーは
Claude Desktop の起動時にプロセスとして立ち上がり、**その時点の
`mcp_server.py` をメモリに読み込んだまま生き続ける**——以降にファイルを
編集しても、走っているプロセスには反映されない。実際にこれで
「ツールが5種しか見えない」（`D-192`/`D-195` で追加した5種が出てこない）
という混乱が起きた。症状は「サーバーが古いビルドで動いている」ように
見えるが、原因はビルドではなく**プロセスの寿命**である。

**Claude Code CLI からの接続は`D-185`で実地検証済み**（`claude mcp add`
→ `✔ Connected`、および`mcp`パッケージのクライアントSDKで
`initialize`→`tools/list`→`tools/call`の実際のプロトコル往復を確認、
`data/mcp_client_test.py`）。**Claude Desktopからの接続も実運用で検証済み**
（2026-09-01以降、`analyst-v1`プロジェクトが`umagic`コネクタ経由で
`predict_race`/`explain_race`/`query_history`等を実際に呼び出し、
`D-197`の指摘のように実データに基づく分析まで行っている）。

接続できない場合はまず `python scripts/mcp_server.py` を直接実行して
エラーが出ないか確認すること。**サーバーのコードを変更した後にツールが
古いまま・数が合わないと感じたら、まずビルドではなくプロセスの寿命を
疑うこと**（上記「サーバーのコードを変更したら」を参照）。

**ツールが「エラー」とだけ返し、詳細が見えない場合**——Claude Desktop
はMCPサーバーの標準エラー出力を自動でログファイルに書き出している
（macOS: `~/Library/Logs/Claude/mcp-server-<サーバー名>.log`、この
サーバーなら `mcp-server-umagic.log`）。**Claude Desktop側から問い合わせ
る前に、まずこのファイルの末尾（`tail -100`程度）を直接見ること。**
stdioベースのMCPサーバーは通信そのものは外部から覗けないが、サーバー
プロセス自身が出す例外・スタックトレースはここに残る。`D-201`（
`predict_race`が本番当日に原因不明のまま失敗し続けた事故）は、この
ログを見て初めて根本原因（`PROD_DB_PATH`がプロセスのカレント
ディレクトリに依存していた）に到達できた。

## 依存

`mcp` パッケージ（`uv add mcp` で追加済み、`mcp==2.1.1`）。`uv sync` で
他の依存と一緒に入る。

## エージェントでの予想の進め方

`Q-048`が検討時点で出していた結論はこうだった: **モデルは市場に対して上乗せ情報を持たない（`D-163`）ので、`predict_race`の数値をそのままLLMに渡しても市場と同じ結論以上のものは出ない。LLMが価値を出せるとすれば、UMAGICの数値には無い情報（当日の気配・直前のニュース等をWeb検索で拾う）を掛け合わせたときだけ**。この節はその掛け合わせ方を手順として書く。**手順を書くことと、その手順が市場を上回ることを検証済みなのは別**——後者は`D-119`〜`D-190`の時点で未達のままである。

この手順を実行するには、同じセッションに`umagic`サーバーと**Web検索ができる何か**（Claude Codeの組み込みWeb検索、または別のMCPサーバー）の両方が接続されている必要がある。`umagic`サーバー自身は`src/umagic/`と`docs/`配下のローカルファイルしか読めず（`_READABLE_ROOTS`）、外部情報には一切アクセスしない。

### 手順

1. **対象レースの`race_id`を特定する。** `umagic`サーバーにはレース一覧を引く手段が無いため、Web検索で netkeiba のレースページ（`race.netkeiba.com/race/shutuba.html?race_id=...`）を探す。出馬表は発走の数日前（例年水〜木曜）にしか公開されない
2. **`predict_race(race_id)`でベースラインを取る。** 戻り値の`predictions`（全頭の勝率）と、`training_data_gap_days`（キャッシュの学習時点から対象レース日までの日数——空くほど新しい馬体重・戦績が反映されていない）、および毎回含まれる市場優位に関する留保をそのまま保持する。**この留保を省略して伝えないこと**
3. **市場（単勝オッズ）と突き合わせる。** `predict_race`はオッズを特徴量に使わない設計（`D-002`）だが、出力後に比較材料として見るのは制約に触れない——本プロジェクトのバックテスト自体、常にこの比較で評価してきた（`normalize(1/単勝オッズ)`との LogLoss 比較、`R-023`）。乖離が大きい馬（モデルが市場より強気/弱気）ほど、次のステップで理由を探す価値がある
4. **`explain_race`で「なぜそう評価したか」を取る**（`D-192`）。ステップ3で見つけた乖離の大きい馬について、モデルのスコアを`F-xxx`単位に分解する。**ここがUMAGICを実際に活かす中心**——「モデルはこの馬を高く見ている」で止めず、「モデルはこの馬の**キャリア成績率**（`F-809`）を高く見ている」まで具体化してから次に進む。特徴量の定義は`lookup_doc('F-809')`で引ける
5. **`query_history`で過去の実データに当たる**（`D-192`）。ステップ4で出た理由が、このコース・条件で実際に効いているかを確かめる。例: 「中山2000m芝の重賞で枠番別の3着内率はどうか」「この騎手のこのコース成績は」。**モデルの内訳とデータの傾向が食い違うときは、モデルを疑う根拠になる**
6. **数値の外側にある情報をWeb検索で補う。** これが`Q-048`のいう「UMAGICの数値には無い情報」であり、この手順で唯一UMAGIC単体を超えうる部分。具体的には: 直前の追い切り評価、乗り替わり・斤量変更、馬体重の増減、パドック・返し馬の気配、当日の馬場傾向（含水率・前残り/差しの決まり方）、天候の変化、有力厩舎のコメント。いずれも`predict_race`の学習データには（`training_data_gap_days`ぶん、あるいは構造的に）反映されていない。**ステップ4で得た具体的な理由を検証する形で調べる**——「`F-809`が高い＝キャリアの勝率が高い」なら、その充実度が今も続いているか（前走からの間隔、追い切りの動き、馬体重）を確認する
7. **モデルの既知の限界を`lookup_doc`/`search_docs`で確認する。** 特に`D-190`（モデル確率での期待値計算は全馬ベタ買いより悪い）・`D-119`（市場を上回れないという核心結論）・`D-189`（劣後幅はG1で最大）・`D-191`（運用時は`F-501`が常に欠損する）・`domain-knowledge.md`3節（G1では斤量・前走着順の情報量が一般的な競馬予想と逆転する）。これらを踏まえずにステップ6の定性情報だけで数値を上書きすると、根拠のない自信になる
8. **統合して提示する。** 「UMAGICの勝率 × 市場との乖離 × モデルの理由（ステップ4）× データの裏づけ（ステップ5）× 外部情報（ステップ6）」をセットで示し、**最後に必ず市場優位が未実証であるという留保を明記する。** 賭けの根拠として断定的に提示しないこと（`predict_race`自体の留保と同じ基準）

### 具体的なプロンプト例

```
umagicのpredict_raceで<race_id>を予測して。市場オッズと比較したうえで、
Web検索で当日の馬場傾向・追い切り評価・乗り替わりを調べて、モデルの
数値と食い違う馬があれば理由を探して。最後に、この予想が市場を上回る
という主張はまだ検証されていないことを明記して。
```

### 期待値・控除率・配当をどう扱うか

ここは**最も間違えやすく、間違えたことに気づきにくい**部分なので、実測を添えて詳しく書く。

#### 控除率（払戻率）は券種ごとに違う

| 券種 | 払戻率 | 控除率 | 利益に必要な `p_true/p_market` |
|---|---|---|---|
| 単勝・複勝 | 80.0% | 20.0% | `> 1.25` |
| 枠連・馬連・ワイド | 77.5% | 22.5% | `> 1.29` |
| 馬単・3連複 | 75.0% | 25.0% | `> 1.33` |
| 3連単 | 72.5% | 27.5% | `> 1.38` |

右端の列が`D-156`が導いた一般条件 `p_true/p_market > 1/(1−t)` である。**「当てる」だけでは足りず、市場より正確でなければ構造的に負ける**ことを示す。

#### 単勝期待値の計算式（と、その落とし穴）

```
EV = p × オッズ − 1        # +なら理論上プラス収支
```

`p` に何を入れるかが全てで、**`p_model`（UMAGICの出力）を入れてはいけない。** これは推測ではなく実測済みの結論である（`D-190`、23,224レース）。

| 戦略 | 賭け数 | 回収率 | 95%CI |
|---|---|---|---|
| モデル `EV > 0` の馬を買う | 176,928 | **0.6665** | [0.6334, 0.7001] |
| モデル `EV > 2.0` の馬を買う | 36,226 | **0.5963** | [0.4982, 0.6976] |
| （対照）全馬ベタ買い | 321,538 | 0.7202 | [0.7011, 0.7391] |
| （対照）市場1番人気だけ買う | 23,224 | 0.7889 | [0.7741, 0.8041] |

**EVフィルタをかけるほど回収率が下がり、何も考えずに全馬買うより悪い。** 理由は`D-190`にある——モデルは市場より不正確（`D-189`）なので、`p_model`と`p_market`が大きく食い違う馬は「市場が見落とした馬」ではなく**単にモデルが外している馬**であり、オッズが高いほどその誤差がEVに増幅されて乗る。`D-156`の条件式（比 `> 1.25`）で絞っても同じ形で失敗する（回収率 `0.6648`）。

**したがってエージェントは、モデルEVがプラスであることを買い材料として提示してはならない。** モデルと市場の乖離は「賭けるべき馬のシグナル」ではなく、**「なぜ食い違うのかを外部情報で調べるための着眼点」としてのみ使う。**

#### 券種の選び方

- **複勝・ワイドを軸に考える。** 控除率が低く分散が小さいため、同じレース数でも遥かに早く有意性が出る（`D-008`）。実測でもモデル本命の複勝は `0.8299` [0.8199, 0.8401] と、単勝でのEV戦略（`0.6665`）ほど壊れない（ただし市場1番人気の `0.8402` には及ばない）
- **3連単は避ける。** 控除率27.5%が最も高いうえ超高分散で、G1で年24競走という標本規模では有意差の検出力がほぼ無い（`D-008`）
- **UMAGICが直接出すのは単勝の勝率だけ。** 複勝・馬連・3連複などの確率は出力していないので、これらを語るときは単勝勝率からの粗い近似であることを必ず断る

#### 回収率を語るときの規律（`D-008`）

単勝1点あたりの標準偏差は σ≈4 程度あり、標準誤差は `4/√n` になる。**n=240（G1の約10年分）でも回収率74%〜126%の範囲では有意差を主張できない。** 数レースの結果で「当たった」「この方法は有効だ」と結論づけないこと。必ずブートストラップ信頼区間を添える。

### 買い方の一案（`D-194`）——利益は出ないが、最もマシな既知の構成

**先に結論**: 本プロジェクトの実測で**利益が出ると確認できた買い方は無い**。以下は「20%負ける」を「2%前後負ける」に変える一案であって、勝つ方法ではない。**「利益が出る」と紹介してはならない。**

**構成**: 単勝1.0〜1.5倍の馬の**複勝**を、**相手が楽なときだけ**買う。相手の楽さは市場の単勝オッズから計算したHarville複勝確率で測る。

| 絞り方 | n | ROI | 95%CI |
|---|---|---|---|
| 単勝1.0〜1.5倍の複勝を全部買う | 2,660 | 0.9497 | [0.9365, 0.9627] |
| **＋相手が楽な上位50%に絞る** | **1,330** | **0.9759** | **[0.9595, 0.9905]** |
| （対照）相手が強い下位50% | 1,330 | 0.9234 | [0.9025, 0.9435] |

根拠は`D-152`/`D-154`が見つけ、現行データ（38,861レース・11.7年）で再現した構造——**複勝プールは相手関係を十分に織り込んでいない**（CIが重ならない差）。頻度は年約114回。

**3つの限界を必ず添えること**:

1. **点推定が`1.0`を超える構成は1つも無い。** 絞り込みを強めると `0.9772`→`0.9730`→`0.9614` とむしろ悪化する。控除率20%のうち約18ポイントを取り返すが、残りが埋まらない（`D-156`/`D-158`）
2. **重賞では成立しない。** 年3.3回しか条件に合わず、有意性を語れる標本に到達しない。実質的に無格付戦の戦略である。**なおG1に限ると `n=10, ROI=1.09` と出るが、これは完全なノイズ**（`D-008`: 10件の標準誤差は概算126%）——この種の数字を成果として提示しないこと
3. **UMAGICを混ぜてはいけない。** 相手の楽さの判定をUMAGICの確率に差し替えると悪化する（市場 `0.9840` 対 UMAGIC `0.9700`、同じnで比較。`D-194`）。`D-190`（単勝でのEV計算）と同じ結論が複勝でも成立した

**この一案は「UMAGICを使わない」ことが要件になる。** モデルの役割は買い目を決めることではなく、`explain_race`/`query_history`で仮説を具体化し過去データで検証することにある（`D-194`）。

### 手順例（数字を入れた具体例）

架空の重賞（16頭）でステップ2〜6を通す。

**ステップ2〜3: `predict_race`の出力を市場と並べる**

| 馬 | `p_model` | 単勝オッズ | `p_market` | 比 | モデルEV |
|---|---|---|---|---|---|
| A | 0.24 | 3.2 | 0.244 | 0.98 | −0.23 |
| B | 0.09 | 24.0 | 0.033 | 2.76 | **+1.16** |
| C | 0.11 | 5.8 | 0.135 | 0.82 | −0.36 |

**ここで「BはEV +1.16だから買い」と結論するのが典型的な誤り。** `D-190`の実測では、この判断基準（`EV > 1.0`）で買った176,483点の回収率は `0.6449` で、全馬ベタ買い（0.7202）より悪い。

**ステップ4: Bの乖離の理由を外部情報で調べる**——これが本来の使い方。「モデルはBを市場の2.76倍評価している。なぜか？」を出発点に、Web検索で以下を確認する。

- モデルが拾えていない**マイナス材料**が市場にはあるか（直前の熱発、輸送減り、鞍上の乗り替わり、極端な外枠）→ **あるなら市場が正しく、モデルの過大評価**。これが大半のケース
- モデルが拾えている**プラス材料**を市場が織り込み損ねているか（前走が展開不利、初の距離短縮が明確に合う、当日の馬場が急変してBの脚質に向いた）→ **これが唯一「市場より正しいかもしれない」ケース**

**ステップ5: 既知の限界に照らして自己点検する**——G1なら`domain-knowledge.md`3節（斤量・前走着順の情報量が一般的な予想と逆転する）、`D-189`（G1ほどモデルは市場に劣後する。G1 +18.3% / G3 +9.3%）を確認する。**格が高いレースほどモデルの意見を割り引く。**

**ステップ6: 統合して意見を述べる**——以下を明示的に分けて書く。

1. **市場が示す序列**（最も信頼できる出発点）
2. **モデルが違う見方をしている点**とその大きさ
3. **その違いを外部情報が支持するか／否定するか**——ここがエージェント自身の判断
4. **結論と、その確信度**
5. **留保**: この判断が市場に対して優位を持つことは未検証（`D-119`〜`D-190`）

### 具体的なプロンプト例（期待値・配当まで含む版）

```
umagicのpredict_raceで<race_id>を予測して。次の順で整理してほしい。

1. 全頭の「モデル勝率／単勝オッズ／市場の暗黙確率／両者の比」を表にする
2. モデルと市場の乖離が大きい馬を3頭選ぶ
3. その3頭について explain_race でモデルのスコアの内訳を出して、
   「モデルは何を根拠にこの評価をしたのか」を F-xxx 単位で説明して。
   知らない F-xxx は lookup_doc で定義を引くこと
4. query_history で、その根拠がこのコース・条件で実際に効いているかを
   過去データで確かめて（例: 同コース同距離の重賞での枠番別3着内率、
   その騎手のコース成績）
5. Web検索で、UMAGICの学習データに無い直前情報を調べて（追い切り、
   乗り替わり、馬体重、当日の馬場傾向、陣営コメント）。3で出た根拠が
   今も有効かを検証する形で調べること
6. 複勝・ワイドを中心に、買うとしたらどう考えるかを控除率を踏まえて述べて。
   ただしモデルEVがプラスであることを買い材料に使わないこと（D-190で
   実測済み: その基準は全馬ベタ買いより回収率が低い）
7. あなた自身の結論と確信度、そして市場優位が未検証であることを明記して
```

### `query_history` を使うときの注意

- **値は日本語**。`runners.status` は `'出走'`（通常）・`'出走取消'`・`'競走除外'`・`'競走中止'`・`'失格'`・`'降着'`。`races.surface` は `'芝'`/`'ダート'`、`races.course` は `'中山'`等。**`status='ran'` のような英語の値は存在しない**（実際にこの誤りで静かに0件が返る事故が起きた、`D-192`）
- 成績を集計するときは `status NOT IN ('出走取消','競走除外')` で絞る（`D-073`）
- **結果が0件のときは、まず `SELECT DISTINCT <列> FROM <表>` で実際の値を確認する**
- このDBは**結果が確定した過去レースだけ**を持つ。予測対象の未来のレースはここに無い

### この手順自体の位置づけ

`Q-048`が挙げていた2用途のうち、この手順は(b)「実際の今後のレースを予想させる運用ツール」にあたる。**手順として実行可能になった（`D-181`〜`D-196`）だけであり、この手順を踏んだ予想が市場を上回るかどうかは未検証。** 検証するには、この手順に従った予想を一定数溜めて回収率をブートストラップ信頼区間つきで見る（`D-008`と同じ基準、単勝なら240レース規模の標本が要る）以外に方法が無く、**その仕組み自体は`D-195`で用意した（`log_prediction`/`score_agent`）が、現時点で記録は0件**。

**この手順の中で、統計的な裏づけがあるのは「モデル単体では市場に勝てない」という否定的な部分だけである**（`D-119`〜`D-190`）。ステップ4の外部情報との掛け合わせに価値があるかどうかは、期待であって実証ではない。

## 注意点

- `predict_race`/`explain_race` は呼ぶたびに**必ずライブでネットワーク
  アクセスする**（出馬表`shutuba`ページはキャッシュしない設計、`D-199`）。
  `D-014` のレート制限（既定5秒間隔）はそのままかかる。同じレースに
  対して複数回呼んでも、毎回その時点の最新の出馬表が返る——`D-197`の
  運用規律（枠順確認は早めに、本命予測は馬体重発表後に）はこの前提の
  上に成り立つ
- `data/umagic.duckdb`（JRA本番DB）は読み取り専用で扱い、書き換えない
  （`D-176`/`D-182` と同じ設計）
- **本命の予測は馬体重発表後（発走の約60分前）に実行する**（`D-197`）。
  馬体重が未発表の状態（金曜の枠順確定直後など）で実行すると
  LogLossが +0.1270 悪化し、本命が入れ替わるレースが13.7%に達する。
  重賞の学習データ22,278行すべてで馬体重が埋まっているため、
  「馬体重なし」はモデルがほぼ見たことのない入力になる
- **運用時は `F-501`（当日脚質バイアス）が常に欠損する**（`D-191`）。
  同日の先行レースが本番DBに無いため。学習時は重賞の99.93%で使えて
  いた特徴量だが、**実害は実測で小さい**（`D-193`: LogLoss +0.0039、
  `D-189` のG1ギャップ0.3462の約1.1%。本命の入れ替わりは300レース中
  4レース＝1.3%）。当日取り込みは実装しない方針
- 市場（単勝オッズ）に対する優位はまだ実証されていない（`D-119`〜
  `D-190`）。`predict_race` の出力を賭けの根拠にしないこと
