# 要件

このシステムが満たさなければならないこと。**「満たされたかどうかを判定できる形」** で書く。

実現方法はここに書かない。どう作るかは `architecture.md`（全体）と `docs/spec/`（モジュール単位）が担う。
判断の根拠もここに書かない。根拠は `decisions.md` に `D-xxx` として置き、ここからは参照する。

書式：

- **区分** … 機能 / 品質 / 制約
- **判定方法** … どうやって満たされたと確認するか
- **根拠** … `D-xxx`（あれば）

## 1. スコープと出力

### R-001 予測対象はJRA平地G1に限る

**区分**: 機能
**判定方法**: 予測コマンドがJRA平地G1の `race_id` を受け付け、それ以外を明示的なエラーで拒否する
**根拠**: `D-001`

### R-002 出走全頭の勝率を出力する

**区分**: 機能
**判定方法**: 出力に出走全頭の行が存在し、勝率の合計が `1.0 ± 1e-6` に収まる
**根拠**: `D-006`

### R-003 過去走が少ない馬にも確率を出す

**区分**: 機能
**判定方法**: 過去走が0件の馬（外国馬）および閾値未満の馬（地方所属馬・2歳馬・長期休養明け）にも確率が付与され、全体の合計が `1.0` を保つ。当該馬を除外したり確率0にしたりしない
**根拠**: `D-006`、`D-032`、`domain-knowledge.md` 3節

### R-004 学習データはJRA平地全レースとJpnIとする

**区分**: 機能
**判定方法**: 学習データにG1以外のJRA平地レースとJpnIが含まれ、障害（J・GI）と海外レースが含まれない
**根拠**: `D-003`、`D-025`

### R-005 当日、発走15分前までに本命予測を出せる

**区分**: 機能
**判定方法**: 馬体重発表後に実行し、対象レースの発走時刻の15分前までに全頭の確率と期待値が出力される
**根拠**: `D-024`（実現可能性は `Q-019` で未検証）

### R-006 枠順確定時点で暫定予測を出せる

**区分**: 機能
**判定方法**: **確定時刻が `木曜` 以前の特徴量のみ**で実行でき、出力に暫定である旨が明示される。天候は予報値を使い、実測値を参照しない。馬場状態は欠損として扱う
**根拠**: `D-024`、`D-028`、`D-029`

### R-007 対象レースの発走前に同日先行レースの結果が取り込まれている

**区分**: 機能
**判定方法**: 当日の本命予測を実行する時点で、同日・同競馬場で `race_number` が対象レースより小さいレースの着順とコーナー通過順がDBに存在する
**根拠**: `D-024`、`D-010`

### R-008 出した予測を全頭分保存する

**区分**: 機能
**判定方法**: 予測実行後、`race_id`・各馬・確率・モデルバージョン・実行時刻がDBに残り、後から実績と突合できる。暫定予測と本命予測が区別できる。**予測時点のオッズと確定オッズの両方**が残り、乖離を後から測れる
**根拠**: `D-027`、`D-031`

### R-009 購入結果と収支を記録し、予測と突合できる

**区分**: 機能
**判定方法**: 購入した券種・組み合わせ・金額・払戻を記録し、`R-008` の予測と突合したレポートが出力される
**根拠**: `D-015`（B判定）

### R-010 成果物はCLIとレポートである

**区分**: 機能
**判定方法**: `umagic predict --race <id>` が動作し、バックテスト結果がMarkdownまたはHTMLのレポートとして出力される
**根拠**: `D-004`

## 2. データ基盤

### R-011 中間スキーマはソース非依存である

**区分**: 制約
**判定方法**: ソース別ローダーを差し替えても、スキーマ定義とその下流（特徴量・モデル・バックテスト）が変更なしで動作する
**根拠**: `D-009`

### R-012 中間スキーマの全テーブルが出所と取得日時を持つ

**区分**: 制約
**判定方法**: `001-schema.md` が定義する中間スキーマの全テーブルに `source` と `fetched_at` が存在し、いずれも NOT NULL 制約がかかっている。運用テーブル（`fetch_log` / `rejected_rows` / `quality_runs` / `quality_findings`）は対象外とする（`D-046`）
**根拠**: `D-026`、`D-046`

### R-013 必須項目を欠く行を取り込まない

**区分**: 品質
**判定方法**: 取り込み済みデータに必須項目のNULLが0件。欠いた行は取り込まれず、`race_id` と欠損項目を添えて除外ログに残る。

**必須項目は `status` に依存する。** 走らなかった馬（出走取消・競走除外）に着順・走破タイム・オッズは存在しないため、これらを一律の必須項目にしない。`status` ごとの必須項目の一覧は `001-schema.md` が持つ

**根拠**: `D-011`（該当行を削除しない）。除外が大量に出た場合の扱いは `Q-020`

### R-014 整合検査をすべて通過する

**区分**: 品質
**判定方法**: 以下がすべて通過する。

| 検査 | 内容 |
|---|---|
| 頭数の整合 | `n_starters` = `status` がゲートを出た値（出走・競走中止・失格・降着）である行数 |
| 出馬表との整合 | `n_entries` = 全 `status` の行数、かつ `n_entries >= n_starters` |
| 払戻の整合 | 払戻の組み合わせに含まれる馬が当該レースに存在し、`status` がゲートを出た値である |
| 着順の整合 | 各馬について **`finish_pos` = 1 + （`finish_pos` が自分より小さい馬の数）**。同着では同一着順が複数行に現れ、その分だけ次の着順が飛ぶ |
| 着順と状態の整合 | `finish_pos` が入る `status` と入らない `status` が `001-schema.md` の定義と一致する |
| 着順マーカーの網羅 | 未知の着順マーカーを持つ行が取り込まれていない（`D-034`） |
| オッズと人気の単調性 | 同一レース内で、`popularity` が小さい馬ほど `odds_win` が小さい（同値を許容）。**実データで不良オッズを検出できることを確認済み**（`D-037`） |
| コーナー通過順の整合 | 完走馬の `runners.corners` の要素数が `races.corner_nos` と一致する（`D-043` / `D-044`） |

各検査と `012-data-quality.md` の `check_id` の対応は同仕様書の「`R-014` との対応」節にある。**どちらの側にも余りを出さない。**

**根拠**: `D-011`、`D-012`、`D-034`、`D-037`、`D-043`、`D-044`

### R-015 取得失敗で全体を停止しない

**区分**: 制約
**判定方法**: 一部の `race_id` で取得・パースが失敗しても処理が継続し、失敗が理由つきで記録される。**「未取得」と「取得済みだが該当データが存在しない」が区別できる**
**根拠**: なし

### R-016 レート制限とキャッシュを実装に組み込む

**区分**: 制約
**判定方法**: 同一URLの再取得がキャッシュで回避される。リクエスト間隔の下限が設定として保証され、設定で下限を下回れない
**根拠**: `D-014`

### R-017 取得データを再配布しない

**区分**: 制約
**判定方法**: 生データおよびその派生物がリポジトリにコミットされない状態が、`.gitignore` とCIの検査によって保証される
**根拠**: `D-014`

## 3. リーク防止

### R-018 予測対象レースのオッズを特徴量にしない

**区分**: 制約
**判定方法**: 特徴量生成が対象レースの `runners.odds_win` / `runners.popularity` / `odds` テーブルを参照しないことをテストで示せる。`F-701` `F-703` が使う過去レースの人気はこの制限の対象外
**根拠**: `D-002`、`Q-006`

### R-019 集計統計量の推定期間もas-ofで切る

**区分**: 制約
**判定方法**: **未来のデータを足して再計算したとき、過去分の特徴量の値が1ビットも変わらない。** 対象は `F-902` の `μ_global`、`F-301` の混合効果モデル、`F-201` の種牡馬embedding、**Stage 1 の学習**を含むすべての集計統計量（`D-054`）。判定は `as_of` を変えた二重実行の突き合わせで行い、**許容誤差を置かない**（`D-055`）
**根拠**: `domain-knowledge.md` 5節 原則7、`D-054`、`D-055`

### R-020 リーク防止の7原則をテストで検証し、CIで常時実行する

**区分**: 制約
**判定方法**: `tests/test_leakage.py` が7原則それぞれに対応するテストを持ち、CIで常時実行される。同日レースの前後判定（`F-501` `F-502` の例外規定）が `race_number` の厳密不等号であることを含む。**合成データで動かし**、実データに対する同じ検査は `pytest -m realdata` で分離する（`D-053`）。封印セット（`D-017`）の不参照も検査項目に含む（`D-056`）
**根拠**: `domain-knowledge.md` 5節、`D-010`、`D-053`、`D-056`

### R-021 同一入力から同一出力が再現できる

**区分**: 品質
**判定方法**: 同じコード・同じデータ・同じ乱数シードで2回実行し、全頭の確率が完全一致する
**根拠**: `D-027`

### R-028 全特徴量が確定時刻を持ち、締切より後に確定する特徴量が使われない

**区分**: 制約
**判定方法**: すべての `F-xxx` に確定時刻の属性が付与されており、属性を持たない特徴量が登録できない。加えて、各予測経路で**その経路の締切より後に確定する特徴量が入力に含まれていない**ことをテストで示せる（暫定予測は `木曜` 以前、本命予測は `T-15` 以前）。合成特徴量の確定時刻が入力のうち最も遅いものに一致することを含む
**根拠**: `D-028`

## 4. 評価と報告

### R-022 検証はwalk-forwardのみとする

**区分**: 品質
**判定方法**: ランダムCVを行うコードが存在しない。各foldの学習期間が検証期間より前であることをテストで示せる
**根拠**: `D-008`

### R-023 開発用検証のG1でLogLossが市場確率を下回る（旧A判定）

**区分**: 品質
**判定方法**: 開発用検証のG1で、モデルのLogLossが `normalize(1/単勝オッズ)` のLogLossを下回る
**根拠**: `D-002`、`D-015`

> **判定結果（2026-08-26）: 現在取得しているデータでは達成不可能と実測で確定した。** 市場確率を `init_score` として与え差分だけを学習させても、`all` で得られる上乗せは最大 `0.0002`〜`0.0010` で5ラウンドで消え、G1では一度も市場を下回らない（`D-119`）。走破時計に基づく能力指標も市場に織り込み済みだった（`D-120`）。**要件は削除せず維持する。** 新しいA判定は `R-029`。

### R-024 封印セットでB判定を満たす

**区分**: 品質
**判定方法**: 以下の両方を満たす。

| 条件 | 判定する標本 |
|---|---|
| LogLossが市場確率を下回る | **各回**の封印評価（1セット約72レース） |
| 複勝・ワイドの回収率のブートストラップ95%信頼区間の下限が100%を上回る | **互いに素な封印セットを累積した標本**。同じ年を2回カウントしない |

報告に累積標本数と累積に要した封印評価の回数を添える
**根拠**: `D-015`、`D-017`、`D-030`（必要な累積標本数は `Q-022`）

> **判定結果（2026-08-26）: 両条件とも現在取得しているデータでは達成不可能と実測で確定した。** 前半（LogLoss）は `R-023` と同じ条件であり `D-119`/`D-120` が否定する。後半（回収率）も、複勝の実払戻で測ったところモデル本命の回収率は市場本命を下回り、**市場に逆らうほど回収率が下がる**（`all` 23,224レースで 0.8465 → 0.8060 → 0.7821、全バケツが有意に100%割れ。`D-121`）。**要件は削除せず維持する。**

### R-025 回収率を信頼区間なしで報告しない

**区分**: 品質
**判定方法**: レポート内に、回収率の点推定のみが信頼区間を伴わずに記載されている箇所が存在しない
**根拠**: `D-008`

### R-026 封印セットの開封回数を報告に添える

**区分**: 品質
**判定方法**: 封印セットの成績を掲載したレポートに、その時点の累積開封回数が必ず併記される
**根拠**: `D-017`

### R-027 年代別の成績を併記する

**区分**: 品質
**判定方法**: walk-forwardの結果レポートに、全期間の平均だけでなく年代別（または年別）のLogLoss / Brier と券種別回収率が出力される
**根拠**: `D-018`

### R-029 開発用検証の全レースで情報捕捉率が0.75以上になる（新A判定）

**区分**: 品質
**判定方法**: 開発用検証の**全レース（`all` 母集団）**で、以下で定義する情報捕捉率が `0.75` 以上になる。**G1の情報捕捉率も併記する（判定には使わない）。**

```
情報捕捉率 = (LL_uniform − LL_model) / (LL_uniform − LL_market)

LL_X = レース単位の平均負対数尤度 = (1/R) Σ_r [ −Σ_i y_ri · log p_X(r,i) ]
  y_ri           1着なら 1/(1着同着頭数)、それ以外 0
  p_uniform(r,i) 1 / n_starters(r)
  p_market(r,i)  normalize(1 / odds_win)（出走取消・競走除外を除く）
  p_model(r,i)   校正後のモデル確率
```

`1.0` が市場と同等。現在値は **0.7131**（`all` 23,224レース、`D-139` 適用後の `v12`）。参考としてG1（135レース）は **0.6098**。合格まで `0.0369`。

> **判定母集団はG1から `all` に変更した（`D-127`）。実質的に基準を緩める変更である。** G1ではこの規模の差を検出できない——本プロジェクトで2番目に強い特徴量を投入しても変化が `+0.0126 [−0.0596, +0.0873]` とノイズに埋もれた（`D-126`）。**本要件は `D-001` が定めたG1スコープに対する達成度を測らない。** G1に向き合う要件は `R-023`（達成不可能と確定済み）と `R-027`（年代別の併記）が担う。

**根拠**: `D-122`（指標の定義と閾値）、`D-127`（判定母集団）、`D-134`（閾値の維持）、`D-126`、`D-073`、`D-074`、`D-097`、`D-098`

### R-030 `P-4` に進む前に市場への上乗せが正で有意であること

**区分**: 制約
**判定方法**: 市場確率とモデル確率を対数線形ブレンドして重み `w_model` を探索したとき、`w_model > 0` がブートストラップ信頼区間つきで有意に示される。満たさない限り `P-4`（期待値・ケリー）に着手しない
**根拠**: `D-103`、`D-119`、`D-122`

## 5. 要件にしないこと

**明示的に要件から外したもの。** 書かないと「決め忘れ」と区別がつかないため記録する。

| 項目 | 扱い | 根拠 |
|---|---|---|
| バックテストの実行時間 | 上限を設けない。**推論は例外**で `R-005` が課す | `D-027`、`D-015` |
| as-of での予測再現（過去の任意時点で出せたはずの予測の再構成） | 要件にしない。代わりに `R-008` で実行時点の予測を保存する。**`R-019`（原則7）はこの緩和の対象外** | `D-027` |
| 馬券購入の自動化 | スコープ外。購入は手動で行い、記録のみ `R-009` が担う | `D-004` |
| Webアプリ・通知連携 | スコープ外 | `D-004` |
| 予測対象としてのJpnI・障害・海外 | 予測対象はJRA平地G1のみ。JpnIは学習データとしてのみ使う | `D-001`、`D-025` |

## 6. 実運用に入る前の前提条件

要件ではないが、**満たさないまま実運用に入ると後から遡って影響する**もの。

| 項目 | 内容 |
|---|---|
| `Q-014` | 払戻金の課税上の扱いを税務の専門家に確認する。**このリポジトリのドキュメントは税務助言ではない** |
| `Q-003` の備考 | JRAの開催スケジュール（最終追い切り・枠順確定・馬体重発表の各時刻）を実運用前に再確認する |
| `D-014` 条件3 | netkeiba の利用規約と `robots.txt` を定期的に再確認する |
