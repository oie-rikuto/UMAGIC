# `D-208` G1/G2/G3開催前トリガー自動化 — 引き継ぎ手順

新しいセッションでこの自動化試験を再実行・継続するための手順。`docs/decisions.md`の`D-208`（試験導入の経緯とパターンBの訂正）を前提とする。

## まず読むもの

- `docs/decisions.md`の`D-208`
- `scripts/auto_predict.py`（決定論的な部分＝モデル勝率・`explain_race`相当のSHAP内訳・Harville組み合わせ確率を計算するスクリプト。実装済みでそのまま使える）
- `docs/mcp-server.md`「エージェントでの予想の進め方」節
- `docs/operations/day-of-runbook.md`
- `data/claude_desktop_selector_agent.md`（`selector-v1`の手順。市場乖離は一方向〈モデル≫市場〉のみを見る設計で、これは`D-195`が意図した検証対象の仮説なので**書き換えないこと**——`D-207`参照）

## 1. 対象レースを特定する

Web検索で今週末のJRA G1/G2/G3を確認し、netkeibaの`race_id`を特定する。**この文書やdecisions.mdに書かれた過去の対象レースを使い回さない**——必ず今すぐ検索して確認する。

## 2. Cronで自動チェックを仕掛ける

- Cronジョブは**このセッション限り**（最大7日で失効）。継続利用したいならセッションを開いたままにする必要があることをユーザーに伝える
- 各レースの発走時刻を確認し、馬体重発表が見込まれる時間帯（目安：発走60分前、`D-197`）を挟むよう、日付を固定したcron式（例: `9,24,39,54 14,15 <日> <月> *`）で15分間隔で数回発火するジョブを作る
- Cronのプロンプトには以下を必ず含める:
  1. `scripts/auto_predict.py <race_id>`を実行し`status`を確認（`weight_not_yet`/`not_drawn`なら何もせず終える。stderrは`2>/dev/null`で捨てる）
  2. `status: ready`かつ`data/auto_predict_reported_<race_id>.flag`が無い場合のみ本分析に進む
  3. `predictions[].drivers`（`explain_race`相当）で根拠を具体化
  4. Web検索でオッズを取得し市場確率との乖離を計算する。Yahoo!スポーツ競馬のオッズページ（`https://sports.yahoo.co.jp/keiba/race/odds/tfw/<race_id>?ninki=1`）がserver-renderedで使いやすいと実測済み——netkeibaの`shutuba`・モバイル版オッズページはどちらも静的HTMLに実オッズが無い（JavaScriptで後から埋まる）ので使えない
  5. `duckdb`で`data/umagic.duckdb`に読み取り専用SQLを投げ、乖離が疑わしい馬について枠番別3着内率・騎手のコース成績で裏取り（`status`列は日本語`'出走'`）
  6. Web検索で追い切り・乗り替わり・馬体重増減・陣営コメントを確認し、明確なマイナス材料がある馬は除外する
  7. 買い目案2パターン（予算各1000円）:
     - **パターンA（複勝・ワイド中心）**: `log_prediction`が受け付ける券種（単勝/複勝/ワイド）のみで構成する。後から正式記録に反映できる形にすることが目的
     - **パターンB（高配当狙い、券種自由）**: 馬連・馬単・ワイド・3連複・3連単のうち、その回で最も高配当が狙える組み合わせを選ぶ。**3連単に固定しない**（当初の誤解、`D-208`で訂正済み）。参考提案のみ、`log_prediction`には記録できないし記録しない。当落を見て有効性を判断する運用はしない（`D-202`/`D-008`）
  8. 全頭表・両パターン・確信度・留保をセッションに報告し、`touch data/auto_predict_reported_<race_id>.flag`

## 3. 結果が出たら答え合わせをする

レース終了後、`data/umagic.duckdb`への正式取り込みは`D-205`により数日遅れるため、**待たずに**netkeibaの結果ページを直接Web検索・取得して確認してよい。

- パターンA・パターンBそれぞれの買い目が実際に的中したかを照合する
- なぜ当たった/外れたかを、`drivers`・市場乖離・裏取りしたデータ・直前情報のどれが効いた/外れたかで具体的に分析する
- **`D-008`の規律を必ず適用する**: 少数レースの結果から統計的な結論を出さない。個別の当たり外れを記述するのはよいが、「このやり方は有効/無効」という一般化はしない
- **`D-207`と同じ過ちを繰り返さない**: バグ・実装上の手抜き・明確な事実誤認（`D-208`のパターンB定義の訂正のような性質のもの）は直してよいが、`selector-v1`の核心的な仮説（手順のステップ4、市場乖離を一方向にしか見ない設計）を少数の結果だけで書き換えてはいけない。この2つを毎回明示的に区別すること
- 検証可能な仮説は`docs/open-questions.md`に`Q-xxx`として起票し、十分なデータで検証してから`decisions.md`に`D-xxx`として確定させる（`Q-049`→`D-207`と同じ手順）。バグ修正や設計判断はそのまま`decisions.md`に`D-xxx`として記録する
- 記録・修正した内容は`docs/tasks.md`・`docs/README.md`「現在の状態」にも反映し、`uv run pytest tests/ -q -m "not realdata"`を通してからfeatureブランチ→main merge→pushする（直接mainにコミットしない）

## 注意事項

- 単勝オッズは静的HTMLのどこにも存在しない。Web検索でのオッズ取得は必須の分担であり省略できない
- 「今日は何日か」「レースはいつか」を思い込みで判断せず、都度確認する
- ユーザーから「どうですか」「進捗は」と聞かれたら、キャッシュされた古い判断を繰り返さず、その都度ライブで確認し直す
