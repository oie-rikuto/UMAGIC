### 1.2 金曜（枠順確定直後）に本予測を出してはいけない

馬体重発表前に`predict_race`を走らせると`f603_*_unavailable=1`が立つ。これは学習データの重賞に一度も現れない入力領域である。

DBでの確認（重賞22,278出走行、`status NOT IN ('出走取消','競走除外')`）:

- `horse_weight IS NULL`: 0件
- `track_condition IS NULL`: 0件

```sql
SELECT COUNT(*) AS n_rows,
       SUM(CASE WHEN ru.horse_weight IS NULL THEN 1 ELSE 0 END) AS n_weight_null,
       SUM(CASE WHEN r.track_condition IS NULL THEN 1 ELSE 0 END) AS n_cond_null
FROM runners ru JOIN races r USING (race_id)
WHERE r.grade IN ('G1','G2','G3') AND ru.status NOT IN ('出走取消','競走除外');
```

実測された劣化（開発側で測定済み）:

| 欠損 | LogLoss差 | 本命入れ替わり |
|---|---|---|
| `F-501`欠損（`D-193`、運用時に常時発生） | +0.0039 [+0.0003, +0.0074] | 1.3%（300レース中4） |
| `F-603`欠損（金曜予測） | +0.1270 [+0.1043, +0.1513] | 13.7%（300レース中41） |

`F-603`欠損は`F-501`欠損の約33倍で、`D-189`のG1ギャップ0.3462の36.7%に相当する。

**規律**: 金曜の`predict_race`は「暫定」としてのみ使う。乖離馬の当たりを付け、`explain_race`で根拠のF-xxxを掴む用途に限る。買い目・確信度・`log_prediction`は当日の馬体重発表後の実行に基づいて行う。

### 1.3 F-501欠損は許容する（作らない）

`D-193`が`D-191`の選択肢(c)を採り、当日の既走レース取り込み（案(a)）は実装しないと決定済み。上表のとおり実害が小さいため。

ただし混同しないこと。**「モデルがF-501をほとんど使っていない」は「当日の馬場バイアスに情報が無い」を意味しない。** `D-119`の枠組みでは「情報はあるがモデルが取り出せていない」側の可能性が残る（`D-198`）。`domain-knowledge.md`が当日馬場バイアスを「市場を超えられる領域」の優先度1に置いた見立ては否定されていない。したがって人間／エージェントの定性判断の層では、馬場バイアスは引き続き見る価値がある（第3節の手計算はそのための道具であり、モデルに注入するものではない）。

## 3. F-501 相当の手計算

### 3.1 定義（`src/umagic/features/f501.py`の写し）

- 対象: 同日・同競馬場・同馬場（芝／ダート）で、`race_number`が対象レースより厳密に小さいレース
- 各レースの1〜3着馬について、最終コーナー通過順 ÷ そのレースの出走頭数
- それら全部の単純平均が`F-501`
- 該当0件なら`f501_unavailable = 1`
- `race_level = True`（レース内の全馬で同じ値）
- 通過順が無いレース（新潟直線1000mなど）は除外される

### 3.2 手順

1. 当日のレース一覧を取得し、対象レースより前の同馬場のレースを列挙する
2. 各レースの結果ページ`https://race.netkeiba.com/race/result.html?race_id=<12桁>`を取得
3. 着順表の「コーナー通過順」列（例`10-11-11-11`）の最後の数字と、ヘッダの頭数（例`16頭`）を読む
4. 1〜3着の3行について、最後の数字 ÷ 頭数を計算
5. 全レース・全該当馬をまとめて単純平均

取得のたびに、返ってきたページのレース番号・レース名・頭数が要求した`race_id`と一致するか確認する（第5節の失敗モード）。

### 3.3 検証済みであること

ラジオNIKKEI賞2026（`202603020211`）で、DBの内訳18行（先行する芝6レース×上位3着）とWeb結果ページの「コーナー通過順」列が同一形式であることを突き合わせ済み。手計算値`F-501 = 0.278`。

DB側の再現SQL:

```sql
WITH t AS (SELECT race_id, date, course, surface, race_number FROM races WHERE race_id = ?)
SELECT hr.race_number, hr.n_starters, ru.finish_pos, ru.corners,
       list_extract(ru.corners, len(ru.corners)) AS last_corner,
       CAST(list_extract(ru.corners, len(ru.corners)) AS DOUBLE)/hr.n_starters AS pos_ratio
FROM t
JOIN races hr ON hr.date=t.date AND hr.course=t.course AND hr.surface=t.surface
              AND hr.race_number < t.race_number
JOIN runners ru ON ru.race_id=hr.race_id AND ru.finish_pos <= 3
WHERE ru.corners IS NOT NULL AND len(ru.corners) > 0
ORDER BY hr.race_number, ru.finish_pos;
```

### 3.4 読むための基準値

値はコースで水準が違う。絶対値でなくコース別の分位で読むこと。

芝、2023-01-01以降、全レース（対象レースより前に同馬場レースがあるもの）:

| コース | n | p05 | p25 | 中央値 | p75 | p95 |
|---|---|---|---|---|---|---|
| 中山 | 595 | 0.167 | 0.229 | 0.283 | 0.341 | 0.422 |
| 阪神 | 526 | 0.191 | 0.289 | 0.356 | 0.411 | 0.510 |

低いほど「前で運んだ馬が上位＝前残り」、高いほど「後方から届く＝差し有利」。中山は阪神より構造的に0.07ほど低い。同じ0.30でも、中山なら平均的・阪神なら明確に前残り寄り。

他場を使うときは同じSQLで引き直すこと:

```sql
WITH t AS (
  SELECT race_id, date, course, surface, race_number FROM races
  WHERE course IN ('中山','阪神') AND surface='芝' AND date >= '2023-01-01'
),
e AS (
  SELECT t.race_id, t.course,
         CAST(list_extract(ru.corners, len(ru.corners)) AS DOUBLE)/hr.n_starters AS pos_ratio
  FROM t
  JOIN races hr ON hr.date=t.date AND hr.course=t.course AND hr.surface=t.surface
                AND hr.race_number < t.race_number
  JOIN runners ru ON ru.race_id=hr.race_id AND ru.finish_pos <= 3
  WHERE ru.corners IS NOT NULL AND len(ru.corners) > 0
),
f AS (SELECT race_id, course, AVG(pos_ratio) AS f501 FROM e GROUP BY race_id, course)
SELECT course, COUNT(*) AS n,
       QUANTILE_CONT(f501,0.05) AS p05, QUANTILE_CONT(f501,0.25) AS p25,
       MEDIAN(f501) AS p50,
       QUANTILE_CONT(f501,0.75) AS p75, QUANTILE_CONT(f501,0.95) AS p95
FROM f GROUP BY course;
```

### 3.6 既知のクセ

- 少頭数レースが同じ重みで入る。5頭立ての3着が4番手なら0.8が1票入る。頭数の少ないレースが混ざる日は値が振れる

## 5. 失敗モードと確認手順

- **別レースの内容が返ってくることがある。** `race_id=202603020209`（9R）を要求して`202603020211`（11R）の中身が返った実例あり。`final_url`が別IDになっていた。取得後にページ内のレース番号・レース名・頭数を照合すること。当日は10本近く連続で叩くので、黙って別レースで計算すると気づけない
- **枠順抽選前は`predict_race`が`retry_later: True`を返す**（`D-196`）。出馬表は公開済みでも馬番・枠番のセルが空になるため。エラーではなく待機状態
- 発走前ページには未検証の状態が残っている可能性がある（除外馬の表示、騎手未定など）。`D-181`の検証5件はすべて結果確定後のページだった。ただし馬体重は結果確定後ページにも載っているため、馬体重入りページのパースは`D-181`で検証済み（この点を「未検証」と扱うのは誤り）

## 6. やってはいけないこと

- **`D-190`の論法**: 「モデル勝率×オッズ−1がプラスだから買い」。実測でモデルEV>0の馬を買うと回収率0.6665、全馬ベタ買い0.7202、市場1番人気のみ0.7889。EV閾値を上げるほど悪化（EV>2.0で0.5963）。モデルの評価は「どの馬が強いか」の判断に使い、オッズとの掛け算には使わない
- **3連単を主軸にした提案。** 控除率27.5%かつ分散が極大で、`D-008`により検出力が無い。`log_prediction`も単勝/複勝/ワイド以外を拒否する。**追記（`D-202`）**: `suggest_exotic_bets`ツールで馬連/馬単/ワイド/3連複/3連単の組み合わせを**提案**することはできるようになったが、これはHarville近似による参考値であり、記録・採点はできない。「提案して当落を見て良し悪しを判断する」という運用はしないこと——n=1〜数レースでは実力と分散を区別できない
- **少数の結果からの結論。** 単勝回収率の標準誤差は目安`4/√n`。n=240でも74〜126%は有意でない
- **結果を見てからの記録。** `log_prediction`は結果確定済みレースと`race_id`×`agent`の重複を拒否する

## 7. エージェント間の分離（`D-195`）

`analyst-v1`と`selector-v1`は同じレースを別々に予想し、`score_agent`で別々に採点して比較する設計になっている。この比較を壊さないために:

- 本文書に含めてよいのは、事実・手順・過去データの集計まで。個別レースの見立て、乖離馬の解釈、買い目、確信度は書かない
- 共有してよい入力: 手計算した`F-501`の値、追い切り評価の生データ、含水率、馬体重、オッズ。これらは両者に等しく与えられる観測値である
- 共有してはいけない出力: 一方のエージェントの結論・推奨・重み付け。混ざると`D-195`の比較が意味を失う
- `log_prediction`の`agent`は必ず各プロジェクトの名前（`analyst-v1`/`selector-v1`）を使う。取り違えないこと

## 9. 留保（毎回明記すること）

UMAGICは2015年以降のJRA全レースで学習しているが、これまでの検証でG1における対数損失が市場（単勝オッズの暗黙確率）を安定して下回れたことは一度もない（`D-119`）。市場確率とモデル確率を最適配合してもモデル側の重みが実質ゼロになる。UMAGICの数値をそのまま賭けの根拠にしても、市場に勝てる保証はどこにもない。

本文書の手順を踏んで当日情報を集めても、この点は変わらない。ここで集められるものはすべて公開情報であり、締切前のオッズには既に織り込まれている。モデルと市場の乖離は「買うべき馬のシグナル」ではなく、「なぜ食い違うのかを外部情報で調べるための着眼点」としてのみ使う。

提示できるのは検証済みの優位ではなく、現時点での見立てである。この区別を読み手に対して常に明確にすること。
