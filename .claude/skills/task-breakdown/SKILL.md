# タスク分解

要件・仕様書・Phase計画から実装タスクを導出し、`docs/tasks.md` を作る。

## このスキルの性質

`spec-hearing` と違い、**ヒアリングが主ではない。導出が主。**

必要な情報は既に `docs/` にある。`R-xxx` が満たすべきことを、`docs/spec/` が作るものを、`architecture.md` 7節が Phase の完了条件を持っている。タスクはそこから機械的に落ちてくる。

ユーザーに聞くのは、**導出できない2点**だけである。

- 着手する範囲（どのPhaseまで洗い出すか）
- 依存が循環している箇所で、どちらを先に置くか

それ以外を質問するのは、docs を読んでいない証拠になる。

## 前提となる規約

`docs/tasks.md` の書式は `.claude/rules/docs-writing.md` の「`tasks.md` の書き方」にある。**書き出す前に必ず読むこと。**

## 手順

### 1. 対象範囲を決める

**着手するPhaseの分だけ**洗い出す。`docs/spec/README.md` に「この一覧は全部書く約束ではない」とあるのと同じ理由で、先のPhaseまで分解しても前提が変わって捨てることになる。

原則として**1つのPhase**を対象にする。範囲がPhaseをまたぐ場合はユーザーに確認する。

### 2. 読む

- `docs/requirements.md` … 満たすべきこと（`R-xxx`）
- `docs/spec/` … 対象Phaseの仕様書。**存在しない仕様書に対応するタスクは作らない**（後述）
- `docs/architecture.md` 7節 … Phase の完了条件
- `docs/decisions.md` … 制約になる決定
- `docs/open-questions.md` … 未決事項。**ブロックされているタスクを見分けるために必ず見る**
- `docs/tasks.md` … 既存があれば、完了済みを消さずに追記する

### 3. タスクを導出する

各仕様書について、「実装する」「テストする」を機械的に並べるのではなく、**検証可能な単位**に割る。

1タスクの目安は**1回のコミットで終わる粒度**。数日かかるものは分解する。「〜を検討する」はタスクではない（検討は仕様書側の仕事で、それが残っているなら `spec-hearing` に戻る）。

各タスクに以下を付ける。

- 該当する仕様書と `R-xxx` への参照
- **検証可能な完了条件**。何ができたら終わりかを、実行できる形で書く

### 4. 依存順に並べる

**上から順に着手できる状態にする。** これがタスク分解の主要な価値であり、並べ替えを怠ると読み手が毎回自分で依存を解くことになる。

このプロジェクトで特に効く順序の制約が4つある。いずれも**後から直すのが高くつく**ものなので、下に落とさない。

| 制約 | 理由 |
|---|---|
| **リーク検査（`004`）を特徴量実装より前に置く** | 後から入れると、それまでに書いた特徴量を全部見直すことになる。`P-1` の早い段階で骨組みだけでも通す |
| **ベースライン（`005`）を本モデルより前に置く** | 市場確率という基準線がないと、改善したかどうかを判定できない。`architecture.md` 6.2 の「最低条件」がこれ |
| **中間スキーマ（`001`）を他のすべてより前に置く** | `D-009` により全モジュールが依存する |
| **学習パイプライン（`014`）をモデル実装より前に置く** | fold 生成と `sample_weight` が決まっていないとモデルを評価できない |

### 5. ブロックされているタスクを明示する

未解決の `Q-xxx` に依存するタスクは、**リストから外さずに、何にブロックされているかを添えて残す。** 外すと存在ごと忘れられ、`Q-xxx` が解決したときに拾い直せない。

```markdown
- [ ] netkeiba のパース規則を実装する（`002-loader.md` / `R-002`）
      **ブロック中: `Q-011`**（必要な項目が実在するか未確認）
      完了条件: 7条件のレースすべてで中間スキーマの全カラムが埋まる
```

### 6. 作ってはいけないタスクを排除する

書き終えたら読み返し、以下がないか確認する。**いずれも決定に違反しており、実行されると設計が壊れる。**

- **封印セットに触れるタスク**（`D-017`）。「直近のG1で精度を確認する」は封印違反。開発中の検証は封印外で行う
- **仕様書が存在しない実装タスク**。書くべき仕様が決まっていない状態で実装すると、仕様書が実装の写しになる。先に `spec-hearing` に戻る
- **G1のみでモデルを学習するタスク**（`D-003`）。学習は全レース
- **予測対象レースのオッズを特徴量に使うタスク**（`D-002`）

### 7. 報告する

- 作成・更新した `docs/tasks.md` のパスと、タスク数
- **ブロックされているタスクの一覧**と、それぞれ何を待っているか
- 依存の循環があった箇所と、どう解いたか
- 仕様書が無いために作らなかったタスク（あれば）

ブロック中のタスクを埋もれさせない。何を解決すれば何本進むかが、そのままユーザーの次の判断材料になる。

## このスキルの範囲外

- **実装コードを書くこと。** タスクが並んだ時点で止まり、着手するかはユーザーに確認する。
- **要件・仕様を決めること。** 分解の途中で仕様の穴が見つかったら、その場で埋めず `spec-hearing` に戻る。
- **既存タスクの完了判定。** チェックを付けるのは実際に完了したときであって、分解時ではない。
