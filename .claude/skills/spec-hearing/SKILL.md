# 仕様ヒアリング

UMAGICの実装仕様書を、ユーザーへのヒアリングを通じて作る。

## このスキルが必要な理由

仕様書をいきなり書こうとすると、決まった形で壊れる。

| 失敗 | 何が起きるか |
|---|---|
| 既に決まっていることを質問する | ユーザーは同じ判断を二度させられる。ドキュメントが信用されなくなる |
| 決まっていないことを推測で埋める | 後から読んだ人が「決定済み」と誤認する。最も害が大きい |
| 調べていないことを確定として書く | それらしく書けてしまうため、検証済みだと誤解される |
| 散文で説明して終わる | 判断には迷わないが手が動かせない。実装者が結局書き起こす |
| 根拠を仕様書に書く | `decisions.md` との役割分担が崩れ、仕様変更のたびに根拠が失われる |

このスキルは、**読んでから聞く / 分からないことは分からないまま記録する / 実装者が再導出せずに済む形で書く** の3点を守らせるためにある。

## 前提となる規約

`docs/` の書き方（役割分担・ID体系・仕様書の手順・制約節に必ず書くもの）は `.claude/rules/docs-writing.md` にある。**書き出す前に必ず読むこと。** ここには再掲しない。

ドメイン上の制約は `CLAUDE.md` の「設計原則」にある。

## 手順

### 1. 対象を特定する

**まず「要件」と「仕様」のどちらを固めるのかを決める。** 混ぜると、満たすべきことと作り方が同じ文書に同居して、どちらも読めなくなる。

| 依頼の形 | 対象 | 書き出し先 |
|---|---|---|
| 「何を満たすべきか」「要件を決めたい」「受入条件を固めたい」 | **要件** | `docs/requirements.md`（`R-xxx`） |
| 「何をどう作るか」「◯◯の仕様を書いて」「NNN-*.md を作って」 | **仕様** | `docs/spec/NNN-*.md` |

判別がつかない依頼（「P-0を固めたい」など）は、**要件が先**である。仕様は要件を満たす手段なので、要件が無いまま仕様を書くと、何のために作るのかが仕様書の中で暗黙になる。ユーザーに確認して選ばせる。

要件が対象なら、以下の手順のうち「仕様書」と書かれている箇所を `requirements.md` に読み替える。書式は `.claude/rules/docs-writing.md` の「要件の書き方」に従う。手順7の「再導出しなくて済む形」は要件にも効く。**判定方法を書かない要件は、満たされたかどうか誰にも分からない。**

仕様が対象なら、`docs/spec/README.md` の想定リストに該当するものがあれば番号と名前をそのまま使う。無ければ次の空き番号を取る。

いずれの場合も **1回のヒアリングで1本**に絞る。複数を同時に進めると質問が混ざり、どちらも中途半端になる。

**タスク分解は対象外。** `tasks.md` を作る依頼は `task-breakdown` スキルを使う。

### 2. 既に決まっていることを棚卸しし、ユーザーに提示する

質問を作る前に必ず読む。

- `docs/decisions.md` … 確定済みの判断（`D-xxx`）
- `docs/architecture.md` … 構成・スキーマ・評価設計・Phase計画
- `docs/domain-knowledge.md` … 特徴量カタログ（`F-xxx`）とリーク防止の原則
- `docs/open-questions.md` … 未決事項（`Q-xxx`）。**ヒアリングで解決できるものは解決する**
- `docs/spec/` の既存ファイル … 先行する仕様書が前提を作っていることがある

読んだうえで、**この仕様書に関係する既決事項を箇条書きで提示する**。

```
001-schema.md を書く前提として、以下は決まっているものとして進めます。

- D-009: ソース非依存の中間スキーマとローダー抽象化を先に作る
- architecture.md 3節: races / runners / horses / payouts の4テーブル構成
- payouts は必須（馬連・3連複の実配当が結果表から復元できないため）

認識が違っていたら教えてください。
```

省略しないこと。ドキュメントが古い場合や、ユーザーの考えが変わっている場合をここで拾える。一度書いた仕様を後から覆すよりはるかに安い。

### 3. 依頼者が言及しない項目を自分で拾う

**依頼者は作りたいものを語るが、運用で必要になるものは語らない。** 棚卸しの最後に、以下を自問する。仕様書を書いた直後には気づかず、実装の後半で「その情報がない」と判明する類のものばかりなので、ここで拾う価値が高い。

- **出所** — そのデータがどこから来たかを記録する必要はないか。複数ソースを合流させる予定があるなら必須になる
- **時刻** — 日付だけでなく時刻が要る場面はないか。順序判定や as-of 参照は日付粒度では成立しないことがある
- **状態** — 「正常」以外を区別する必要はないか。取消・失敗・保留・無効を一律 `NULL` にすると復元できなくなる
- **母数** — 件数を数えるとき、何を分母にするかが一意に決まるか
- **単位・尺度** — 数値の単位と、順序尺度か間隔尺度かが仕様から一意に読めるか

該当するものが見つかったら、仕様に入れるか、`Q-xxx` にするかを判断する。勝手に足したなら、報告でそう言う。

### 4. 埋まらない項目を3つに仕分ける

仕様書のテンプレートを埋めようとして足りないものを列挙し、**必ず次の3つに分類する**。混同するとドキュメント構造が壊れる。

**① 仕様として決めればいいこと** → 仕様書本文に書く

他に選択肢が無いか、あっても後から変えるのが安いもの。「日付は ISO 8601」など。根拠を残す必要はない。

**② 設計判断（根拠が要ること）** → `decisions.md` に `D-xxx` を起こし、仕様書からは参照する

他の選択肢が実在し、選んだ理由が後から問われるもの。**仕様書には結論だけを書き、理由は `D-xxx` に置く。**

**③ 今決められないこと** → `open-questions.md` に `Q-xxx` を起こす

外部情報待ち、実験待ち、あるいはユーザーが判断を保留したもの。**推測で埋めない。**

見分け方はこれで足りる。

> 3ヶ月後に「なぜそうしたのか」と聞かれて答えに窮するなら ②。
> 今は答えられないなら ③。それ以外は ①。

### 5. ヒアリングする

`AskUserQuestion` を使い、**テーマごとに最大4問ずつまとめて**聞く。1問ずつ往復するとヒアリングが終わらない。

- **選択肢と推奨を必ず添える。** 「どうしますか？」という開いた質問は、設計をユーザーに丸投げしている。docsを読んだ側が案を持って聞くのが筋。
- **選択肢には「選んだら何が変わるか」を書く。** 判断材料になるのは選択肢の名前ではなく帰結。
- **既にdocsに答えがある事項は聞かない。** 手順2をやった意味がなくなる。
- **ユーザーが「わからない」「保留」と答えたら、それは ③。** 粘って推測させない。判断できないことを記録するのは失敗ではなく、正しい成果物。
- **依頼を勝手に一般化しない。** 「馬IDはソースのIDを使う」と言われたとき、レースID・騎手IDにも広げてよいかは別の質問である。広げるなら確認する。

本筋と関係ない論点が出てきたら、その場で解決しようとせず `Q-xxx` に登録して戻る。

### 6. どこまで聞いたら止めるか

> **実装者が仕様書だけを読んで、判断に迷わず着手できるか。**

読んだ人が設計判断を迫られる箇所が残っているなら足りない。逆に、これ以上細かくしても実装コードの写しにしかならない粒度に達したら止める。

### 7. 書き出す

`.claude/rules/docs-writing.md` の規約に従う。加えて、以下は仕様書の質を直接決めるので必ず守る。

#### 実装者が再導出しなくて済む形で書く

**これが仕様書の成果物である。** 散文で説明して実装者に書き起こさせるのは、仕様書の役目を果たしていない。「判断には迷わないが手が動かせない」成果物が最も無駄になる。

| 仕様書の種類 | 成果物の形 |
|---|---|
| スキーマ | 実行可能なDDL。型・NULL可否・主キー・一意制約・外部キー・CHECK |
| インターフェース | 型シグネチャそのもの（Protocol / ABC の定義） |
| 正規化・変換 | 入力→出力の対応表 |
| アルゴリズム | 数式または疑似コード |
| テスト | 具体的なケース一覧（入力と期待値） |

表や散文での補足は、この成果物に**加えて**書くものであって、代わりにはならない。

#### 調べていないことを確定として書かない

「おそらくこうである」は仕様ではなく `Q-xxx` である。

特に危険なのは外部データソースの中身に関する記述で、ページ構造・文字エンコーディング・コード値の一覧・レスポンス形式など、実物を見ずに書くとそれらしく書けてしまう。後から読んだ人は検証済みだと思う。

**「〜で動作確認済み」「〜であることを確認した」と書けるのは、実際にその手順を実行したときだけ。** 実行していないなら書かない。

未確認の項目は、その場所で `Q-xxx` を添えて未確定と分かる形にする（`NULL` 許容にする、値の列挙を確定させない、など）。末尾の未決事項表にだけ書いて本文は断定する、という書き方をしない。それは後出しであって留保ではない。

#### 根拠を仕様書に残さない

「〜のため」「〜を選んだ理由は」といった判断根拠の文が仕様書に現れたら、`decisions.md` に移すべき内容である。`decisions.md` の「根拠」欄の文章を仕様書に複製しない。参照するだけでよい。

**書き終えたら仕様書を読み返し、根拠の文が残っていないか確認する。**

### 8. 報告する

何をどこに書いたかを要約する。ユーザーはこの要約を見て分類が妥当かを判断する。

- 作成した仕様書のパスと、埋めた項目の概要
- 新設した `D-xxx` の一覧（決定内容を1行ずつ）
- 新設した `Q-xxx` の一覧（**何がブロックされるかを添える**）
- 解決した既存の `Q-xxx`
- **依頼になかったが自分の判断で足したもの**（手順3で拾った項目、依頼を一般化した箇所）

`Q-xxx` と「自分の判断で足したもの」を埋もれさせない。前者は次に何を調べるかがそのままユーザーのアクションになり、後者は確認されないと既定事実になる。

## このスキルの範囲外

- **実装コードを書くこと。** 仕様が固まった時点で止まり、実装に進むかはユーザーに確認する。
- **ドメイン知識の追加。** ヒアリング中に新しい競馬ドメインの知見が出てきた場合、`domain-knowledge.md` に `F-xxx` として追記するのは妥当だが、仕様書に混ぜない。
- **既存の決定を独断で覆すこと。** `D-xxx` と矛盾する仕様が必要になったら、その場で書き換えず、矛盾をユーザーに提示して判断を仰ぐ。
