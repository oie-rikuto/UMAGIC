# 仕様ヒアリング

UMAGICの実装仕様書を、ユーザーへのヒアリングを通じて作る。

## このスキルが必要な理由

仕様書をいきなり書こうとすると、このリポジトリでは決まった形で壊れる。

| 失敗 | 何が起きるか |
|---|---|
| 既に決まっていることを質問する | ユーザーは同じ判断を二度させられる。ドキュメントが信用されなくなる |
| 根拠を仕様書に書く | `decisions.md` と `spec/` の役割分担が崩れ、仕様変更のたびに根拠が失われる |
| 決まっていないことを推測で埋める | 後から読んだ人が「決定済み」と誤認する。最も害が大きい |
| IDを振らない・使い回す | 相互参照が壊れ、決定の履歴が追えなくなる |
| 実装の写しのような細かさで書く | 仕様書が保守されなくなる |

このスキルは、**読んでから聞く / 分からないことは分からないまま記録する / 根拠と仕様を分けて置く** の3点を機械的に守らせるためにある。

## 前提となる規約

`docs/README.md` に全体像がある。特に効いてくるのは役割分担で、**仕様書には「何をどう作るか」だけを書き、「なぜそうするか」は書かない**。根拠は `decisions.md` に `D-xxx` として置き、仕様書からは `D-xxx` で参照する。

こうしておくと、仕様が変わっても根拠が残り、根拠が変わったときに影響を受ける仕様書を特定できる。逆に仕様書に根拠を混ぜると、両方が同時に腐る。

## 手順

### 1. 対象を特定する

どの仕様書を書くのかを確定させる。`docs/spec/README.md` に想定リスト（`001-schema.md` 〜 `011-cli.md`）があるので、そこに該当するものがあれば番号と名前をそのまま使う。無ければ次の空き番号を取る。

ユーザーの依頼が「P-0の仕様を決めたい」のようにPhase単位で曖昧な場合、そのPhaseに複数の仕様書が対応することがある。**1回のヒアリングで1本**に絞ること。複数を同時に進めると質問が混ざり、どちらも中途半端になる。どれから始めるかはユーザーに選ばせる。

### 2. 既に決まっていることを棚卸しし、ユーザーに提示する

質問を作る前に、必ず以下を読む。

- `docs/decisions.md` … 確定済みの判断（`D-xxx`）
- `docs/architecture.md` … 構成・スキーマ・評価設計・Phase計画
- `docs/domain-knowledge.md` … 特徴量カタログ（`F-xxx`）とリーク防止の原則
- `docs/open-questions.md` … 未決事項（`Q-xxx`）。**ここに既に登録されている論点は、ヒアリングで解決できるなら解決する**
- `docs/spec/` の既存ファイル … 先行する仕様書が前提を作っていることがある

読んだうえで、**この仕様書に関係する既決事項を箇条書きでユーザーに提示する**。

```
001-schema.md を書く前提として、以下は決まっているものとして進めます。

- D-009: ソース非依存の中間スキーマとローダー抽象化を先に作る
- architecture.md 3節: races / runners / horses / payouts の4テーブル構成
- payouts は必須（馬連・3連複の実配当が結果表から復元できないため）
- runners.corners は F-101 と F-501 の両方が依存する

認識が違っていたら教えてください。
```

この確認は省略しないこと。ドキュメントが古い場合や、ユーザーの考えが変わっている場合をここで拾える。一度書いた仕様を後から覆すよりはるかに安い。

### 3. 埋まらない項目を3つに仕分ける

仕様書のテンプレート（目的 / 入出力 / 仕様 / 制約 / テスト観点）を埋めようとして足りないものを列挙し、**必ず次の3つに分類する**。混同するとドキュメント構造が壊れる。

**① 仕様として決めればいいこと** → 仕様書本文に書く

他に選択肢が無いか、あっても後から変えるのが安いもの。「カラム名は snake_case」「日付は ISO 8601」など。根拠を残す必要はない。

**② 設計判断（根拠が要ること）** → `decisions.md` に `D-xxx` を起こし、仕様書からは参照する

他の選択肢が実在し、選んだ理由が後から問われるもの。「馬IDをソース側のIDにするか独自採番にするか」など。**仕様書には結論だけを書き、理由は `D-xxx` に置く。**

**③ 今決められないこと** → `open-questions.md` に `Q-xxx` を起こす

外部情報待ち（規約確認、価格調査）、実験待ち（データを見ないと分からない）、あるいはユーザーが判断を保留したもの。**推測で埋めない。**

見分け方はこれで足りる。

> 3ヶ月後に「なぜそうしたのか」と聞かれて答えに窮するなら ②。
> 今は答えられないなら ③。それ以外は ①。

### 4. ヒアリングする

`AskUserQuestion` を使い、**テーマごとに最大4問ずつまとめて**聞く。1問ずつ往復するとヒアリングが終わらず、ユーザーの時間を浪費する。

質問の作り方で結果が大きく変わる。

- **選択肢と推奨を必ず添える。** 「どうしますか？」という開いた質問は、設計をユーザーに丸投げしている。docsを読んだ側が案を持って聞くのが筋。
- **選択肢には「選んだら何が変わるか」を書く。** 判断材料になるのは選択肢の名前ではなく帰結。
- **既にdocsに答えがある事項は聞かない。** 手順2をやった意味がなくなる。
- **ユーザーが「わからない」「保留」と答えたら、それは ③。** 粘って推測させない。判断できないことを記録するのは失敗ではなく、正しい成果物。

ヒアリング中に、当初の対象と関係ない論点が出てくることがある。その場で解決しようとせず、`Q-xxx` として登録して本筋に戻る。

### 5. どこまで聞いたら止めるか

判定基準はひとつ。

> **実装者が仕様書だけを読んで、判断に迷わず着手できるか。**

読んだ人が設計判断を迫られる箇所が残っているなら、まだ足りない。逆に、これ以上細かくしても実装コードの写しにしかならない粒度に達したら止める。仕様書は実装の設計図であって、実装そのものではない。

### 6. 書き出す

**IDの採番** — 既存の最大値を調べてから振る。**一度振ったIDは絶対に再利用しない。**

```bash
grep -h '^## [DQ]-' docs/decisions.md docs/open-questions.md
ls docs/spec/
```

決定が覆る場合は、元のIDに `Superseded by D-xxx` を残したうえで新しいIDを振る。上書きしない。

**仕様書** — `docs/spec/README.md` のテンプレートに従う。ヘッダ表の `関連決定` / `関連特徴量` は、手順2で棚卸ししたものと手順4で新設した `D-xxx` を並べる。新規作成時の `状態` は `Draft`。

**制約の節** — UMAGIC固有の制約のうち、その仕様書に該当するものを必ず明記する。特に以下は該当すれば漏らさないこと。実装時に最も踏まれやすい地雷であり、仕様書に書いていないと確実に踏まれる。

- 予測対象レースのオッズを特徴量にしない（`D-002`。例外は `F-701` / `F-703` の過去オッズのみ）
- 学習はG1に絞らず全レースで行う（`D-003`）
- リーク防止の6原則（`docs/domain-knowledge.md` 5節）。特に同日レースの前後判定（`F-501` / `F-502` の例外規定）
- 回収率は信頼区間なしに報告しない（`D-008`）

**`decisions.md`** — 手順3で②に分類したものを `D-xxx` として追記する。書式は既存エントリに合わせ、**決定 / 根拠 / 影響 / 状態** を埋める。

**`open-questions.md`** — 手順3で③に分類したものを `Q-xxx` として追記する。**問い / 必要な情報 / ブロックするもの / 状態** を埋める。「決めるために何を調べればいいか」まで書くこと。これが無いと、次に読んだ人が同じところで止まる。

既存の `Q-xxx` をヒアリングで解決できた場合は、`open-questions.md` 側を `Resolved → D-xxx` に更新する。放置すると未決リストが信用できなくなる。

### 7. 報告する

書き終えたら、何をどこに書いたかを要約する。ユーザーはこの要約を見て、分類が妥当かを判断する。

- 作成した仕様書のパスと、埋めた項目の概要
- 新設した `D-xxx` の一覧（決定内容を1行ずつ）
- 新設した `Q-xxx` の一覧（**何がブロックされるかを添える**）
- 解決した既存の `Q-xxx`

`Q-xxx` は「聞いたけど決まらなかったこと」なので、報告で埋もれさせない。次に何を調べればいいかが、そのままユーザーの次のアクションになる。

## このスキルの範囲外

- **実装コードを書くこと。** 仕様が固まるまでがこのスキルの仕事。仕様書を書き終えた時点で一度止まり、実装に進むかはユーザーに確認する。
- **ドメイン知識の追加。** ヒアリング中に新しい競馬ドメインの知見（特徴量のアイデアなど）が出てきた場合、`domain-knowledge.md` に `F-xxx` として追記するのは妥当だが、仕様書に混ぜてはいけない。
- **既存の決定を独断で覆すこと。** ヒアリングの結果 `D-xxx` と矛盾する仕様が必要になったら、その場で書き換えず、矛盾をユーザーに提示して判断を仰ぐ。
