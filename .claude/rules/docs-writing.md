# ドキュメント執筆規約

`docs/` 配下を編集するときの規約。設計原則そのものは `CLAUDE.md` にある。

## 役割分担

「なぜ」と「何を作るか」を分離している。**この境界を壊さないこと。**

| ファイル | 書くこと | 書かないこと |
|---|---|---|
| `docs/requirements.md` | 満たすべき要件（`R-xxx`）。検証可能な形で書く | 実現方法 |
| `docs/decisions.md` | 設計判断とその根拠 | 実装の詳細 |
| `docs/domain-knowledge.md` | 競馬ドメインの知識、特徴量カタログ | 実装の詳細 |
| `docs/architecture.md` | 構成・スキーマ・評価設計・Phase計画 | 個別の実装仕様 |
| `docs/spec/` | 実装仕様 | **判断の根拠**（`D-xxx` を参照するに留める） |
| `docs/tasks.md` | 実作業の単位と完了条件 | 設計・要件の本体（参照に留める） |

`design.md` は作らない（`D-019`）。設計は `architecture.md`（全体）と `docs/spec/`（モジュール単位）が担う。

仕様書を書いている最中に新しい設計判断が発生したら、**まず `decisions.md` に `D-xxx` を追加してから**仕様書側で参照する。仕様書の本文に根拠を書き込まない。

「〜のため」「〜を選んだ理由は」といった判断根拠の文が仕様書に現れたら、それは `decisions.md` に移すべき内容である。

## ID体系

| プレフィックス | 対象 | 定義場所 |
|---|---|---|
| `D-xxx` | 決定 | `decisions.md` |
| `F-xxx` | 特徴量 | `domain-knowledge.md` |
| `Q-xxx` | 未決事項 | `open-questions.md` |
| `P-x` | 開発フェーズ | `architecture.md` |
| `R-xxx` | 要件 | `requirements.md` |

`docs/tasks.md` のタスクにはIDを振らない（`D-019`）。完了すれば消える性質のため、`R-xxx` と仕様書への参照で追跡する。

**一度振ったIDは再利用しない。** 決定が覆った場合は、元のIDに `Superseded by D-xxx` を残したうえで新しいIDを振る。上書きしない。

採番の前に既存の最大値を確認する。

```bash
grep -hE '^#{2,3} [DQR]-' docs/decisions.md docs/open-questions.md docs/requirements.md
```

**見出しレベルはファイルによって違う。** `decisions.md` と `open-questions.md` は `## D-xxx` / `## Q-xxx` だが、`requirements.md` は `## 1. スコープと出力` のような区分の下に `### R-xxx` を置く。`^## ` だけを見る grep は R を1件も拾わず、**既存の要件が無いように見えて採番が衝突する。**

## 要件の書き方（`requirements.md`）

要件は **「満たされたかどうかを判定できる形」** で書く。判定できない文は要件ではない。

| これは要件ではない | 要件の形 |
|---|---|
| 精度の高いモデルを作る | G1での LogLoss が市場確率 `normalize(1/単勝オッズ)` を下回る |
| データを正しく取り込む | 取り込んだ全レースで `n_starters` と `status='ran'` の行数が一致する |
| リークを防ぐ | 発走時刻より後の情報を参照した特徴量が存在しないことをテストで示せる |

**実現方法を書かない。** 「LightGBMのlambdarankを使う」は設計であって要件ではない。要件は「何を満たすか」までで止め、どう作るかは `architecture.md` と `docs/spec/` に置く。

多くの要件は既存の `D-xxx` から導出できる（`D-002` `D-008` `D-015` など）。ヒアリングの主目的は、**決定になっていない暗黙の要件を掘り出すこと**。

書式：区分の見出し（`## 1. スコープと出力`）の下に置く。

```markdown
### R-001 <一文で書いた要件>

**区分**: 機能 / 品質 / 制約
**判定方法**: どうやって満たされたと確認するか
**根拠**: `D-xxx`（あれば）
```

## `tasks.md` の書き方

Phase ごとの見出しとチェックボックスで書く。IDは振らない（`D-019`）。

```markdown
## P-0 データ基盤

- [ ] 中間スキーマのDDLを実装する（`001-schema.md` / `R-003`）
      完了条件: 全テーブルが作成でき、意図した制約違反が拒否される
```

各タスクは以下を満たすこと。

- **検証可能な完了条件を持つ。** 「〜を検討する」はタスクではない
- **1回のコミットで終わる粒度。** 数日かかるものは分解する
- **参照を持つ。** 該当する仕様書と `R-xxx`
- **依存順に並べる。** 上から順に着手できる状態にする

## 仕様書を書く手順

1. `docs/spec/NNN-<名前>.md` を作る。番号は `docs/spec/README.md` の想定リストに従う
2. ヘッダ表で関連する `D-xxx` / `F-xxx` を参照する。新規作成時の状態は `Draft`
3. 新たな設計判断が出たら、先に `decisions.md` に `D-xxx` を追加してから参照する
4. 決められないことは `open-questions.md` に `Q-xxx` として登録する。**推測で埋めない**

推測で埋めると、後から読んだ人が「決定済み」と誤認する。これが最も害が大きい。

未検証の事実を確定として書かないこと。「調査していないが、おそらくこうである」は仕様ではなく `Q-xxx` である。

## 仕様書の制約節に必ず書くもの

該当する場合は漏らさないこと。実装時に最も踏まれやすく、仕様書に書いていないと確実に踏まれる。

- 予測対象レースのオッズを特徴量にしない（`D-002`）
- 学習はG1に絞らず全レースで行う（`D-003`）
- リーク防止の7原則（`domain-knowledge.md` 5節）。特に同日レースの前後判定（`F-501`/`F-502` の例外規定）と、原則7（集計統計量の推定期間も as-of で切る）
- 回収率は信頼区間なしに報告しない（`D-008`）

## テンプレート

`docs/spec/README.md` にある。ヘッダ表・目的・入出力・仕様・制約・テスト観点・未決事項の構成。
