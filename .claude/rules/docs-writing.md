# ドキュメント執筆規約

`docs/` 配下を編集するときの規約。設計原則そのものは `CLAUDE.md` にある。

## 役割分担

「なぜ」と「何を作るか」を分離している。**この境界を壊さないこと。**

| ファイル | 書くこと | 書かないこと |
|---|---|---|
| `docs/decisions.md` | 設計判断とその根拠 | 実装の詳細 |
| `docs/domain-knowledge.md` | 競馬ドメインの知識、特徴量カタログ | 実装の詳細 |
| `docs/architecture.md` | 構成・スキーマ・評価設計・Phase計画 | 個別の実装仕様 |
| `docs/spec/` | 実装仕様 | **判断の根拠**（`D-xxx` を参照するに留める） |

仕様書を書いている最中に新しい設計判断が発生したら、**まず `decisions.md` に `D-xxx` を追加してから**仕様書側で参照する。仕様書の本文に根拠を書き込まない。

「〜のため」「〜を選んだ理由は」といった判断根拠の文が仕様書に現れたら、それは `decisions.md` に移すべき内容である。

## ID体系

| プレフィックス | 対象 | 定義場所 |
|---|---|---|
| `D-xxx` | 決定 | `decisions.md` |
| `F-xxx` | 特徴量 | `domain-knowledge.md` |
| `Q-xxx` | 未決事項 | `open-questions.md` |
| `P-x` | 開発フェーズ | `architecture.md` |

**一度振ったIDは再利用しない。** 決定が覆った場合は、元のIDに `Superseded by D-xxx` を残したうえで新しいIDを振る。上書きしない。

採番の前に既存の最大値を確認する。

```bash
grep -h '^## [DQ]-' docs/decisions.md docs/open-questions.md
```

## 仕様書を書く手順

1. `docs/spec/NNN-<名前>.md` を作る。番号は `docs/spec/README.md` の想定リストに従う
2. ヘッダ表で関連する `D-xxx` / `F-xxx` を参照する。新規作成時の状態は `Draft`
3. 新たな設計判断が出たら、先に `decisions.md` に `D-xxx` を追加してから参照する
4. 決められないことは `open-questions.md` に `Q-xxx` として登録する。**推測で埋めない**

推測で埋めると、後から読んだ人が「決定済み」と誤認する。これが最も害が大きい。

未検証の事実を確定として書かないこと。「調査していないが、おそらくこうである」は仕様ではなく `Q-xxx` である。

## 仕様書の制約節に必ず書くもの

該当する場合は漏らさないこと。実装時に最も踏まれやすく、仕様書に書いていないと確実に踏まれる。

- 予測対象レースのオッズを特徴量にしない（`D-002`）
- 学習はG1に絞らず全レースで行う（`D-003`）
- リーク防止の6原則（`domain-knowledge.md` 5節）。特に同日レースの前後判定（`F-501`/`F-502` の例外規定）
- 回収率は信頼区間なしに報告しない（`D-008`）

## テンプレート

`docs/spec/README.md` にある。ヘッダ表・目的・入出力・仕様・制約・テスト観点・未決事項の構成。
